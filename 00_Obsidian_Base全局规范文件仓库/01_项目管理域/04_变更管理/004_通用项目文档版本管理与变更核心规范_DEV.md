## 3. 范围

本规范适用于所有**自动化项目**（含 PLC 控制、Python 开发、机器人控制、上位机数据系统、产品化项目等）的文档版本管理和变更控制，旨在确保文档的可追溯性、一致性和质量。

## 4. 术语定义

| 术语 | 定义 |
|------|------|
| 版本管理 | 对文档的版本进行控制和管理的过程 |
| 变更控制 | 对文档变更进行评估、审批和实施的过程 |
| 语义化版本 | 一种版本号格式，包含主版本、次版本和补丁版本 |
| 基线 | 文档的一个特定版本，作为后续变更的参考点 |
| 变更请求 | 正式提出的文档变更申请 |

## 5. 文档版本管理

### 5.1 版本号格式

文档版本号应遵循语义化版本规范：

```
MAJOR.MINOR.PATCH
```

- **MAJOR**：不兼容的文档变更，如结构重大调整、内容大幅修改
- **MINOR**：向后兼容的功能添加，如新增章节、扩展内容
- **PATCH**：向后兼容的错误修复，如修正拼写错误、调整格式

### 5.2 版本号管理

1. **初始版本**：新文档的初始版本号为 `V1.0.0`
2. **版本递增**：
   - 重大变更：增加主版本号，次版本和补丁版本重置为0（如 `V1.0.0` → `V2.0.0`）
   - 功能添加：增加次版本号，补丁版本重置为0（如 `V1.0.0` → `V1.1.0`）
   - 错误修复：增加补丁版本号（如 `V1.0.0` → `V1.0.1`）
3. **版本标记**：版本号仅在文档内部声明（frontmatter `version` 字段 + 文档基础信息表 + 版本变更记录表），文件名不包含版本号。版本信息的权威来源是 frontmatter 和 `spec_registry.json`

### 5.3 版本命名规范

文档文件名使用前缀码标识文档类型，格式为：

**格式**：`[文档名称]_[前缀码].md`

> **说明**：版本号不再包含在文件名中。版本信息通过文档内部声明（frontmatter `version` 字段、文档基础信息表、版本变更记录表）和 `spec_registry.json` 进行管理。这避免了每次版本变更都需要重命名文件的问题。

## 6. 文档变更控制

### 6.1 变更流程

1. **变更申请**：提出变更请求，描述变更原因、内容和影响
2. **变更评估**：评估变更的必要性、可行性和影响
3. **变更审批**：根据变更的影响程度，由不同级别的人员审批
4. **变更实施**：执行已批准的变更
5. **变更验证**：验证变更是否成功实施
6. **变更记录**：记录变更的详细信息，包括变更原因、内容、审批人和实施人

### 6.2 变更请求

变更请求应包含以下信息：

- **变更编号**：唯一标识变更的编号
- **变更原因**：说明为什么需要变更
- **变更内容**：详细描述变更的具体内容
- **变更影响**：分析变更对其他文档和项目的影响
- **变更优先级**：标记变更的紧急程度
- **变更申请人**：提出变更的人员
- **申请日期**：提出变更的日期

### 6.3 变更审批

根据变更的影响程度，变更审批分为以下级别：

| 变更级别 | 影响程度 | 审批人 |
|---------|----------|--------|
| 轻微变更 | 影响范围小，不影响其他文档 | 文档负责人 |
| 中等变更 | 影响范围中等，可能影响其他文档 | 项目经理 |
| 重大变更 | 影响范围大，可能影响整个项目 | 项目负责人 |

### 6.4 变更记录

变更记录应包含以下信息：

- **变更编号**：唯一标识变更的编号
- **变更内容**：详细描述变更的具体内容
- **变更原因**：说明为什么需要变更
- **变更前版本**：变更前的文档版本
- **变更后版本**：变更后的文档版本
- **审批人**：批准变更的人员
- **实施人**：执行变更的人员
- **变更日期**：变更实施的日期

## 7. 文档基线管理

### 7.1 基线定义

基线是文档的一个特定版本，作为后续变更的参考点。基线应在以下情况下建立：

- 文档首次发布时
- 文档经过重大变更后
- 项目的关键里程碑点

### 7.2 基线管理

1. **基线创建**：创建基线时，应记录基线的版本号、创建日期和创建原因
2. **基线变更**：基线一旦建立，除非经过正式的变更审批流程，否则不得修改
3. **基线回溯**：应能够回溯到任何已建立的基线版本

### 7.3 基线命名

基线命名格式为：

**格式**：`[文档名称]_BASE`

**示例**：
- `需求分析文档_BASE`
- `技术设计文档_BASE`

> **说明**：基线版本号通过文档内部版本变更记录和 Git 标签管理，不再包含在文件名中。

## 8. 文档版本历史

### 8.1 版本历史记录

每个文档应包含版本历史记录，记录文档的所有版本变更。版本历史记录应包含以下信息：

| 版本号 | 变更内容 | 变更人 | 变更日期 |
|--------|----------|--------|----------|
| V1.0.0 | 初始版本 |  |  |
| V1.0.1 | 修正拼写错误 |  |  |
| V1.1.0 | 新增章节 |  |  |
| V2.0.0 | 结构重大调整 |  |  |

### 8.2 版本历史管理

- 版本历史记录应位于文档的末尾
- 每次变更后，应更新版本历史记录
- 版本历史记录应按时间倒序排列，最新版本在前

## 10. 文档版本管理最佳实践

1. **一致性**：在整个项目中保持文档版本管理的一致性
2. **可读性**：使用清晰、描述性的版本号和变更记录
3. **可追溯性**：确保每个版本的变更都有详细的记录
4. **安全性**：确保文档的版本历史不被意外删除或修改
5. **协作性**：支持多人协作编辑文档，同时保持版本的一致性
6. **自动化**：使用工具自动管理文档版本和变更
7. **定期审查**：定期审查文档版本管理的执行情况，及时纠正不符合规范的做法

## 11. 常见问题与解决方案

### 11.1 版本冲突

**问题**：多人同时编辑文档时出现版本冲突

**解决方案**：
- 使用支持冲突解决的版本控制系统
- 建立文档编辑的协作规则，避免同时编辑同一文档
- 定期合并和同步文档版本

### 11.2 版本丢失

**问题**：文档版本历史丢失或损坏

**解决方案**：
- 定期备份文档和版本历史
- 使用可靠的版本控制系统
- 建立版本历史的审计机制

### 11.3 变更管理混乱

**问题**：变更管理流程不规范，导致变更混乱

**解决方案**：
- 建立明确的变更管理流程
- 使用变更管理工具跟踪变更
- 定期审查变更管理的执行情况
