# 046_通用任务派发契约模板 (Handoff Payload Template)

本规范用于定义多智能体在跨域流转（如 PM -> PLC, PM -> Fullstack）时，物理派发契约（handoff_payload.json）中必须携带的核心 Prompt（提示词）指令。

## 1. Grooming (预研模式)

当 PM 发起前期技术探路与代码基上下文调研时，子代理必须遵循以下约束：

### Goal (目标)
[阶段：Grooming/预研] 请根据 PM_SESSION 了解业务背景，并使用工具主动检索当前项目代码库（包括 SCL/Python/QML 源码、.plc.json、INT.md、VAR.md、DTO、现有测试用例）。请提取相关变量定义、工站状态机逻辑、接口协议与依赖关系，评估变更可行性与受影响范围，然后通过 handoff_result 回传事实摘要给 PM。

### Strict Constraints (绝对约束)
1. 绝对服从隔离原则，本次仅仅是技术探路与事实挖掘，严禁直接修改或编写业务代码。
2. 严禁向 PM 或用户询问代码库中已存在的变量名、常量、配置参数或现有逻辑。
3. 必须提供具体代码位置（文件路径、行号范围、数据结构定义）。
4. 如果发现需求中存在与现有代码严重冲突或物理硬件不可行之处，在回执中明确列出冲突点与备选技术建议。

## 2. Execution (执行模式)

当需求明确且经过审批，PM 发起正式代码执行时，子代理必须遵循以下约束：

### Goal (目标)
[阶段：Execution/执行] 请根据 PM_SESSION 中的最新需求和架构设计，进行代码重构与填空（若有 TODO: [auto-pm check]）。完成编码后，必须确保所有语法测试与物理门禁全绿，然后回执。

### Strict Constraints (绝对约束)
1. 绝对服从零负担原则，不要把未通过门禁（非 Exit Code 0）的半成品抛回给 PM。
2. 你的所有行为规范和业务逻辑约束，已在下方的 injected_specs 中提供，严禁自行脑补规范。
3. 若存在不可抗拒的外部库原因导致测试无法通过，且确定逻辑无误，需在代码中使用特定的豁免标签（如 # SUPPRESS_TAMPER_CHECK: 架构师已批准，或 // SUPPRESS_TAMPER_CHECK）放行，但必须在回执中明确说明原因。
