# 功能模块迭代流程标准

## 1. 文档定位

### 1.1 在规范体系中的位置

本文档是 `[[010_通用项目管理规范]]` 在 **技术项目迭代执行层面** 的操作细化：

| 规范层次 | 文档 | 关注点 |
|----------|------|--------|
| L1 - 原则层 | 010_通用项目管理规范 | 项目管理的原则、最佳实践 |
| L2 - 计划层 | 027_迭代项目计划模板 | 单次迭代的计划制定 |
| **L3 - 执行层** | **本文档 (033)** | **迭代的具体执行步骤、质量门禁、角色分工** |
| L4 - 验证层 | 032_GUI测试方案标准 | 迭代中的测试验证方法 |

### 1.2 适用场景

- Python项目管理工具 (SW-2026-004) 及其衍生项目的功能模块迭代
- 使用 Trae IDE Agent 架构进行 AI 辅助开发的项目
- 需要 Spec 驱动开发的软件项目（可推广到其他类似项目）

- 010 定义了项目管理的"原则和框架"（做什么）

## 2. 文档概述

### 2.1 目的

本文档旨在建立标准化的功能模块迭代流程，确保每次迭代都能：

- **高质量交付**（bug 少、稳定性高）
- **可追溯**（有完整的 spec 和 test 记录）
- **可复用**（测试方案和迭代流程可供后续参考）
- **低风险**（充分测试后再发布）

本文档是基于实际项目多个版本迭代的实战经验总结而成，所有流程、检查点和规范都经过实际验证。

### 2.2 适用范围

- 所有功能模块的新增、修改、重构
- Bug 修复（特别是 P0/P1 级别）
- 性能优化
- 技术债务偿还

### 2.3 核心原则

1. **文档先行**：先写 spec，再编码。实际项目的成功证明了这一点——先有清晰的 spec.md、tasks.md、checklist.md，实现时才能有的放矢。
2. **小步快跑**：每个 iteration 聚焦 1-3 个核心问题。实践表明，一次试图解决太多问题会导致质量失控。
3. **真实测试**：必须在真实环境验证，不接受模拟结果。某些版本的核心问题就是用脚本模拟测试，导致用户完全不信任。
4. **充分沟通**：每个阶段结束都与相关方确认。
5. **根因分析**：不只是修 symptom，而是找到 root cause。通过诊断阶段可以发现隐藏问题。

## 3. 迭代生命周期

### 3.1 迭代阶段总览

```
┌─────────────────────────────────────────────────────────────┐
│                    迭代生命周期                              │
├─────────┬─────────┬─────────┬─────────┬─────────┬──────────┤
│ Phase 0 │ Phase 1 │ Phase 2 │ Phase 3 │ Phase 4 │ Phase 5  │
│ 需求分析│  Spec   │  实现   │  验证   │  文档   │  发布   │
│  &规划  │  设计   │         │  &测试  │  &总结  │  &归档  │
└─────────┴─────────┴─────────┴─────────┴─────────┴──────────┘
     0.5h      1-2h     2-8h     1-3h      1-2h      0.5h
```

**总周期估算**：小型迭代（1-3 个 bug）约 6-16 小时，建议在 1 个工作日内完成。

---

### 3.2 各阶段详细说明

#### Phase 0: 需求分析与规划（输入）

**目标**: 明确"做什么"和"为什么做"

**参与角色**: 用户/产品经理 + 技术负责人

**活动**:

1. 收集需求（用户反馈、bug 报告、新功能请求）
2. 分析需求可行性
3. 评估影响范围
4. 确定优先级（P0/P1/P2/P3）
5. 制定 iteration scope（聚焦核心，避免过度承诺）

**产出物**:

- [ ] 需求描述文档（可以是简单的 issue 描述）
- [ ] 影响范围分析
- [ ] 优先级排序
- [ ] Iteration scope 定义（明确做什么，不做什么）

**时间估算**: 0.5 - 1 小时

**退出标准**:

- ✅ 需求明确无歧义
- ✅ scope 清晰且可控
- ✅ 相关方对目标达成一致

**实践要点**：
以某次实际迭代为例，用户反馈模板刷新后只显示 1 个模板、版本号错误等问题。影响分析涉及 constants.py、template_manager.py、config.py、template_service.py 四个文件。最终 scope 决策：只聚焦模板数量、刷新逻辑、版本号三个核心问题，不做其他功能改进，优先级全部定为 P0。

---

#### Phase 1: Spec 设计（计划）

**目标**: 明确"怎么做"

**参与角色**: 技术负责人 + 开发工程师

**活动**:

1. 创建 `.trae/specs/{change-id}/` 目录
2. 编写 `spec.md`（需求规格说明书）
3. 编写 `tasks.md`（任务分解清单）
4. 编写 `checklist.md`（验收检查清单）
5. 进行技术方案评审（如需要）

**spec.md 内容要求**:

```markdown
# {Feature Name} Spec

## Why
[1-2句话说明问题或机会]

## What Changes
- 变更项1
- 变更项2
- **BREAKING** 如有破坏性变更

## Impact
- 影响的 spec: [...]
- 影响的代码: [关键文件列表]

## Requirements
### Requirement: XXX
The system SHALL provide...

#### Scenario: Success case
- **WHEN** user does X
- **THEN** result Y
```

**tasks.md 内容要求**:

- 每个任务都是**可验证的**（有明确的 done 标准）
- 任务粒度适中（0.5-2 小时可完成）
- 标注依赖关系
- 标注优先级（P0/P1/P2/P3）
- 包含具体的 Test Requirements

**checklist.md 内容要求**:

- 每个 requirement 都有对应的检查项
- 检查项是二值的（通过/不通过）
- 包含最终的 AC（Acceptance Criteria）
- GUI 测试项要具体到操作步骤

**产出物**:

- [ ] spec.md（已通过 NotifyUser 确认）
- [ ] tasks.md（任务分解完成）
- [ ] checklist.md（验收标准明确）

**时间估算**: 1 - 2 小时

**退出标准**:

- ✅ spec 已获得用户/项目经理批准
- ✅ 任务分解合理且可执行
- ✅ 验收标准清晰可量化

**实践要点**：
优秀的 spec 设计体现在：Why 清晰直接列出核心问题；Scope 明确用"聚焦范围"标题强调只做核心修复；Impact 具体列出受影响的代码文件；Requirements 可测试每个 requirement 都有 WHEN-THEN 场景；Open Questions 引导诊断预留了需要探索的问题。spec.md 中特别好的做法是增加了"Open Questions"部分，这为诊断任务提供了明确的探索方向。tasks.md 的优秀之处包括：Task 1 是纯诊断任务不修改代码先理解问题；每个任务都有 Test Requirements；标注了依赖关系支持并行执行。

#### Phase 2: 实现（执行）

**目标**: 按照 spec 完成编码

**参与角色**: 开发工程师（Senior Developer agent）

**活动**:

1. 读取 tasks.md，理解任务要求
2. 按 task 顺序（考虑依赖关系）逐一实现
3. 每完成一个 task，立即更新 tasks.md 的 checkbox
4. 遵循现有代码风格和架构模式
5. 如遇需求不清，及时反馈不要猜测

**编码规范**:

- ✅ 先读现有代码，理解上下文
- ✅ 复用已有的工具函数和类
- ✅ 保持一致的命名风格
- ✅ 添加必要的错误处理和日志
- ❌ 不要过度设计（YAGNI 原则）
- ❌ 不要引入未经测试的新依赖

**产出物**:

- [ ] 修改后的代码文件（已通过语法检查）
- [ ] tasks.md 更新（完成的 task 已勾选）
- [ ] 关键代码段的注释或 commit message

**时间估算**: 根据 task 数量和复杂度（通常 2-8 小时）

**退出标准**:

- ✅ 所有 task 的代码已完成
- ✅ 无语法错误
- ✅ tasks.md 全部勾选

**实践要点**：
良好的实现阶段遵循以下实践：Task 1 先诊断读取关键配置文件对比参考规范发现缺少某些模板定义；检查相关模块的刷新逻辑。Task 2 和 3 并行修复根据诊断结果同时修复模板定义和 UI 逻辑。Task 4 独立处理其他问题确认修改是否生效。增量式更新每完成一个 task 就勾选保持进度透明。关键发现可能包括：数据库中存在旧记录这是之前版本的残留数据；配置文件存在多层配置关系修改时需注意级联效应；服务层需要增加清理逻辑来处理脏数据。

---

#### Phase 3: 验证与测试（质量控制）

**目标**: 确保实现满足需求

**参与角色**: QA 工程师 + 开发工程师 + 用户（最终验收）

**这是最关键的阶段！**

多次迭代的成功和失败都证明了这个阶段的重要性。

##### 3.1 自动化验证（如有）

- 运行单元测试
- 运行 lint 检查（pylint, flake8 等）
- 运行类型检查（mypy 等）

##### 3.2 GUI 功能测试（必须！）

**参照 `[[032_GUI测试方案标准]]` 执行**

**测试层级**:

**Level 1: Smoke Test（冒烟测试）- 10 分钟**

- [ ] 程序能启动
- [ ] 核心功能可访问
- [ ] 无明显崩溃

**Level 2: Function Test（功能测试）- 30-60 分钟**

- [ ] 按照 checklist.md 逐项验证
- [ ] 正常路径测试
- [ ] 边界情况测试
- [ ] 异常路径测试

**Level 3: Regression Test（回归测试）- 20-30 分钟**

- [ ] 之前修复的 bug 未复现
- [ ] 相关功能未被破坏
- [ ] 性能无明显退化

**Level 4: Data Consistency Test（数据一致性）- 10 分钟**

- [ ] 数据库记录与 UI 显示一致
- [ ] 生成的文件/目录结构符合预期
- [ ] 配置文件正确更新

**测试执行原则**:

1. **真实性**: 必须运行真实程序，不能模拟
   - **反例**：用脚本调用 API 模拟 GUI 操作，结果"测试通过"但实际 GUI 有严重 bug
   - **正例**：启动完整 GUI 程序，手动点击按钮、查看界面、创建项目
2. **完整性**: 按照测试方案严格执行，不能跳过步骤
3. **可追溯**: 保留截图、日志、测试数据
4. **诚实性**: 发现问题如实记录，不掩盖

**产出物**:

- [ ] 测试报告（包含每个 test case 的结果）
- [ ] 截图证据（关键步骤）
- [ ] 日志证据（如有错误或警告）
- [ ] Bug 清单（如有问题）

**时间估算**: 1 - 3 小时（取决于测试范围）

**退出标准**:

- ✅ checklist.md 所有检查项通过
- ✅ 无 P0/P1 级 bug
- ✅ 测试报告已撰写
- ✅ 用户（或代理用户）已验收

**实践对比**：

| 维度 | 失败案例 | 成功案例 |
|------|---------|---------|
| 测试方式 | 脚本模拟 API 调用 | 启动真实 GUI 程序 |
| 测试深度 | 只检查返回值 | 手动点击、截图、创建项目 |
| 问题发现 | 未发现 UI 渲染问题 | 发现数据库残留数据 |
| 测试耗时 | 较短（但无效） | 约 1 小时（有效） |
| 用户信任 | 不信任 | 信任 |

成功的测试过程详细记录了 GUI 测试过程：版本号验证启动程序后看到标题栏显示正确版本号；模板数量验证初始加载显示正确数量数据；刷新功能验证连续点击多次刷新每次都稳定显示正确数量；项目创建验证使用不同模板分别创建项目验证目录结构；最终结果所有测试项全部通过。**重要发现**：在测试过程中发现了数据库层面的脏数据问题，这是纯代码审查无法发现的。这再次强调了**真实环境测试**的必要性。

#### Phase 4: 文档化与总结（收尾）

**目标**: 记录经验教训，产出可复用的资产

**参与角色**: Documentation Expert + Project Manager

**活动**:

1. 更新用户手册（如有功能变更）
2. 更新 API 文档（如有接口变更）
3. 编写迭代总结报告
4. 归档测试产物
5. 更新版本历史

**迭代总结报告模板**:

```markdown
# Iteration {Version} 总结报告

## 基本信息
- 版本号: Vx.x.x
- 迭代周期: YYYY-MM-DD ~ YYYY-MM-DD
- 参与人员: [...]

## 目标达成情况
| Goal | Status | Notes |
|------|--------|-------|
| 目标1 | ✅/❌ | ... |

## 完成的任务
- [x] Task 1: ...
- [x] Task 2: ...

## 发现的问题
| Bug ID | Description | Severity | Status |
|--------|-------------|----------|--------|
| BUG-xxx | ... | P0/P1/P2 | Fixed/Open |

## 经验教训
### 做得好的
1. ...
2. ...

### 需要改进的
1. ...
2. ...

## 数据指标
- 代码变更行数: +/- xxx
- 新增/修改文件数: xx
- 测试用例数: xx (通过率 xx%)
- 测试耗时: x 小时

## 下一步计划
- [ ] ...
```

**产出物**:

- [ ] 迭代总结报告
- [ ] 更新后的用户文档（如有）
- [ ] 测试产物归档
- [ ] version.py 版本号更新

**时间估算**: 1 - 2 小时

**实践要点**：
从成功实践中可以提取的关键经验：

**做得好的**：
1. Scope 聚焦策略有效 - 只做核心问题避免过度承诺
2. 诊断先行策略有效 - Task 1 的纯诊断避免了盲目修改
3. 真实 GUI 测试发现了代码审查无法发现的问题（数据库脏数据）
4. 增量式验证减少了返工 - 每修一个就测一个

**需要改进的**：
1. 数据库层面验证不够前置 - 应该在 Phase 1 的 Impact 分析中就考虑数据迁移
2. 配置级联关系复杂 - 多层配置关系应该文档化
3. 初次测试可以更全面 - 第一次测试应该包含数据一致性检查

## 4. 角色职责分工

### 4.1 角色定义

| 角色 | 职责 | 技能要求 |
|------|------|----------|
| **用户/产品经理** | 提出需求、验收最终成果 | 业务理解、需求表达 |
| **技术负责人** | Spec 设计、技术方案评审 | 架构设计、技术选型 |
| **开发工程师** | 编码实现、单元测试 | 编码能力、调试技能 |
| **QA 工程师** | 测试执行、缺陷报告 | 测试方法论、细致耐心 |
| **文档工程师** | 文档编写、知识沉淀 | 写作能力、结构思维 |
| **项目经理** | 进度管控、协调沟通 | 项目管理、风险管理 |
| **发布工程师** | 打包部署、版本管理 | 构建工具、运维知识 |

### 4.2 协作流程

```
用户提出需求
    ↓
技术负责人设计 Spec ←→ 用户确认
    ↓
开发工程师实现 ←→ 技术负责人 code review
    ↓
QA 工程师测试 ←→ 开发工程师修复 bug
    ↓
用户验收 ←→ 项目经理协调
    ↓
发布工程师打包交付
```

### 4.3 Trae IDE Agent 架构的角色映射（重要）

**当前项目的角色映射**（基于 Trae IDE 的 Agent 架构）：

| 传统角色 | Trae Agent | 实际执行者 |
|---------|-----------|-----------|
| 用户/产品经理 | 用户本人 | 用户提供需求，NotifyUser 确认 |
| 技术负责人 | Documentation Expert / Senior Developer | 编写 spec，设计方案 |
| 开发工程师 | Senior Developer agent | 执行编码任务 |
| QA 工程师 | Documentation Expert + 用户 | 执行 GUI 测试，记录结果 |
| 文档工程师 | Documentation Expert | 编写文档，总结经验 |
| 项目经理 | 用户 + Documentation Expert | 协调进度，管理风险 |
| 发布工程师 | 用户或自动化脚本 | 执行打包和部署 |

**Trae IDE Agent 架构的特殊性说明**：

本文档特别针对使用 Trae IDE Agent 架构的项目进行了优化。在这种架构下：

1. **Agent 协作模式**：不同的 Agent 扮演不同角色，通过对话和文件协作完成任务
2. **Documentation Expert 的核心作用**：不仅负责文档编写，还承担技术负责人、QA、PM 等多重角色
3. **用户的深度参与**：用户不仅是需求提出者，还是关键的确认者和验收者
4. **Spec 驱动的重要性增强**：由于 Agent 需要明确指令，spec.md 的质量直接影响执行效果
5. **自动化程度高**：编码、测试等环节可以高度自动化，但质量门禁不能省略

## 5. 质量门禁（Quality Gates）

在每个 Phase 结束时，必须通过对应的质量门禁才能进入下一阶段。

### 5.1 门禁清单

| Phase | Quality Gate | 验证方式 | Gatekeeper |
|-------|-------------|----------|------------|
| Phase 0 → 1 | 需求明确且 scope 可控 | 需求评审会议 | 技术负责人 |
| Phase 1 → 2 | Spec 已获批准 | NotifyUser 确认 | 用户/PM |
| Phase 2 → 3 | 代码完成且无语法错误 | 代码审查 + 自动检查 | 技术负责人 |
| Phase 3 → 4 | 测试通过率 >= 标准 | 测试报告审核 | QA 工程师 |
| Phase 4 → 5 | 文档完整且经验总结完毕 | 文档审查 | PM |
| Phase 5 → End | 交付物完整且用户满意 | 验收签署 | 用户 |

### 5.2 门槛标准

**Phase 3 (测试) 的具体标准**:

- P0 用例通过率: **100%**
- P1 用例通过率: **>= 90%**
- P2 用例通过率: **>= 80%**
- 新增 P0/P1 bug 数: **0**
- 回归 bug 数: **0** (之前修复的问题不能复发)

**如果未达到标准**:

1. 返回 Phase 2 修复问题
2. 重新进入 Phase 3 测试
3. 重复直到通过 Quality Gate

**历史数据参考**：

| 版本类型 | P0 通过率 | P1 通过率 | 新增 P0 Bug | 是否达标 |
|----------|----------|----------|------------|---------|
| 失败案例（虚假测试） | N/A | N/A | 多个 | 否 |
| 过渡方案 | ~80% | ~70% | 2 个 | 否 |
| 最佳实践 | 100% | 100% | 0 个 | 是 |

## 6. 风险管理

### 6.1 常见风险及应对

| 风险类型 | 可能性 | 影响 | 应对措施 |
|----------|--------|------|----------|
| 需求变更 | 高 | 中 | Phase 0 充分沟通，锁定 scope |
| 技术难题 | 中 | 高 | Phase 1 技术预研，预留 buffer |
| 测试不充分 | 高 | 高 | 强制执行 GUI 测试方案 |
| 数据库迁移问题 | 中 | 高 | Phase 3 增加 data consistency test |
| 配置级联复杂 | 中 | 中 | 文档化配置链路，增加验证 |
| 过度承诺 | 高 | 高 | 每次 iteration 聚焦 1-3 个问题 |

### 6.2 应急预案

**如果发现重大问题（P0 bug）**:

1. 立即停止当前工作
2. 评估影响范围
3. 创建 hotfix iteration（简化流程）
4. 修复 → 冒烟测试 → 发布
5. 事后复盘根因

**如果用户临时加需求**:

1. 记录新需求到 backlog
2. 评估是否影响当前 iteration
3. 如果不影响：加入当前 iteration（需评估工作量）
4. 如果影响：放入下一个 iteration
5. 与用户沟通优先级

**紧急修复案例参考**：

典型的 hotfix 场景包括：
- 触发条件：某版本的虚假测试暴露后，用户失去信任
- 简化流程：跳过部分文档工作，聚焦 P0 问题
- 快速修复：集中精力解决 UI 渲染、版本号、目录结构等致命问题
- 后果：虽然解决了主要问题，但因为赶工可能导致后续还需要继续修复

**教训**：hotfix 可以简化流程，但不能省略测试。如果当时做了完整的 GUI 测试，可能就不需要额外的修复版本了。

## 8. 持续改进机制

### 8.1 定期回顾

- **频率**: 每 3-5 个 iteration 进行一次回顾会议
- **参与者**: 所有角色代表
- **议题**:
  - 哪些做得好？继续保持
  - 哪些需要改进？如何改进？
  - 流程是否有优化空间？
  - 工具是否需要升级？

**第一次回顾建议时机**: 完成一定数量的成功迭代后进行

**回顾议程模板**:

1. 数据展示（15 分钟）
   - 本周期的 iteration 数量和成功率
   - 平均 cycle time
   - Defect escape rate
   - Rework rate

2. 亮点分享（15 分钟）
   - 每个 iteration 选出一个"最佳实践"
   - 分享成功的经验和技巧

3. 问题讨论（30 分钟）
   - 列出遇到的问题和阻碍
   - 分类：流程问题 / 工具问题 / 沟通问题
   - 讨论解决方案

4. 改进计划（15 分钟）
   - 确定 2-3 个优先改进项
   - 指定负责人和时间表
   - 记录到 backlog

5. 总结（5 分钟）
   - 会议纪要
   - Action items
   - 下次会议时间

### 8.2 文档维护

**GUI 测试方案**: 每次迭代后根据新发现更新
- 新增测试场景
- 优化测试步骤
- 补充边界条件

**Iteration Plan (本文档)**: 每季度 review 一次，根据实际情况调整
- 更新成功/失败案例
- 调整质量门槛标准
- 优化流程细节

**模板库**: 积累常用的 code snippet, test case, document template
- spec.md 模板（不同类型的需求）
- tasks.md 模板（不同类型的任务）
- checklist.md 模板（不同类型的验收标准）
- test report 模板（不同类型的测试报告）

### 8.3 度量指标

建议跟踪以下指标来衡量迭代效率：

| 指标 | 定义 | 目标值 | 基准参考 |
|------|------|--------|---------|
| Cycle Time | 从需求到发布的总时长 | < 1 天 (小型迭代) | ~4 小时（符合） |
| Defect Escape Rate | 发布后发现的 bug 比例 | < 10% | 待观察 |
| Test Coverage | 测试用例覆盖率 | > 90% (P0/P1) | 100%（最佳实践） |
| Rework Rate | 返工率（需要重新做的 iteration）| < 20% | 0%（一次成功） |
| User Satisfaction | 用户满意度评分 | > 4.0/5.0 | 待收集反馈 |

**度量方法**:

1. **Cycle Time**: 从 Phase 0 开始到 Phase 5 结束的时间差
2. **Defect Escape Rate**: 发布后 7 天内发现的 P0/P1 bug 数 / 总 bug 数
3. **Test Coverage**: (P0 用例通过数 + P1 用例通过数) / (P0 总数 + P1 总数)
4. **Rework Rate**: 返工的 iteration 数 / 总 iteration 数
5. **User Satisfaction**: 用户主观评分（1-5 分）

**数据收集方式**:

- Cycle Time: 从 tasks.md 的时间戳推断
- Defect Escape Rate: 从用户反馈和 bug report 统计
- Test Coverage: 从 checklist.md 和 test report 统计
- Rework Rate: 从 iteration 历史统计
- User Satisfaction: 每次发布后发送简短的满意度调查

#### A.2 做对了什么

1. ✅ **Scope 聚焦**: 只关注模板模块，不做无关的事
   - 明确列出 3 个核心问题，不在本次 iteration 中引入新功能
   - 与过度承诺的"全面修复"形成鲜明对比

2. ✅ **Spec 驱动**: 先诊断再修复，有清晰的 tasks 和 checklist

   - **根因**: 过度自信，跳过了 GUI 测试环节
   - **解决**: 补充完整的 GUI 测试流程

### 9.1 快速参考卡片

**Iteration Checklist (一页纸版本)**:

```
□ Phase 0: 需求明确? Scope 可控? 优先级确定?
□ Phase 1: Spec 已批准? Tasks 已分解? Checklist 已定义?
□ Phase 2: 代码完成? 无语法错误? Tasks 已勾选?
□ Phase 3: 真实 GUI 测试? 无 P0/P1 bug? 测试报告完成?
□ Phase 4: 文档完整? 经验总结? 产物归档?
□ Phase 5: 交付物完整? 用户满意? 版本已标记?
```

**Phase 3 测试速查表**:

```
Smoke Test (10 min):
  □ 程序启动无崩溃
  □ 核心功能可访问
  □ 版本号正确显示

Function Test (30-60 min):
  □ 按照 checklist 逐项验证
  □ 正常路径 + 边界 + 异常
  □ 截图记录关键步骤

Regression Test (20-30 min):
  □ 旧 bug 未复现
  □ 相关功能正常
  □ 性能无明显退化

Data Consistency (10 min):
  □ DB 记录 = UI 显示
  □ 文件结构符合预期
  □ 配置文件正确更新
```

### 9.2 常见问题 FAQ

**Q1: 一个 iteration 应该做多大的范围？**

A: 建议 1-3 个核心问题，能在 0.5-1 天内完成。宁可拆成多个小 iteration，也不要做一个大而全的。

**依据**:
- 某版本尝试做"全面修复"（6+ 个问题），结果质量失控，需要后续两次返工
- 某成功版本只做 3 个问题，4 小时完成，一次成功

**判断标准**:
- 能否在一天内完成？如果不能，拆分
- 是否有强依赖关系？如果没有，拆成独立 iteration
- 风险是否可控？如果风险高，缩小范围

---

**Q2: 如果测试发现有新 bug 怎么办？**

A:

- **P0/P1**: 立即修复，重新测试
  - 不要进入 Phase 4，回到 Phase 2
  - 修复后再跑一遍 Phase 3
  - 直到所有 P0/P1 用例通过

- **P2/P3**: 记录到 backlog，下一个 iteration 处理（除非时间充裕）
  - 在 iteration_summary.md 中记录
  - 评估是否阻塞当前 AC
  - 如果不阻塞，可以先发布

**依据**:
- 某成功版本在测试中发现数据库脏数据（P0），立即修复后才算通过
- 如果当时选择忽略，会导致用户在使用中遇到同样问题

---

**Q3: 必须写这么多文档吗？**

A: 核心文档（spec, tasks, checklist）是必须的，它们能显著提高质量和效率。总结报告可以根据 iteration 大小决定是否详细。

**最小文档集**（不可省略）:
- spec.md: 明确目标和范围
- tasks.md: 分解任务和依赖
- checklist.md: 定义验收标准

**可选文档**（根据情况决定）:
- gui_test_report.md: 如果有 GUI 变更，强烈建议
- iteration_summary.md: 如果是重要的 iteration，建议写
- 其他文档：按需生成

**效率论证**:
- 某成功版本花了约 1 小时写 spec/tasks/checklist，但节省了至少 2 小时的返工时间
- 文档投入产出比约为 1:2 或更高

---

**Q4: 用户临时改变需求怎么办？**

A: 记录下来，评估影响。如果不影响当前 scope，可以加入；否则放入下一个 iteration。关键是沟通。

**决策流程**:

```
用户新需求
    ↓
记录到需求池
    ↓
评估影响范围
    ↓
┌─ 影响 < 20%工作量 ──→ 加入当前 iteration（需告知用户）
│
└─ 影响 >= 20%工作量 ──→ 放入下一个 iteration
                           ↓
                       与用户讨论优先级
```

**原则**:
- 不拒绝用户的合理需求
- 但要保护当前 iteration 的稳定性
- 用数据和事实说话（影响范围、工作量估算）

---

**Q5: 如何平衡速度和质量？**

A: 对于小型 iteration（bug 修复），质量优先于速度。因为返工的时间成本远高于多花 1-2 小时测试的成本。

**成本计算**:

| 方案 | 时间成本 | 质量风险 | 用户信任 |
|------|---------|---------|---------|
| 快速发布（少测试） | 4 小时 | 高 | 低 |
| 稳健发布（完整测试） | 6 小时 | 低 | 高 |
| 快速发布 + 返工 | 8+ 小时 | 中 | 很低 |

**结论**: 选择稳健发布，总成本最低，用户信任最高。

**例外情况**: 紧急 hotfix（如生产环境崩溃）可以简化流程，但仍需做冒烟测试。

| Root Cause | 根因 | 问题的根本原因（非表面症状） |
| Dirty Data | 脏数据 | 数据库中的过期或错误数据 |
| Config Cascade | 配置级联 | 多层配置文件之间的依赖关系 |
| Trae Agent | Trae 智能体 | Trae IDE 中的 AI 辅助开发角色 |
