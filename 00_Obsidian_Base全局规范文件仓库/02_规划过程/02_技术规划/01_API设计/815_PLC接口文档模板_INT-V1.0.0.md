## 20. IO映射表标准格式 (DEV-V1.1.0 新增)

### 20.1 三层映射模型

```
物理层(I/Q) ←→ 逻辑层(M/D) ←→ 接口层(FB参数)
   ↑                ↑               ↑
 传感器/执行器    主控程序         业务功能块
```

**说明**：
- **物理层(I/Q)**：PLC硬件的物理输入/输出地址（如I0.0、Q0.0）
- **逻辑层(M/D)**：主控程序中的中间变量（如M区内存变量、D区数据块）
- **接口层(FB参数)**：功能块的VAR_INPUT/VAR_OUTPUT参数

**设计原则**：
1. 功能块(FB)不应直接引用物理地址(I/Q/M/D)，应通过参数传递
2. 主控程序负责IO映射和信号分配
3. 实现业务逻辑与硬件解耦，提高代码可移植性和复用性

### 20.2 标准IO映射表模板

| 物理地址 | 逻辑变量名 | 数据类型 | 方向 | 所属功能块 | 备注 |
|---------|-----------|---------|------|----------|------|
| I0.0 | `i_b急停` | BOOL | PRG→FB | 全局 | 安全回路 |
| I0.1 | `i_b启动` | BOOL | PRG→FB | 全局 | 启动按钮 |
| Q0.0 | `o_b电机` | BOOL | FB→PRG | 执行器 | - |
| Q0.1 | `o_b指示灯` | BOOL | FB→PRG | HMI | 状态指示 |

**字段说明**：
- **物理地址**：PLC硬件的实际IO地址
- **逻辑变量名**：主控程序中定义的变量名（建议使用匈牙利命名法）
- **数据类型**：BOOL/INT/DINT/REAL等
- **方向**：
  - `PRG→FB`：从主控程序传入功能块（输入信号）
  - `FB→PRG`：从功能块输出到主控程序（输出信号）
  - `FB↔PRG`：双向传递（INOUT参数）
- **所属功能块**：该信号归属的功能块或模块
- **备注**：特殊说明（如安全相关、HMI显示等）

## 21. 纯逻辑FB接口声明示例 (DEV-V1.1.0 新增)

### 21.1 设计原则

**核心理念**：业务功能块(FB)应该是纯逻辑单元，与具体硬件解耦

**优势**：
- ✅ **可移植性**：FB可在不同项目中复用，无需修改内部代码
- ✅ **可测试性**：支持离线仿真，使用虚拟数据进行单元测试
- ✅ **可维护性**：硬件变更只需修改映射表，不影响业务逻辑
- ✅ **标准化**：统一接口规范，降低团队协作成本

## 22. Region标记在接口文档中的展示方式 (DEV-V1.1.0 新增)

### 22.1 Region标记的作用

**目的**：在功能块源码中使用Region标记进行变量分组，提高代码可读性和维护性

**命名规范**：
- 格式：`[序号]_[分类]_[功能描述]`
- 示例：`110_系统控制信号`、`140_传感器输入`
- 序号规则：
  - 100-199：VAR_INPUT（输入变量）
  - 200-299：VAR_OUTPUT（输出变量）
  - 300-399：VAR_INOUT（双向变量）
  - 400-499：VAR（内部变量）

### 22.3 Region标记的最佳实践

**✅ 推荐做法**：

1. **分层清晰**：每个Region只包含一类相关的变量
2. **命名规范**：使用统一的编号和命名规则
3. **注释完整**：每个变量都有清晰的注释说明来源和用途
4. **数量统计**：在文档中标注每组变量的总数，便于核对
5. **优先级标识**：对安全相关变量明确标注优先级

**❌ 避免做法**：

1. **混合放置**：将不同类型的变量放在同一个Region
2. **编号混乱**：Region编号不连续或跳跃过大
3. **注释缺失**：缺少必要的注释说明
4. **过度细分**：Region划分过细导致碎片化（建议每组5-15个变量）

### 22.4 文档与代码的同步检查清单

在发布接口文档前，请确认以下事项：

- [ ] 变量数量统计准确无误
- [ ] 数据类型、默认值与代码匹配
- [ ] 注释说明清晰完整
