## 3. 目的与适用范围

### 3.1 目的

本操作规程（SOP）旨在为 `00_Obsidian_Base全局规范文件仓库` 中所有规范文件的版本更新提供**标准化、可重复、可审计**的操作指南。通过明确的步骤、角色分工和异常处理机制，确保：

- 每次规范更新均遵循统一的操作流程
- 版本号递增、变更记录、归档管理等环节无遗漏
- 新旧版本不共存、引用链接不断裂、目录结构不混乱
- 所有操作可追溯、可回滚

### 3.2 适用范围

| 适用对象 | 说明 |
|----------|------|
| 操作对象 | 规范仓库内所有 `.md` 格式的规范文件（含模板、规程、检查清单等） |
| 操作人员 | 规范编写者、审核者、仓库管理员 |
| 操作场景 | 规范内容修订、版本迭代、紧急修正、归档清理 |

### 3.3 不适用场景

- 项目级文档（位于具体项目目录中的非规范文件）-- 此类文档遵循项目自身的版本管理规则
- Obsidian 笔记（个人知识库中的非规范化笔记）
- 自动化脚本或工具代码文件的版本管理

## 4. 角色与职责

### 4.1 角色定义矩阵

| 角色 | 主要职责 | 权限范围 | 对应人员示例 |
|------|----------|----------|-------------|
| **规范编写者** | 执行规范的编辑修改、版本号更新、变更记录填写 | 读写目标规范文件 | 技术文档工程师、领域专家 |
| **规范审核者** | 审查发布前检查清单、确认变更内容准确性 | 审核通过/退回 | 技术负责人、项目经理 |
| **仓库管理员** | 执行归档操作、维护目录结构、处理冲突文件、通知发布 | 全仓库读写权限 | 配置管理员、DevOps工程师 |

### 4.2 职责详细说明

#### 4.2.1 规范编写者

- 负责使用 **SearchReplace** 工具对现有规范进行原地编辑（禁止使用 Write 创建新文件）
- 负责正确递增版本号并填写变更记录
- 负责在提交前完成自检（参照 [规范发布检查清单_CHK-V1.0.0.md](../05_收尾过程/规范发布检查清单_CHK-V1.0.0.md) 的A类必查项）
- 负责将编辑完成的文件移交审核

#### 4.2.2 规范审核者

- 负责执行 [规范发布检查清单_CHK-V1.0.0.md](../05_收尾过程/规范发布检查清单_CHK-V1.0.0.md) 的全部A类必查项核查
- 有权批准发布或退回修改（附退回原因）
- 负责确认B类验证项在发布后执行

#### 4.2.3 仓库管理员

- 负责将旧版文件归档至 `_archive/YYYY-MM-DD_操作描述/` 目录
- 负责清理 `_conflict` 冲突文件
- 负责通知相关人员规范已更新
- 在异常情况下负责执行回滚操作

## 5. 标准操作流程

### 5.1 流程总览

```
阶段1: 准备 --> 阶段2: 编辑 --> 阶段3: 自检 --> 阶段4: 审核 --> 阶段5: 发布 --> 阶段6: 收尾
```

### 5.2 阶段1: 准备（Preparation）

**执行角色**: 规范编写者

**操作步骤**:

| 步骤 | 操作内容 | 输入 | 输出 | 通过标准 |
|------|----------|------|------|----------|
| 1.1 | 确认待更新规范的当前路径和版本号 | 规范文件路径 | 当前版本号确认 | 路径存在于规范仓库中，非 `_archive` 目录下 |
| 1.2 | 使用 Read 工具读取原文件完整内容 | 原文件绝对路径 | 完整文件内容 | 成功读取，无读取错误 |
| 1.3 | 确定本次变更类型和版本递增方案 | 变更需求描述 | 版本递增决策 | 遵循语义化版本规则（见 §5.2.1） |
| 1.4 | 确认无其他人员正在编辑同一文件 | 文件状态查询 | 并发安全确认 | 无锁定、无正在进行的编辑会话 |

#### 5.2.1 版本递增决策规则

| 变更类型 | 版本递增方式 | 示例 | 典型场景 |
|----------|-------------|------|----------|
| **重大结构性变更** | MAJOR+1, MINOR=0, PATCH=0 | V1.2.3 → V2.0.0 | 章节重组、删除核心章节、命名规则变更 |
| **功能新增/扩展** | MINOR+1, PATCH=0 | V1.2.3 → V1.3.0 | 新增章节、新增检查项、扩展适用范围 |
| **错误修复/微调** | PATCH+1 | V1.2.3 → V1.2.4 | 错别字修正、链接修复、格式调整 |

### 5.3 阶段2: 编辑（Editing）

**执行角色**: 规范编写者

**核心原则**: **严格使用 SearchReplace 原地编辑，禁止使用 Write 创建新文件**

**操作步骤**:

| 步骤 | 操作内容 | 工具/方法 | 关键约束 |
|------|----------|-----------|----------|
| 2.1 | 定位需要修改的内容段落 | Read 工具查看上下文 | 必须包含足够的上下文行以确保唯一匹配 |
| 2.2 | 使用 SearchReplace 执行修改 | SearchReplace 工具 | old_str 必须能唯一匹配目标段落 |
| 2.3 | 如有多处修改，重复 2.1-2.2 | 循环执行 | 每次只改一处，确保精准可控 |
| 2.4 | 更新「文档基础信息」中的版本号 | SearchReplace 工具 | 同步更新文件名、基础信息表两处版本号 |
| 2.5 | 在「版本变更记录」表首行追加新条目 | SearchReplace 工具 | 5列完整填写，变更描述控制在50字以内 |

#### 5.3.1 正确示例 vs 错误示例

**正确做法 -- SearchReplace 原地编辑**:

```markdown
# 操作: 将版本号从 V1.0.0 更新为 V1.0.1

# Step 1: 使用 SearchReplace 更新基础信息表中的版本号
old_str: | **文档版本** | V1.0.0 |
new_str: | **文档版本** | V1.0.1 |

# Step 2: 使用 SearchReplace 追加变更记录
old_str: | V1.0.0 | 初始版本 | 文档专家 | 2026-01-01 | 初始创建 |
new_str: | V1.0.1 | 修正错别字和格式问题 | 文档专家 | 2026-04-24 | 修正§3.2标题编号错误 + 统一表格对齐 |
        | V1.0.0 | 初始版本 | 文档专家 | 2026-01-01 | 初始创建 |

# Step 3: 重命名文件名 (由文件系统操作完成)
# 原文件名: XXX_V1.0.0.md -> 新文件名: XXX_V1.0.1.md
```

**错误做法 -- Write 新建文件（严禁！）**:

```markdown
# 以下操作被严格禁止！

# 错误: 使用 Write 工具创建新文件，导致新旧版本共存
Write(文件路径="XXX_V1.0.1.md", content=...)

# 后果:
# 1. 仓库中同时存在 XXX_V1.0.0.md 和 XXX_V1.0.1.md
# 2. 引用方可能指向旧版文件
# 3. Graph视图出现重复节点
# 4. Dataview查询返回重复结果
```

### 5.4 阶段3: 自检（Self-Check）

**执行角色**: 规范编写者

**依据文档**: [规范发布检查清单_CHK-V1.0.0.md](../05_收尾过程/规范发布检查清单_CHK-V1.0.0.md) A类必查项

**操作步骤**:

| 步骤 | 检查项 | 操作方法 | 不通过处理 |
|------|--------|----------|-----------|
| 3.1 | 旧版本号残留检查 | Grep 全仓库搜索旧版本号字符串 | 返回编辑阶段清除残留 |
| 3.2 | 链接有效性验证 | Grep 提取所有 markdown 链接，逐个验证目标文件存在 | 修复或移除失效链接 |
| 3.3 | Markdown语法验证 | 在 Obsidian 中预览渲染效果 | 修正语法错误 |
| 3.4 | 文件名一致性确认 | 确认文件名中的版本号与内部基础信息表一致 | 统一两处版本号 |
| 3.5 | 变更记录完整性确认 | 确认变更记录表包含本次更新条目且描述清晰 | 补充缺失条目 |

**自检通过标志**: A类全部27项检查点均已勾选通过。

### 5.5 阶段4: 审核（Review）

**执行角色**: 规范审核者

**操作步骤**:

| 步骤 | 操作内容 | 通过标准 | 不通过处理 |
|------|----------|----------|-----------|
| 4.1 | 执行完整的A类必查项审查 | 逐项核对 [规范发布检查清单_CHK-V1.0.0.md](../05_收尾过程/规范发布检查清单_CHK-V1.0.0.md) | 任一项不通过即整体退回 |
| 4.2 | 内容准确性评审 | 确认变更内容与需求一致、技术表述准确 | 附具体退回意见后退回编写者 |
| 4.3 | 影响范围评估 | 评估本规范变更对关联规范的影响 | 如有影响需同步更新关联规范 |
| 4.4 | 签署审核结论 | 明确标注「通过」或「退回（附原因）」 | 记录审核人和审核时间 |

**审核输出**:
- **通过**: 进入阶段5发布
- **退回**: 返回阶段2编辑，附退回原因清单

### 5.6 阶段5: 发布（Release）

**执行角色**: 仓库管理员（协同规范编写者）

**操作步骤**:

| 步骤 | 操作内容 | 详细说明 |
|------|----------|----------|
| 5.1 | 确认审核通过 | 核实审核者签署的「通过」结论 |
| 5.2 | 执行B类验证项 | 按 [规范发布检查清单_CHK-V1.0.0.md](../05_收尾过程/规范发布检查清单_CHK-V1.0.0.md) §5 执行5项发布后验证 |
| 5.3 | 归档旧版文件 | 将上一版文件移动至 `_archive/YYYY-MM-DD_简述操作内容/` 目录 |
| 5.4 | 清理冲突文件 | 扫描并删除同路径下的 `_conflict` 后缀文件 |
| 5.5 | 发布通知 | 通知相关干系人规范已更新（含版本号、变更摘要、文件路径） |

#### 5.6.1 归档目录命名规范

```
_archive/
  └── YYYY-MM-DD_操作描述/
      ├── 原文件名_归档时间戳.md
      └── ...
```

**示例**:
```
_archive/
  └── 2026-04-24_更新PLC变量命名规范至V1.0.4/
      ├── 801_PLC变量命名与功能块命名规范_DEV-V1.0.3.md
      └── ...
```

### 5.7 阶段6: 收尾（Closure）

**执行角色**: 仓库管理员

**操作步骤**:

| 步骤 | 操作内容 | 输出物 |
|------|----------|--------|
| 6.1 | 更新版本变更台帐 | 在 [041_通用版本变更台帐模板_CHG-V2.1.0.md](04_变更记录/041_通用版本变更台帐模板_CHG-V2.1.0.md) 中记录本次变更 |
| 6.2 | 确认Graph视图正常 | 在Obsidian Graph视图中确认节点关系正确 |
| 6.3 | 关闭变更单（如适用） | 在 [040_通用变更单模板_CHG-V2.0.0.md](01_变更单/040_通用变更单模板_CHG-V2.0.0.md) 中关闭关联变更单 |
| 6.4 | 操作完成确认 | 向规范编写者和审核者发送完成确认 |

## 6. 工具链说明

## 7. 异常处理

### 7.1 异常分类与处理预案

| 异常类型 | 触发条件 | 处理措施 | 责任角色 | 恢复时间目标 |
|----------|----------|----------|----------|-------------|
| **并发编辑冲突** | 编辑过程中检测到 `_conflict` 文件 | 见 §7.2 详细流程 | 编写者+管理员 | 30分钟内 |
| **审核退回** | 审核者在阶段4判定不通过 | 返回阶段2编辑，按退回意见修改后重新提审 | 编写者 | 视退回原因复杂度 |
| **发布验证失败** | 阶段5 B类验证项未通过 | 定位失败原因，修复后重新验证 | 编写者+管理员 | 1小时内 |
| **回滚需求** | 发布后发现严重错误需回退到上一版 | 见 §7.3 回滚流程 | 管理员 | 15分钟内 |
| **引用方未同步** | 本规范更新后，引用本规范的其他规范未同步更新 | 识别所有引用方，逐一通知更新 | 管理员 | 1个工作日内 |

### 7.2 并发编辑冲突处理流程

```
检测到冲突
    │
    ▼
┌─ 停止当前编辑 ─────────────────────────┐
│  立即保存已完成的工作，避免覆盖冲突文件   │
└─────────────────────────────────────────┘
    │
    ▼
┌─ 分析冲突文件 ─────────────────────────┐
│  1. 打开 xxx_conflict_YYYYMMDDHHmmss.md │
│  2. 对比冲突文件与当前文件的差异         │
│  3. 确定保留哪些变更                     │
└─────────────────────────────────────────┘
    │
    ▼
┌─ 合并变更 ─────────────────────────────┐
│  1. 手动将需要的变更合并到主文件          │
│  2. 使用 SearchReplace 逐一应用合并内容   │
│  3. 确认合并后的内容完整无误             │
└─────────────────────────────────────────┘
    │
    ▼
┌─ 清理冲突文件 ─────────────────────────┐
│  1. 删除 _conflict 后缀文件              │
│  2. 记录冲突事件到操作日志               │
└─────────────────────────────────────────┘
    │
    ▼
  继续正常流程（阶段3自检）
```

### 7.3 回滚流程

**触发条件**: 发布后发现严重错误（如关键信息遗漏、重大逻辑错误），必须回退到上一版本。

**操作步骤**:

| 步骤 | 操作 | 执行角色 | 详细说明 |
|------|------|----------|----------|
| R-1 | 暂停使用当前版本 | 管理员 | 通知所有用户暂停参考该规范 |
| R-2 | 从 _archive 取出上一版 | 管理员 | 从归档目录恢复上一版文件到原始位置 |
| R-3 | 恢复上一版文件名 | 管理员 | 将文件名恢复为上一版的名称和版本号 |
| R-4 | 将错误版移入归档 | 管理员 | 将刚发布的错误版本移入 `_archive/YYYY-MM-DD_回滚操作/` |
| R-5 | 发送回滚通知 | 管理员 | 通知所有干系人回滚事实和原因 |
| R-6 | 记录回滚事件 | 管理员 | 在版本变更台帐中记录回滚操作及原因 |
| R-7 | 启动根因分析 | 审核者+编写者 | 分析导致错误发布的原因，制定预防措施 |

**回滚后要求**: 回滚完成后必须进行根因分析，并在后续更新中避免同类问题复发。

## 8. 操作记录模板

每次规范更新操作应留存以下记录（可用于版本变更台帐）：

| 字段 | 填写说明 | 示例 |
|------|----------|------|
| 操作日期 | YYYY-MM-DD | 2026-04-24 |
