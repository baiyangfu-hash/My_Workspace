## 0. 先给结论

auto-pm 当前已经不适合继续被定义成“统一 CLI 管理 PLC/Python 多技术栈项目的脚手架工具”。从实际代码、文档和 dogfooding 记录看，它已经进入更高一级的产品形态：

> 面向电气自动化工程师的项目标准化、PLC 工程资产管理、文档自动化、变更闭环和交付门禁工具。

下一阶段最重要的事情不是继续堆功能，而是让它完整托管一个真实自动化设备项目。建议将下一条主线定义为：

> **V0.4.0：真实自动化项目落地版。**

V0.4.0 的目标不是“做更多页面”，而是回答一个朴素问题：

> 一个电气自动化工程师能不能用 auto-pm 从立项、PLC 架构、IO 表、程序文档、变更、调试记录到交付检查，完整管理一个真实设备项目？

## 1. 当前判断

### 1.1 当前优势

项目已经具备几个非常有价值的底座：

| 能力 | 当前状态 | 价值 |
|------|----------|------|
| CLI + GUI 双入口 | 已具备 | 适合工程师快速操作，也适合 GUI 日常管理 |
| PLC 标准项目模板 | 已具备 | 能把项目目录、文档、PLC 示例统一起来 |
| 变更管理闭环 | 已具备 | 已覆盖 create/list/show/edit/transition + 台帐 + dogfooding |
| 发布门禁 | 已初步具备 | ruff/mypy/pytest/dogfood 形成工程质量约束 |
| PM_SESSION 项目记忆 | 已形成习惯 | 能防止多模型、多轮迭代后失忆和漂移 |
| 技术债治理 | 已形成机制 | 当前已偿还大部分技术债，具备继续演进基础 |

### 1.2 当前风险

| 风险 | 说明 | 建议 |
|------|------|------|
| 产品定位偏窄 | 仍偏“脚手架工具”表述，低估了项目管理和交付管理能力 | V0.4.0 起调整为“自动化项目作业系统” |
| 功能多但工作台价值不足 | 项目列表、变更中心、规范中心都有，但第一屏还不够像工程师工作台 | 优先做项目驾驶舱 |
| PLC 工程对象建模不足 | 当前更多管理文件和目录，尚未充分建模设备、站点、IO、程序块、报警、通讯 | 建议引入 PLC 工程资产模型 |
| 文档模板仍偏静态 | 模板能生成，但还没有充分利用项目元数据自动填充 | 做“半自动文档生成” |
| dogfood 仍集中在 auto-pm 自身 | 已有 5 次闭环，但真实设备项目落地证据还不够 | V0.4.0 必须选一个真实 PLC 项目试运行 |

## 2. V0.4.0 推荐定位

### 2.1 产品定位

建议将 V0.4.0 的一句话定位改为：

> auto-pm 是面向电气自动化工程师的本地项目作业系统，用于统一管理 PLC 项目结构、工程文档、变更闭环、调试记录、质量门禁和交付证据。

### 2.2 不建议做的事情

V0.4.0 不建议优先做：

- 在线协作
- 云端同步
- 甘特图
- 复杂权限系统
- PLC 代码自动生成
- 大而全的项目管理平台
- 为了 UI 好看而重做大页面

这些都容易把项目拖向泛化工具。对当前用户来说，真正刚需是减少重复劳动、避免项目失控、让交付资料可信。

### 2.3 建议做的事情

V0.4.0 建议围绕 5 个核心场景展开：

1. 项目驾驶舱
2. 标准设备项目模板
3. PLC 工程资产台帐
4. 文档半自动生成
5. 真实项目试运行闭环

## 3. 建议一：项目驾驶舱作为 GUI 第一入口

### 3.1 背景

当前 GUI 已经有项目列表、变更中心、规范中心、模板管理等模块，但从电气工程师日常工作角度看，第一屏应该回答：

- 哪些项目正在设计？
- 哪些项目正在调试？
- 哪些项目快交付？
- 哪些项目有未关闭变更？
- 哪些项目缺关键文档？
- 哪些项目 PLC 结构检查失败？
- 哪些项目最近被修改过？

### 3.2 建议功能

新增或强化“项目驾驶舱”页面，包含：

| 模块 | 内容 |
|------|------|
| 项目状态总览 | developing / commissioning / production / archived 数量 |
| 交付风险列表 | 缺文档、检查失败、未关闭变更、门禁未过 |
| 最近活动 | 最近变更单、最近扫描、最近文档修改 |
| 我的待办 | 待审批、待实施、待验收、待关闭 |
| 项目健康度 | 文档完整度、PLC 检查结果、变更闭环状态 |

### 3.3 GLM5.2 执行建议

建议执行顺序：

1. 先补 `ReportService` 或新增 `DashboardService`，只做数据聚合，不先碰 UI。
2. 数据源优先复用现有 `ProjectService`、`ChangeService`、`PlcChecker`、SQLite 缓存。
3. 输出一个 DTO，例如 `DashboardSummaryDTO`。
4. 增加单元测试验证统计口径。
5. 最后把 GUI 首页从单纯项目列表升级为“驾驶舱 + 项目列表”。

done_when：

- GUI 第一屏能看到项目总数、阶段分布、未关闭变更数、检查失败项目数。
- 不进入具体项目，也能判断今天最该处理什么。

## 4. 建议二：从“技术栈模板”升级为“项目类型模板”

### 4.1 背景

当前模板按 `plc/python` 技术栈区分，这是开发视角。真实自动化项目更常按业务形态区分：

- 单机设备
- 整线项目
- 改造项目
- 维保项目
- 标准库 / 功能块
- 测试台 / 仿真项目

这些项目所需目录、文档、PLC 程序结构、验收清单并不相同。

### 4.2 建议新增字段

在项目元数据中新增或标准化：

| 字段 | 示例 | 说明 |
|------|------|------|
| `project_type` | `single_machine` | 项目类型 |
| `equipment_type` | `conveyor` | 设备类型 |
| `customer` | `内部/客户名` | 客户或使用方 |
| `plc_vendor` | `Siemens` / `Mitsubishi` | PLC 品牌 |
| `plc_model` | `S7-1200` | CPU 型号 |
| `hmi_vendor` | `Weinview` / `Siemens` | HMI 品牌 |
| `io_count` | `128` | IO 点数，可后续自动统计 |

### 4.3 建议模板类型

| 模板 | 用途 |
|------|------|
| `plc-single-machine` | 单机设备项目 |
| `plc-line-project` | 整线项目 |
| `plc-retrofit-project` | 改造项目 |
| `plc-maintenance-project` | 维保项目 |
| `plc-shared-library` | 标准库 |
| `plc-test-suite` | 测试套件 |

### 4.4 GLM5.2 执行建议

不要一次性新增所有模板。建议先做一个最贴近日常工作的模板：

> `plc-single-machine`

done_when：

- `auto-pm project create --stack plc --project-type single_machine ...` 可生成单机设备项目。
- `.copier-answers.yml` 中保留 `project_type/equipment_type/plc_vendor/plc_model`。
- `project show` 能展示项目类型和 PLC 基础信息。
- GUI 新建项目对话框能选择项目类型。

## 5. 建议三：把 PLC 工程资产变成一等对象

### 5.1 背景

当前 PLC 管理主要集中在项目结构检查、文档命名、规范漂移检测。下一阶段建议管理“工程对象”，而不仅是文件。

### 5.2 推荐最小资产模型

建议先从 6 类对象开始：

| 对象 | 字段示例 | 价值 |
|------|----------|------|
| PLC 站点 | station_id, name, cpu_model, ip | 多 PLC 项目基础 |
| IO 模块 | module_name, address_range, type | IO 表和电气设计联动 |
| IO 点 | tag, address, signal_type, device, remark | 自动生成 IO 分配表 |
| 程序块 | block_type, block_name, purpose, owner | 程序架构文档 |
| 报警项 | alarm_code, trigger, reset, level | 报警清单 |
| 通讯接口 | protocol, peer, address, data_area | 接口文档 |

### 5.3 存储建议

V0.4.0 不建议直接做复杂数据库建模。建议先采用项目内结构化文件：

```text
02_PLC程序/
  工程资产/
    plc_stations.yml
    io_points.csv
    program_blocks.yml
    alarms.csv
    communications.yml
```

这样便于人工编辑，也便于后续 GUI 和文档生成读取。

### 5.4 GLM5.2 执行建议

先做“读取 + 校验 + 展示”，不要急着做复杂编辑器。

done_when：

- 新模板包含 `工程资产` 目录和示例文件。
- 新增 `auto-pm plc assets show <PROJECT_ID>` 或同等能力。
- 新增 `auto-pm plc assets check <PROJECT_ID>`，能检查必填列、重复地址、空 tag。
- 文档生成时能读取这些资产文件。

## 6. 建议四：文档模板从静态模板升级为半自动生成

### 6.1 背景

当前已有 PRD、DSN、INT、TEC、PLC 程序文档、IO 表等模板。下一步的价值不在“再多几个模板”，而在让模板自动吸收项目数据。

### 6.2 推荐自动填充内容

| 文档 | 自动填充内容 |
|------|--------------|
| PRD | 项目编号、项目名称、客户、设备类型、目标、范围 |
| DSN | PLC 架构、程序块列表、工艺流程、关键联锁 |
| INT | 通讯接口、IO 点表、HMI 变量、第三方设备 |
| TEC | PLC 选型、系统架构、风险、测试策略 |
| IO 表 | 从 `io_points.csv` 生成 |
| 程序架构文档 | 从 `program_blocks.yml` 生成 |
| 调试记录 | 从变更单和检查结果汇总 |

### 6.3 GLM5.2 执行建议

建议新增一个“文档刷新”能力：

```powershell
auto-pm doc refresh <PROJECT_ID>
auto-pm doc refresh <PROJECT_ID> --dry-run
```

原则：

- 不覆盖人工填写区。
- 自动生成区用清晰标记包围。
- 支持 dry-run 预览。
- 每次刷新应记录到变更或日志中。

建议自动生成区标记：

```markdown
<!-- AUTO_PM:BEGIN io-summary -->
自动生成内容
<!-- AUTO_PM:END io-summary -->
```

done_when：

- 修改 `io_points.csv` 后执行 `doc refresh`，IO 分配表或接口文档对应区域自动更新。
- 人工填写区不被覆盖。
- 有单元测试覆盖“只替换自动生成区”。

## 7. 建议五：把变更管理扩展为交付门禁的一部分

### 7.1 背景

当前变更管理已经很强，但还可以更贴近自动化现场：

- PLC 改了，HMI 是否同步？
- IO 地址改了，电气图纸是否同步？
- 报警逻辑改了，说明书是否同步？
- 程序块改了，测试项是否补充？

### 7.2 建议新增影响矩阵

在变更单中标准化影响范围：

| 影响域 | 是否影响 | 必填说明 |
|--------|----------|----------|
| PLC 程序 | 是/否 | 程序块、变量、逻辑说明 |
| HMI 画面 | 是/否 | 画面、按钮、报警、权限 |
| IO / 电气图纸 | 是/否 | 地址、端子、图纸页码 |
| 通讯接口 | 是/否 | 协议、地址、数据区 |
| 机械动作 | 是/否 | 机构、节拍、安全 |
| 文档 | 是/否 | 需更新的文档 |
| 调试验证 | 是/否 | 需补充的测试项 |

### 7.3 建议关闭门禁

变更单从 `completed` 到 `closed` 前建议检查：

- 影响域已填写
- 验证结论已填写
- 若影响文档，相关文档已刷新或人工确认
- 若影响 PLC/HMI/IO，至少有测试记录
- 台帐状态已同步

done_when：

- `change transition --to closed` 能给出明确门禁失败原因。
- 门禁失败不是直接崩溃，而是提示缺什么。

## 8. 建议六：真实项目试运行

### 8.1 背景

当前 dogfooding 多数围绕 auto-pm 自身，这是必要的，但不足以证明工具适合电气自动化项目。V0.4.0 必须选一个真实或准真实 PLC 项目试运行。

### 8.2 推荐试运行项目

建议选择一个规模适中的单机设备项目，满足：

- 有 PLC 程序
- 有 IO 表
- 有 HMI 或通讯接口
- 有至少 1 次需求变更
- 有调试或交付文档
- 项目规模不要太大，适合快速闭环

### 8.3 试运行最小闭环

| 步骤 | 产物 |
|------|------|
| 新建项目 | 标准项目目录 + 元数据 |
| 录入 PLC 资产 | IO 点表、程序块、通讯接口 |
| 生成文档 | PRD/DSN/INT/TEC 自动区填充 |
| 创建变更单 | 至少 1 张真实变更 |
| 执行检查 | PLC 结构检查 + 文档完整度检查 |
| 完成交付门禁 | 形成试运行报告 |

done_when：

- `09_整改项` 中新增一份真实项目试运行报告。
- 报告中明确列出哪些功能省时间，哪些功能增加负担。
- 基于试运行结果决定 V0.4.1，而不是凭想象继续开发。

## 10. 质量门禁建议

V0.4.0 继续沿用当前发布门禁，但建议增加产品级门禁：

| 门禁 | 内容 |
|------|------|
| G1 | `ruff check .` 0 errors |
| G2 | `mypy auto_pm` 0 errors |
| G3 | `pytest --no-cov` 全绿 |
| G4 | 本轮 CHG 完整闭环 |
| G5 | `PM_SESSION`、`CHANGELOG`、`005_变更记录_CHG.md` 已回写 |
| G6 | 至少一个真实/准真实 PLC 项目试运行通过 |
| G7 | 新功能必须有“对工程师节省了什么劳动”的说明 |

G7 很重要。auto-pm 不是为了展示功能数量，而是为了减少工程师在项目资料、变更追踪、交付检查上的重复劳动。

## 12. 最终建议

Codex/GPT 的判断是：

> auto-pm 下一阶段的价值不在“更像通用项目管理软件”，而在“更懂电气自动化项目”。

所以请把 V0.4.0 的成功标准定义为：

1. 能托管一个真实单机设备 PLC 项目。
2. 能把 IO、程序块、通讯、报警、文档和变更联系起来。
3. 能在交付前告诉工程师还缺什么。
4. 能减少手工整理文档和追溯变更的时间。
5. 能留下可信的项目证据链。

如果这 5 条成立，auto-pm 就已经不是脚手架，而是你自己的自动化项目方法论平台。
