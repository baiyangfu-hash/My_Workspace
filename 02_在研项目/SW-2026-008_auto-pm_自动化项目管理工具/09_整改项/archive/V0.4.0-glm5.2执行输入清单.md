## 5. 推荐执行顺序

严格按下面顺序执行，不要跳步。

### Step 1：GUI 先接 `OverviewTab`

推荐方案：

- 不先把 `asset_summary` 塞进 `DashboardService`
- 先在单项目视角的 `OverviewTab` 增加“工程资产摘要”区块

原因：

- `OverviewTab` 天然承载单项目详情，和 `asset_summary` 语义一致
- 首页驾驶舱应保持聚合层轻量，不应过早承载细粒度工程资产展示
- 这样更容易补 UI 测试，回归范围更可控

done_when：

- 选中 PLC 项目后，概览页能看到工程资产健康状态、三类资产数量、前 3 条问题摘要
- 至少补 1 组 `OverviewTab` 或等价 DTO/UI 测试

### Step 2：补历史项目兼容

推荐方案：

- 为 PLC 历史项目提供一个最小 retrofit 能力
- 目标不是“重写所有文档”，而是对目标文档注入缺失的 `AUTO_PM:BEGIN/END` 标记

可选形态二选一：

- 方案 A：`auto-pm doc retrofit-markers <project_id>`
- 方案 B：`auto-pm doc refresh <project_id> --inject-markers`

建议优先：

- 方案 A，更清晰，也更容易测试

done_when：

- 针对缺少自动区标记的旧 PLC 项目，工具能在目标文档中补入标记
- 再执行 `doc refresh` 时，不再只是报 issue，而能真正刷新

### Step 3：补 Python 项目“不适用”口径

目标：

- 驾驶舱中的 PLC 检查失败项，只反映 PLC 项目
- Python 项目不要再被暗示成“检查失败”

done_when：

- `DashboardService` 或等价聚合层明确区分“PLC 检查失败”和“非 PLC 不适用”
- 至少补 1 组服务层测试，防止口径回退
