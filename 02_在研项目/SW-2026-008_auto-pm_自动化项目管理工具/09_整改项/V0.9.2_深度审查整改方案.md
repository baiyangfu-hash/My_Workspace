## 一、Bug 修复（4 项）

### B1 [CRITICAL] `scan_single_project` 方法不存在 → 运行时 AttributeError

**涉及文件：**
- `auto_pm/ui/qml/bridges/workbench_bridge.py` L150 — `detectProject` 方法
- `auto_pm/application/workbench_facade.py` L470 — `import_project` 方法

**根因：** `ProjectScanner` 只有 `try_identify_project(project_path)` 方法，没有 `scan_single_project`。

**影响：** GUI 项目导入和 `detectProject` 在运行时必然崩溃。

**修复方案：**
1. `workbench_bridge.py:150` — `scanner.scan_single_project(path)` → `scanner.try_identify_project(path)`
2. `workbench_facade.py:470` — `scanner.scan_single_project(dest_path)` → `scanner.try_identify_project(dest_path)`

**验证：** `python -m pytest tests/qml/test_workbench_bridge.py -v` + `mypy auto_pm/` 确认无新增错误

---

### B2 [MEDIUM] QML 新建变更单对话框 nature 值与后端校验不匹配

**涉及文件：** `auto_pm/ui/qml/dialogs/NewChangeDialog.qml` L118-122

**根因：** QML ComboBox 的 nature 映射为 `["REQ", "DSN", "IMP", "TEST", "OPT", "DEF"]`，但后端 `change/constants.py` 的 `BUSINESS_NATURES` 只接受 `REQ/DEF/OPT/CFG/EMRG`。`"DSN"`, `"IMP"`, `"TEST"` 会触发 `validate_business_nature()` 抛出 `SpecViolationError`。

**影响：** 用户在 GUI 中选择"DSN (设计)"、"IMP (实施)"、"TEST (测试)"后提交，后端校验必然失败。

**修复方案：**
将 QML ComboBox 的 model 和映射对齐后端 `BUSINESS_NATURES`：

```qml
model: ["REQ (需求变更)", "DEF (缺陷修复)", "OPT (优化改进)", "CFG (配置调整)", "EMRG (紧急变更)"]
onActivated: {
    var map = ["REQ", "DEF", "OPT", "CFG", "EMRG"]
    root.nature = map[currentIndex]
}
```

**验证：** 检查 `change/constants.py` 中 `BUSINESS_NATURES` 的 key 集合与 QML 映射一致

### B3 [MEDIUM] `workbench_bridge.py` 访问 Facade 私有属性

**涉及文件：**
- `auto_pm/ui/qml/bridges/workbench_bridge.py` L146 — `detectProject` 中 `self._facade._project_service`
- `auto_pm/application/workbench_facade.py` — 新增 `detect_project` 公共方法

**根因：** Bridge 层直接访问 Facade 的私有属性 `_project_service`，违反封装原则。Facade 内部重构会导致此代码静默失效。

**修复方案：**
1. 在 `WorkbenchFacade` 中新增 `detect_project(path: str)` 公共方法，封装 `ProjectScanner` 调用
2. 修改 `workbench_bridge.py` 的 `detectProject` 方法，通过 Facade 调用，移除私有属性访问

**验证：** `python -m pytest tests/qml/test_workbench_bridge.py -v` 确认通过

### B4 [CRITICAL] 变更单数据库主键限制导致多项目同名变更覆盖冲突，且 Bridge/QML 接口缺少 project_id 导致数据展示“串台”

**涉及文件：**
- **模型层**：`auto_pm/models/change.py` L118, L146 (`ImpactAnalysis`, `ApprovalRecord`)
- **数据访问与迁移层**：`auto_pm/db/schema.py` L47, L74, L90, L151 / `auto_pm/db/repository.py` L189, L254, L313, L345, L366, L402, L463, L493
- **解析器与核心 Service**：`auto_pm/change/parser.py` L125 / `auto_pm/change/change_service.py` L430, L603, L616
- **Facade 接口层**：`auto_pm/application/change_facade.py` L137, L161
- **Bridge 桥接层**：`auto_pm/ui/qml/bridges/change_bridge.py` L20, L52, L110, L144, L160
- **QML 前端**：`auto_pm/ui/qml/views/ChangeCenterView.qml` / `auto_pm/ui/qml/components/LedgerTableView.qml` / `auto_pm/ui/qml/components/ChangeDetailPanel.qml`

**根因：**
1. SQLite 缓存中 `change_requests` 和 `impact_analysis` 表仅将 `change_number` 设为 PRIMARY KEY，导致多项目下重名的变更单在写入时发生冲突覆盖（例如 `SW-2026-008` 与 `DJ-2026-005` 均有名为 `CHG-DOCU-2026-001` 的变更单，后者会被覆盖丢失）。
2. QML 和 Bridge 层在调用详情查询 `getChangeRequest(change_number)` 和状态流转 `transitionChange` 时未传递 `project_id`。后端由于不知道所属项目，在全工作空间递归扫描时，总是返回字母排序靠前的项目文件，导致界面展示的数据错乱“串台”。

**修复方案：**
1. **模型层升级**：在 `ImpactAnalysis` 和 `ApprovalRecord` 类中新增 `project_id` 属性。
2. **主键/外键重构**：将 SQLite 的 `change_requests` 和 `impact_analysis` 表主键修改为联合主键 `(project_id, change_number)`；将 `approval_history` 和 `impact_analysis` 对 `change_requests` 的外键修改为联合外键；在 `migrate_schema` 中检查并自动删除旧表结构并触发重建以支持平滑过渡。
3. **仓储与服务层向下传参**：更新 repository 的增删查改逻辑及 `ChangeService`/`ChangeFacade`，确保获取详情、时间线、影响分析、状态流转等操作均通过联合键 `(project_id, change_number)` 进行。
4. **QML Bridge 缓存与接口升级**：桥接层 `_change_detail_cache` 的 key 升级为 `f"{project_id}:{change_number}"`；更新 `@Slot` 接口以支持 `project_id` 作为第二个可选参数；`transitionChange` 增加读取 `project_id` 参数。
5. **QML 前端参数打通**：
   - 列表 `ListView` 委托点击、台账 `LedgerTableView` 行点击时同时传出 `change_number` 和 `project_id`。
   - 详情面板 `ChangeDetailPanel` 调用 `getChangeTimeline` 时传入 `project_id`，且在状态流转时将 `project_id` 封装在 cmd 字典中传给后端。

**验证：**
- 全量运行 `python -m pytest`，确保各级单元测试通过；
- 运行 GUI，验证在 Change Center 分割视图中点击 `SW-2026-008` 项目的 `CHG-DOCU-2026-001` 时，右侧详情面板不会错显为 `DJ-2026-005` 项目的信息；
- 确认后台数据库 `change_requests` 表包含两个项目的 `CHG-DOCU-2026-001` 共存记录。
