# 旧项目补完与新项目连续性完整方案

## Summary

目标分两段推进，顺序固定：

1. 先把两个旧项目的“持续协作闭环”补完，做到：
   - 会话开始自动恢复上下文
   - 会话结束自动生成交接草稿
   - 人工确认后可半自动写回 `PM_SESSION`
   - 技能、hooks、项目状态文件三者规则一致
2. 在旧项目闭环稳定后，再补“新项目初始化能力”，做到：
   - 新建软件项目或 PLC 项目时，可一次性初始化 `PM_SESSION`、`.github/hooks/`、handoff 目录和模板
   - 以后新项目默认继承这套连续协作机制，而不是靠手工复制旧项目配置

本方案以“低风险、可回退、优先补完旧项目”为原则，不直接改动业务源码逻辑，先补项目治理层和协作层能力。

## Assumptions & Decisions

### 已锁定决策

- 先补完两个旧项目，再做新项目初始化能力
- 旧项目采用“半自动写回”，即：
  - 自动生成 draft
  - 明确执行 `apply-handoff.ps1`
  - 不在 `sessionEnd` 中无确认直接改写 `PM_SESSION`
- 软件项目与 PLC 项目继续使用两套不同模板
- `PM_SESSION_<项目编号>.md` 继续作为唯一项目状态真源
- hooks 自动化只负责“恢复、提醒、起草、半自动写回”，不直接替代验证结论

### 关键假设

- 工作区后续还会持续新增同类软件项目和 PLC 项目
- 旧项目的脚本逻辑可以安全沉淀为模板
- 项目级 hooks 仍然是可接受的落地方式
- 对 PLC 项目，人工审核与现场验证始终保留在流程中，不会被自动化绕过

## Risks

### 风险 1：`apply-handoff.ps1` 写回错误导致 `PM_SESSION` 污染

影响：

- 会破坏项目单一真源

缓解：

- 写回前强制备份
- 章节完整性校验
- 标记重复检测
- 先在两个旧项目验证，再复制到模板

### 风险 2：软件与 PLC 两套模板后续漂移

影响：

- 新项目初始化质量不一致

缓解：

- 模板统一放在 `c:\Users\fubai\Desktop\My_Workspace\.trae\project-bootstrap\`
- 以模板为源头，旧项目脚本只做回归验证参考

### 风险 3：hooks 提示过多，用户忽略提醒

影响：

- 自动化存在但不被执行

缓解：

- 提示只保留关键动作
- 统一话术：恢复上下文、生成 draft、执行 apply
- 在 README 中给出最短路径说明

### 风险 4：PLC 项目被误解为“已自动验证通过”

影响：

- 可能引入工程安全风险

缓解：

- PLC hooks 与技能文档中持续强调：
  - 文档一致性不等于可上机
  - 编译、现场、安全相关复核必须人工确认
