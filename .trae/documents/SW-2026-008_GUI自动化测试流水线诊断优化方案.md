# SW-2026-008 GUI 自动化测试流水线诊断与优化方案

> 诊断日期: 2026-07-03
> 基线代码: V0.5.4 (pyproject.toml)
> 触发背景: 自动化运行 → 截图 → 多模态 AI 分析 → 回传修改循环无法产生可用的 GUI

---

## 0. 执行摘要

**诊断结论**：流水线的核心问题不在 pm-workflow 技能，也不在 fullstack-engineer 技能本身，而在于 **两者之间的"分析→回传"环节存在三个结构性断层**：

| 断层 | 现象 | 影响 |
|------|------|------|
| **断层1**：截图分析结果无法结构化回传 | 多模态 AI 产出的自然语言分析无法被代码改动流程自动消费 | 每次都需要人工翻译"文字描述→代码改动"，效率低、易出错 |
| **断层2**：测试通过 ≠ 用户可用 | 程序化检查（out_of_bounds/zero_size）覆盖的是维度而非功能正确性；三视口截图在隔离 tmp 工作空间产生，与真实工作空间结构不同 | 0 bug 报告背后隐藏真问题 |
| **断层3**：迭代节奏缺乏门禁** | 6 天内 16 次 dogfooding 闭环（V0.5.0→V0.5.4），但每次只修 2-4 个问题；GUI 稳定性未收敛 | 电气部门反馈"目前只是一个看板，无法正常工作使用" |

**核心建议**：不需要重写技能，而是需要 **强化流水线中间件**——让截图、AI 分析和代码改动之间形成可机读的结构化数据流。

## 2. 三个断层详解

### 2.1 断层1：截图分析→代码改动链断裂

**问题链路**：

```
gui_plc_full_test.py  →  85张截图  →  多模态AI分析  →  自然语言报告  →  [人工翻译]  →  代码改动
        ✅                    ✅             ⚠️ 外部              ❌ 非结构化         ❌ 断层         ✅
```

**根因**：多模态 AI 的输出是"这里有一个按钮超出边界"这样的自然语言，fullstack-engineer 技能需要的是"修改 `auto_pm/ui/main_window.py:237`，将 `setPopupMode(InstantPopup)` 改为 `setPopupMode(DelayedPopup)`"这样的精确指令。这个翻译过程目前全靠人工。

**影响**：即使 AI 正确识别了 12 个视觉问题（V0.5.2 报告中的 3 out_of_bounds + 9 zero_size），实际能转化为代码改动的不到 30%。

### 2.2 断层2：测试通过 ≠ 用户可用

**程序化检查的盲区**：

| 检查项 | 覆盖范围 | 遗漏范围 |
|--------|---------|---------|
| `out_of_bounds` | 控件几何超出父控件 | 控件内容是否可读、是否有滚动条 |
| `zero_size` | 宽/高为 0 | 宽/高 > 0 但被其他控件遮挡、z-order 错误 |
| `text_truncation` | 文本宽度 > 控件宽度 | 字体渲染问题（emoji 缺失）、编码问题 |
| `low_contrast` | 窗口文字色对比度 | 徽标/卡片/表格的颜色可区分性 |

**隔离 tmp 工作空间 vs 真实工作空间差异**：

| 维度 | tmp 工作空间 | 真实工作空间 |
|------|-------------|-------------|
| 项目数 | 1-2 个 | 13 个 |
| 项目分布 | 全是 PLC | 6 PLC + 6 Python + 1 未知 |
| DB 缓存 | 空库首次初始化 | 已有历史缓存数据 |
| 路径结构 | 扁平 | 嵌套 `01_Project自动化项目管理/Python自动化项目总库/02_在研项目/` |

这些差异导致：
- 在 tmp 空间通过的测试，真实空间可能因项目数多而触发不同的代码路径（如 DB 增量同步的 bug）
- 项目分类问题（stack=unknown、phase 为空）在 tmp 空间不会出现（fixture 自带 `.plc.json` 完整字段）

### 2.3 断层3：迭代节奏太快导致修复难以沉淀

PM_SESSION 显示：
- 6 天内 16 次 dogfooding 闭环（CHG-062~CHG-077 + CHG-079~CHG-085）
- 每次 2-4 个 Fix，版本号小步快跑（0.3.0→0.5.4）
- 每个 Fix 都有"全量回归 XXXX passed 7 skipped 0 failed"

但电气部门试用反馈"无法正常工作使用"，说明：
- **全量回归的 passed 数不能代表 GUI 可用性**
- 每次修复引入的新代码没有被充分 soak（在真实工作空间下连续运行验证）

## 3. 优化方案

### 3.0 总体策略：不改造技能，改造流水线中间件

pm-workflow 和 fullstack-engineer 技能本身没有结构性缺陷——前者管理流程、后者执行编码，职责清晰。问题出在**中间的连接管道**。

需要创建一个**GUI 视觉测试报告生成器**（一个新脚本/模块），作为流水线中间件：

```
gui_plc_full_test.py
  → 截图 + 程序化检查
  → GUI视觉测试报告生成器（★新增）
    → 结构化 JSON（包含截图路径、控件路径、视觉问题摘要、建议修复方向）
    → 多模态 AI 可直接消费此 JSON（附截图路径引用）
    → AI 返回结构化修复建议
  → fullstack-engineer 按建议实施
  → 回归验证
```

### 3.1 方案 A：增强结构化测试输出（关键，优先级最高）

**目标**：让多模态 AI 能精确定位问题，让 fullstack-engineer 能直接执行修复。

**修改文件**：`scripts/gui_plc_full_test.py`（新增报告格式）+ 新增 `scripts/gui_visual_reporter.py`

**实施要点**：

1. **程序化检查结果结构化增强**：
   - 每次检查记录映射到具体的源代码文件和行号（如 `auto_pm/ui/main_window.py:237`）
   - 输出格式增加 `fix_hint` 字段（如 `"将 setPopupMode(InstantPopup) 改为 DelayedPopup 或添加 menu-indicator 样式"`）
   - 新增 `widget_snapshot.json`：记录每个被检查控件的 objectName / class / geometry / visible / parent

2. **AI 消费接口**：
   - 输出 `ai_analysis_input.json`：包含截图文件列表 + widget_snapshot + bug_summary，可直接喂给多模态模型
   - 预定义 prompt 模板：让 AI 输出结构化修复指令（文件路径 + 行号范围 + 修改方案）

3. **真实空间回归模式**（`--real-workspace` 标志）：
   - 测试脚本支持直接指向真实工作空间而非 tmp 隔离空间
   - 只读模式：不创建/修改项目，只截图+检查+分析

**产出物**：

```
test_reports/gui/
  ai_analysis_input_<timestamp>.json   # 给多模态 AI 的结构化输入
  ai_fix_suggestions_<timestamp>.json  # AI 返回的结构化修复建议（模板）
```

### 3.2 方案 B：补齐程序化检查盲区

**目标**：让自动化检查覆盖更多真实用户可感知的问题。

**修改文件**：`scripts/gui_plc_full_test.py` 中的 `run_visual_checks()`

**新增检查项**：

| 检查项 | 描述 | 实现方式 |
|--------|------|---------|
| `z_overlap` | 可见控件被其他控件遮挡 | 比较兄弟控件的 geometry 交叠 + z-order |
| `scrollbar_missing` | 内容溢出但父控件无滚动条 | 检查内容 size 是否 > viewport size 且无 QScrollArea 包裹 |
| `empty_space` | 大面积空白区域（可能布局失败） | 检查连续 widget 间隙 > 阈值 |
| `text_encoding` | 中文/emoji 等特殊字符是否正常渲染 | 对比 label.text() 与像素宽度预期 |

### 3.3 方案 C：pm-workflow 技能 CHG 模板增强

**目标**：让 pm-workflow 技能能直接消费视觉测试报告。

**修改范围**：pm-workflow 技能使用的 CHG 变更单模板（'040 规范）

**实施要点**：
- CHG 模板增加 `§10.2 视觉回归检查` 章节（V0.5.4 已有 `§10.1 验证项清单`，新增视觉子章）
- CHG 创建时可选从 `bug_report.json` 自动填充视觉问题列表
- pm-workflow 的 `current_focus` 中包含上次测试报告的视觉问题摘要

### 3.4 方案 D：fullstack-engineer 技能测试模式优化

**目标**：让 fullstack-engineer 在 GUI 修改后自动触发真实工作空间只读回归。

**修改范围**：fullstack-engineer 技能的测试执行流程

**实施要点**：
- 修改 GUI 代码后，先跑 tmp 空间的单元测试 → 再跑真实空间的只读截图回归
- 真实空间回归结果与上次基线 diff，差异 ≥ 阈值时阻断合并
- 失败时自动生成 AI 可消费的问题描述（截图 + widget_snapshot + diff 对比）

## 5. 验证方法

1. **步骤 1-2 完成后的验证**：
   - 在真实工作空间运行 `python scripts/gui_plc_full_test.py --real-workspace`
   - 检查 `test_reports/gui/ai_analysis_input_*.json` 是否包含完整结构
   - 用此 JSON 喂给多模态模型，验证 AI 能否产生精确到文件名+行号的修复建议

2. **步骤 3-4 完成后的验证**：
   - 模拟修改某 UI 代码后，运行只读回归
   - 验证 diff 对比是否准确
   - 验证失败时的 AI 输入 JSON 是否完整

3. **全链路验证**：
   - 运行 → 截图 → 生成 JSON → 喂给 AI → AI 输出修复建议 → fullstack-engineer 实施 → 再运行
   - 循环 2-3 次，观察 GUI 问题是否收敛

## 6. 结论

**pm-workflow 技能没有问题**：它在管理迭代节奏、变更闭环、文档同步方面工作良好。

**fullstack-engineer 技能没有结构性缺陷**：它能执行编码和测试任务，测试基础设施（gui_plc_full_test.py + tests/gui/ + tests/ui/）本身很完善。

**问题在于两者之间缺少"结构化管道"**：当前的截图分析→代码修改循环依赖人工翻译，导致：
- 多模态 AI 的分析结果无法直接驱动代码改动
- 0 bug 的测试报告与实际用户体验之间存在断裂
- 快速迭代下修复难以沉淀（每次都修 2-3 个点，没有收敛验证）

**最优路径**：创建 `gui_visual_reporter.py` 作为中间件，让截图分析结果能够被程序化消费，而不需要改造两个技能本身。
