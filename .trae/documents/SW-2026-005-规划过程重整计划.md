# SW-2026-005 规划过程重整计划

## Summary

- 目标不是为当前 `SW-2026-005` 做一次“能打开工作空间目录”的临时修补，而是把项目重新定位为一个长期可演进的 **Trae 伴生式 PLC 工作空间管理器**。
- 新的规划过程将服务于后续交给 GLM5.1 的开发执行，因此文档必须做到“决策闭环 + 文件落点明确 + 接口边界清晰 + 测试口径可直接执行”。
- 本轮重整重点是 `01_项目文档/02_规划过程/` 目录，但为了避免入口文档继续指向失效版本，需同步修正少量上游/下游索引文件。
- 规划主线将从“独立桌面项目管理工具”调整为“Trae 中开发 PLC 程序，SW-2026-005 负责工作空间挂载、治理、索引、检查、文档与汇总视图”的产品形态。
- 未来研究方向文档，如 `01_项目文档/02_规划过程/012_V3.0开发规划_DEV-PLAN-V3.0.0.md`，保留但移出主线，不作为本轮 GLM5.1 开发输入。

## Current State Analysis

### 1. 代码现状与方案缺口

- `03_主程序/01_主程序核心代码/src/services/artifact_registry_service.py`
  - 当前 `detect_project_type()` 仅识别 `DJ_SINGLE_MACHINE` 与 `GENERIC`。
  - 不支持 `workspace.json`、`PLC_LIBRARY`、`PLC_WORKSPACE` 等概念。
- `03_主程序/01_主程序核心代码/src/services/project_service.py`
  - 当前仅支持单项目加载与 DJ 项目导入。
  - 不存在 `load_workspace_from_path()` 或等价工作空间聚合加载能力。
- `03_主程序/01_主程序核心代码/src/ui/controllers/project_controller.py`
  - `on_project_opened()` 仅接受根目录配置文件或 DJ 单机目录。
  - 未对“工作空间根节点打开”提供分支处理。
- `03_主程序/01_主程序核心代码/src/core/constants.py`
  - `ProjectType` 只有 `GENERIC` 和 `DJ_SINGLE_MACHINE`。
  - `BusinessLine` 无共享库/工作空间治理语义。

结论：
- 用户给出的 `SW-2026-005-PLC项目库工作空间支持方案.md` 指向的根因与代码现状一致。
- 但这份方案仍偏“在现有桌面工具中补工作空间打开能力”，尚未完整吸收你已确认的长期定位，即 “Trae 主开发，工具做挂载/治理/汇总”。

## Proposed Changes

### A. 规划目录重构原则

- 保留 `006~010` 作为“当前主线规划文档”编号区间。
- 将“当前主线”“历史规划”“未来储备”三类内容彻底分层，避免混在同一个 README 导航中。
- 主线文档全部改为围绕以下统一定位展开：
  - 产品定位：Trae 伴生工具
  - 核心对象：PLC Workspace / Project / Shared Library / Spec Directory
  - 主要职责：挂载、浏览、索引、治理、检查、文档、汇总
  - 非目标：不替代 Trae 编辑器；不把 PLC 主开发迁回独立 GUI；不做“大而全”单体桌面平台
- 所有主线文档都必须增加“文档适用范围”和“GLM5.1 执行入口”说明。

## Assumptions & Decisions

### 已确认决策

- 本轮目标是 **长期方案**，不是临时兼容补丁。
- 产品形态确定为 **Trae伴生工具**，而非继续强化成独立桌面主工具。
- 后续交付对象是 **GLM5.1 开发执行**，因此文档粒度必须做到“可直接开发”。
- 架构原则必须坚持 **高内聚、低耦合**。
- 开发过程中必须保持 **文档随实现同步更新**。
- `012_V3.0开发规划_DEV-PLAN-V3.0.0.md` 保留，但移出当前主线。

### 规划假设

- 本轮首先重整文档，不在该计划阶段直接修改代码。
- `01_项目文档/02_规划过程/` 目录允许新增一份面向当前主线的开发规划文档。
- 历史规划文档可以保留，但必须从主线索引中降级。
- 现有 `SW-2026-005-PLC项目库工作空间支持方案.md` 将作为输入材料，而不是最终交付位置。
