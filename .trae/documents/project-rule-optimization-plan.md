# project-rule.md 优化建议方案

## 一、现状分析

### 当前规则文件内容

```markdown
0.在编写任何代码之前，要详细描述你的方案，包括功能、实现方式、依赖项等，如果需求不明确，要先与项目负责人沟通，确认需求。
1.如果任务特别负载，需要修改或者编写的文件较多，需要先停下来，进行分解任务，每个任务只负责一个功能模块。
2.在编写代码时，要考虑到项目的可维护性和可扩展性。
3.在编写代码时，要符合项目的编码规范和样式。
4.编写代码后，列出可能出现的问题和解决方法。并建议用相应的测试用例进行验证。
5.每次当我纠正你之后，你重新审视我们的对话确认，在本规则中重新添加相关规则，这样那就保证不会再发生类似的情况。
6.当发现bug时，首先编写以能重现bug的代码，确认bug的存在。然后不断测试代码，直到bug被修复。
```

### 项目上下文

本工作空间是一个**工业自动化综合工作空间**，包含：

* **PLC自动化**（SCL/Siemens）— 核心业务

* **Python工具**（PyQt5/PySide6/Flask）— 辅助工具

* **全局规范体系**（Obsidian知识库）— 规范治理

* **三层规则架构**：全局规则 → 技术栈规则（plc-rules.md / python-rules.md）→ 项目级规则

## 三、优化建议

### 建议一：结构化重组（优先级：🔴高）

将7条平铺规则按**开发阶段**分组，增加标题和层级：

```markdown
# 全局开发规则

## 一、编码前准备
1. [方案描述] 编写代码前，必须详细描述方案...
2. [任务分解] 任务复杂时，必须分解为单功能模块任务...

## 二、编码过程
3. [规范遵循] 必须遵循当前工作目录对应的技术栈规范...
4. [质量要求] 代码必须满足可维护性和可扩展性...

## 三、编码后验证
5. [问题预判] 编码完成后，列出可能的问题和解决方法...
6. [Bug修复] 发现bug时，先编写复现代码...

## 四、持续改进
7. [规则迭代] 每次纠正后，审视对话并更新规则...
```

### 建议二：增加规则层级说明（优先级：🔴高）

明确全局规则与技术栈规则的关系：

```markdown
## 规则层级

本工作空间采用三层规则架构：
1. **全局规则**（本文件）：适用于所有项目的通用开发准则
2. **技术栈规则**：针对特定技术栈的详细规范
   - PLC: `0100_PLC自动化/.trae/rules/plc-rules.md`
   - Python: `01_Project自动化项目管理/.trae/rules/python-rules.md`
3. **项目级规则**：单个项目的特殊约定

**冲突处理**：当全局规则与技术栈规则冲突时，以技术栈规则为准。
```

### 建议三：增加安全规则（优先级：🔴高）

```markdown
## 安全红线

- 禁止在代码中硬编码密钥、Token、密码等敏感信息
- 禁止将敏感信息文件（如 *.key, *.token, *.secret）提交到版本库
- 禁止在日志中输出敏感信息
```

### 建议四：增加技术栈感知规则（优先级：🟠高）

```markdown
## 技术栈适配

根据当前工作目录自动适配对应的技术栈规范：
- 工作在 `0100_PLC自动化/` 下 → 遵循 plc-rules.md + 905/904/903/906规范
- 工作在 `01_Project自动化项目管理/` 下 → 遵循 python-rules.md + 210/211/220规范
- 跨域修改时 → 同时遵循两个技术栈的规范
```

### 建议五：增加版本管理基本要求（优先级：🟠高）

```markdown
## 版本管理

- 提交信息必须遵循 `git-commit-message.md` 规范
- 每次提交应该是原子性的（一个逻辑变更一次提交）
- 禁止提交无法编译/运行的代码
```

### 建议六：修正文字错误（优先级：🟡中）

* 规则1："负载" → "复杂"

* 规则5："那就" → "才能"

### 建议七：增强规则可执行性（优先级：🟡中）

将笼统的规则细化为可检查的要点：

```markdown
## 编码过程

3. [规范遵循] 编码时必须遵循当前技术栈的编码规范：
   - PLC/SCL: 遵循905编程规范（命名、语法、代码结构）
   - Python: 遵循210编程规范（命名、风格、架构）
   - 不确定时，查阅对应技术栈的规则文件

4. [质量要求] 代码必须满足：
   - 可维护性：函数/功能块单一职责，命名清晰，注释充分
   - 可扩展性：避免硬编码，使用配置/常量，预留扩展接口
   - 可测试性：关键逻辑可独立测试，避免全局状态依赖
```

### 建议八：增加规范体系入口引用（优先级：🟡中）

```markdown
## 规范体系

项目规范权威目录：
- 全局PM规范: `00_Obsidian_Base全局规范文件仓库/`
- PLC技术栈规范: `0100_PLC自动化/00_通用规范/PLC编程/`
- Python技术栈规范: `01_Project自动化项目管理/00_通用规范/Python开发/`
- 规范注册表: `00_Obsidian_Base全局规范文件仓库/spec_registry.json`
```

### 建议九：增加反面约束（优先级：🟢低）

```markdown
## 禁止事项

- 禁止跳过方案描述直接编码
- 禁止在未确认需求的情况下假设需求
- 禁止忽略已有规范自行发明新的编码风格
- 禁止提交包含敏感信息的代码
```
