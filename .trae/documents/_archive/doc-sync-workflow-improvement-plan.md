### 0.3 核心矛盾

```
理想流程:  文档先行 → 代码实现 → 同步文档
实际流程:  需求讨论 → 快速编码(AI加速) → 文档追不上 → 放弃同步
```

**本质问题**：不是"不想同步"，而是**同步成本 > 同步收益**时的理性选择导致的技术债累积。

## 1. 方案：分层同步策略（Tiered Sync）

### 1.1 设计原则

| 原则         | 说明                                |
| ---------- | --------------------------------- |
| **承认速度差**  | 不追求"代码改了文档立刻改"，而是**分层级、分频率**同步    |
| **降低同步粒度** | 从"每个FB 4份文档"缩减为"1份接口真相源 + 按需生成其余" |
| **自动化优先**  | 能自动生成的绝不手写，能批量处理的绝不一处处            |
| **门禁兜底**   | 里程碑节点必须有文档检查，但不阻塞日常开发             |

### 1.2 三层同步模型

```
┌─────────────────────────────────────────────────────┐
│  L0 实时层 (Real-time)    ← 每次代码修改必同步       │
│  ─────────────────────────────────────────────────  │
│  • GlobalVars.db          (变量声明 = 代码的一部分)   │
│  • .scl 文件头注释         (版本号 + 变更记录)          │
│  • PM_SESSION             (current_focus + logs)      │
├─────────────────────────────────────────────────────┤
│  L1 里程碑层 (Milestone)   ← 每个迭代结束必同步       │
│  ─────────────────────────────────────────────────  │
│  • IFC 接口文档           (从 GlobalVars.db 自动提取) │
│  • CHG 变更记录           (从 git log / PM_SESSION 提取)│
│  • 801 编码规范            (新增规则追加)              │
├─────────────────────────────────────────────────────┤
│  L2 按需层 (On-demand)     ← 交付/审核前按需更新       │
│  ─────────────────────────────────────────────────  │
│  • DSN 详细设计说明书      (架构级文档, 低频变更)       │
│  • UM 使用手册            (面向操作员, 稳定后编写)     │
│  • 变更台帐               (项目级统计, 月度汇总)        │
└─────────────────────────────────────────────────────┘
```

### 1.3 各层具体规则

#### L0 实时层 — 零妥协

| 动作                 | 规则                                    | 执行者      |
| ------------------ | ------------------------------------- | -------- |
| 修改 `.scl`          | 文件头版本号必须递变，变更记录必须追加一行                 | AI(Trae) |
| 修改 `GlobalVars.db` | 变更记录区必须追加一行，结构注释必须更新                  | AI(Trae) |
| 修改任何代码             | `PM_SESSION.md` 的 `change_log` 必须追加一条 | AI(Trae) |

> **理由**：这三项是"代码的副产品"，修改代码时顺手完成，额外成本 < 1分钟。

#### L1 里程碑层 — 迭代边界强制

| 触发条件          | 必做动作                 | 验收标准             |
| ------------- | -------------------- | ---------------- |
| 一个 FB 的接口变更完成 | 更新对应 IFC 文档版本号 + 接口表 | IFC版本 ≥ 代码版本     |
| 一个迭代/阶段完成     | 批量更新所有受影响FB的 CHG 记录  | CHG最新条目 = 本次迭代内容 |
| 新增编码规范        | 801规范版本号递变 + 自检清单追加  | 新规范有编号可追溯        |

> **执行时机**：PM Workflow 的 Step 4（会话落盘）时一并处理。

#### L2 按需层 — 交付前检查

| 触发条件    | 动作                        | 说明             |
| ------- | ------------------------- | -------------- |
| 项目交付/验收 | 全部DSN + UM 对齐到代码最终版       | 一次性批量处理        |
| 月度复盘    | 变更台帐汇总本月所有 change\_log 条目 | 从PM\_SESSION聚合 |
| 架构评审    | ARC架构文档反映当前系统拓扑           | 低频，仅在重大重构后     |

### Phase 2：建立自动化辅助工具

#### Step 2.1：创建 IFC 文档生成脚本（概念）

```
输入: GlobalVars.db (已完成，含完整中文注释)
输出: IFC-FBxxx-Vx.x.x.md (接口表格)

逻辑:
  1. 解析 GlobalVars.db 中 stXxx STRUCT 的 VAR 声明
  2. 提取每个变量的: 名称 + 类型 + 默认值 + //行内注释
  3. 生成标准 Markdown 表格
  4. 与现有 IFC 文档 diff，仅高亮差异部分
```

> **注意**：这不是要立即开发的脚本，而是定义"未来可自动化"的方向。
> 当前阶段由 AI 在 L1 里程碑节点手动执行此逻辑。

#### Step 2.2：创建文档同步 Checklist 模板

在每个迭代的 PM\_SESSION 更新时，附带以下检查：

```markdown
## 文档同步检查 (L0+L1)
- [ ] .scl 文件头版本号已递变?
- [ ] GlobalVars.db 变更记录已追加?
- [ ] PM_SESSION change_log 已追加?
- [ ] 受影响FB的IFC文档版本是否≥代码版本?
  - [ ] FB_1002: 代码V__ / IFCV__
  - [ ] FB_1003: 代码V__ / IFCV__
  - [ ] FB_1004: 代码V__ / IFCV__
  - [ ] FB_2001: 代码V__ / IFCV__
  - [ ] External: 代码V__ / IFCV__
  - [ ] OB1: 代码V__ / IFCV__
  - [ ] DB1: 代码V__ / IFCV__
```

### Phase 3：固化到工作流

#### Step 3.1：修订 PM Workflow Step 4

当前 Step 4 仅要求更新 PM\_SESSION。**新增 L1 文档同步检查**：

```
Step 4 (增强版): 会话落盘 + 文档同步门禁
  4a. 更新 PM_SESSION (原有)
  4b. 执行 L0 检查 (文件头/DB1/SESSION 三者一致)
  4c. 若本次事件涉及接口变更 → 执行 L1 同步 (更新IFC/CHG)
  4d. 若到达里程碑边界 → 执行 L2 检查 (DSN/UM/台帐)
  4e. 输出 "文档同步报告" 附在 SESSION 末尾
```

#### Step 3.2：定义"里程碑边界"

| 里程碑类型     | 触发条件                  | L1/L2 要求                  |
| --------- | --------------------- | ------------------------- |
| **FB级迭代** | 单个FB的接口/行为变更完成        | L1: 该FB的IFC+CHG必须对齐       |
| **子系统迭代** | 多个FB联动变更(如Conveyor重构) | L1: 所有受影响FB的IFC+CHG + OB1 |
| **版本发布**  | V x.y.z 递增            | L1全部 + L2: DSN摘要更新 + 台帐回填 |
| **项目交付**  | 最终验收                  | L0+L1+L2 全量对齐             |

## 3. 方案对比（为什么选这个方案）

| 维度           | 理想方案(每次同步)      | 本方案(分层同步)                    |
| ------------ | --------------- | ---------------------------- |
| **日常开发阻力**   | 高（每次改代码都要改4份文档） | **低（仅L0，<1分钟）**              |
| **文档准确性**    | 100%实时准确        | **L0=100%, L1=里程碑准, L2=交付准** |
| **技术债累积风险**  | 无               | **可控（有明确的偿还触发点）**            |
| **实施成本**     | 高（需强纪律+工具）      | **低（利用现有PM\_SESSION机制扩展）**   |
| **适合AI辅助场景** | 差（AI产出速度快于文档速度） | **好（匹配AI的批次处理特性）**           |

## 5. 风险与缓解

| 风险                              |  概率 |  影响 | 缓解措施                            |
| ------------------------------- | :-: | :-: | ------------------------------- |
| 分层策略导致L1/L2文档长期不更新              |  中  |  中  | PM\_SESSION中增加"文档健康度"指标，每次打开时提醒 |
| AI对话中途切换任务导致L0遗漏                |  中  |  低  | 将L0检查写入 project-rule.md 作为强制规则  |
| 版本号体系混乱(如External V4 vs IFC V6) |  高  |  低  | Phase 1.1 第5项统一版本线              |
