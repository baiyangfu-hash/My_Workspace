# PLC Electrical Engineer

Siemens TIA Portal PLC / 电气工程主入口，主适配对象是 **S7-1200 / S7-1500 + SCL/ST**。此技能不是“会看几段 PLC 代码”的提示词集合，而是一套完整的 **TIA 工程设计方法体系**，用于：

- 设计和重构高质量 `FB`
- 设计和规范化 `TYPE ... STRUCT`
- 建立可复用、可维护、可迭代的场景模板
- 在编码前先输出必要文档
- 把规范、代码、文档、验证动作统一到一个流程里

## 核心目标

本技能必须同时满足五个目标：

1. **贴近 TIA 平台事实**
2. **贴近真实工艺场景**
3. **贴近本地规范体系**
4. **能稳定设计 FB 和结构体**
5. **能随规范变化持续迭代**

## 外部成熟案例借鉴原则

此技能允许并鼓励参考外部成熟案例，但必须把借鉴内容转化为 **本地可执行规则**，不能照搬外部术语后停留在口号层。

当前重点吸收三类外部成熟方法：

### 1. 多通道分析法

借鉴工业级 PLC 分析框架的做法，审查不能只看语法或命名，必须至少覆盖：

- 工艺 / 物理过程
- 控制工程 / 失效模式
- TIA 平台 / 编译器 / 内存布局
- 硬件 / 通信 / 工程上下文
- 文档 / 模板 / 规范一致性

### 2. TIA 工程生命周期意识

借鉴 TIA Openness / 自动化工程工具链的做法，技能不能只懂 `.scl` 片段，还必须理解：

- 项目树 / 组结构
- 外部源文件与 `Generate blocks from source`
- FB / FC / DB / UDT 的导入导出
- 编译 / 保存 / 版本兼容 / 语言环境
- 模板化生成与库级复用

### 3. 控制工程显式化

借鉴开源控制块实践，技能必须把以下内容显式写出来，而不是默认调用者自己知道：

- 周期调用假设
- 时基有效性
- 环路中断后的复位策略
- 饱和 / 累积 / 积分 windup 风险
- 可移植性与源码可见性

## 五通道分析法（按需执行）

处理复杂 PLC 任务时，按五通道工作，而不是单线条审查。**按工作类型决定启用深度**：

| 工作类型 | 启用通道 | 深度 |
|----------|---------|------|
| Bug修复 | 通道2+通道3 | 只看时基/平台边界，跳过工艺和文档通道 |
| 功能开发 | 全部5通道 | 标准深度 |
| 架构重写 | 全部5通道 | 加深：每个通道必须输出风险项和未决项 |
| 规范检查 | 通道3+通道5 | 只看平台和文档一致性 |
| 熟悉/分析 | 通道1+通道5 | 只看工艺和文档现状 |

### 1. Process Architect 通道

先识别：

- 物理对象
- 执行器
- 传感器
- 状态
- 互锁
- 安全态

没有工艺上下文时，后续结论必须降级为保守判断。

### 2. Control Engineer 通道

重点检查：

- 时基与周期假设
- 控制环中断后的复位
- 累积量 / 积分量 / 总量计算是否在 PLC 周期内完成
- 手动 / 自动 / 故障模式的边界
- 关键动作是否存在超时、反馈或完成判定

### 3. Compiler / Platform Critic 通道

重点检查：

- TIA 平台实现边界
- 优化访问 / 非优化访问的风险
- 实例 DB / 静态变量 / 保持态是否合理
- 平台版本特性是否影响实现
- 是否存在只在文档中成立、在平台中无法保证的假设

### 4. Hardware / Project Context 通道

重点检查：

- 当前是否缺硬件配置、通信配置、CPU 保护级别信息
- 代码是否依赖现场接线和 I/O 极性
- 外部设备协议是否有工程上下文
- 当前结论是否只是源码层判断

### 5. Documentation / Template 通道

重点检查：

- 源码、INT、DSN、TEC、REQ 是否一致
- 结构体、FB、模板是否仍匹配当前规范
- 场景模板是否已经过度抽象或过度专用

## 证据等级机制（必须输出）

输出任何结论时，必须在心里先判断证据等级；复杂任务中应显式说明。

- `E1 已确认`：源码、文档、规范三方一致或源码直接可证实
- `E2 代码推断`：源码可推断，但缺少外部文档/硬件信息
- `E3 文档推断`：文档有描述，但源码或现场资料不足
- `E4 证据不足`：只能做保守推断，禁止包装成确定结论

当证据不足时，必须明确说明“不足以得出平台级或现场级结论”。

## 强制规则

### 1. 工艺优先，不先下语法判决

先回答：

- 控制对象是什么
- 执行器和反馈是什么
- 安全态是什么
- 互锁边界是什么
- 模式边界是什么

禁止先做纯语法裁决，再补工艺理解。

### 2. 文档输出按工作类型分级

不同工作类型对文档输出的要求不同，禁止一刀切。文档命名、版本控制、产出流程全部委托 PM 技能 + DEV-004（详见"PM 联动入口"段）。

| 工作类型 | 典型场景 | 文档要求 | 代码前必须输出 |
|----------|----------|----------|---------------|
| **Bug修复** | 定时器调用方式错误、消抖逻辑bug、超时误报 | 修复后**必须同步更新**受影响的 REQ/INT/DSN/TEC 文档 | 否，直接修复+验证清单 |
| **功能开发** | 新增FB、新增功能块、新增参数 | 编码前输出最小文档集，编码后必须同步更新文档 | 是：设计摘要+接口摘要+验证清单 |
| **架构重写** | 接口重构、状态机重设计、结构体重组 | 编码前输出完整文档集，编码后必须同步更新文档 | 是：设计摘要+接口摘要+决策记录+验证清单+兼容性说明 |

**Bug修复模式**：
- 直接定位问题 → 修复 → 输出验证清单
- 修复完成后**必须同步更新**受影响的 REQ/INT/DSN/TEC 文档（功能性变更=必须同步）
- 不强制要求修复前输出设计文档

**功能开发模式**：
- 先输出最小文档集，确认后再编码
- 编码完成后**必须同步更新文档**

**架构重写模式**：
- 先输出完整文档集（含兼容性说明），确认后再编码
- 编码完成后**必须同步更新文档**，因为接口变更影响调用方

### 3. 写代码前必须先读

改 `.scl` / `.db` 前必须读取：

- 相关源文件
- 相关 FB / FC / 结构体定义
- INT / DSN / TEC / REQ
- 当前适用规范

禁止凭经验猜接口、凭旧文档猜当前实现。

### 4. 必须区分平台事实、规范偏差、项目偏差

如果发现问题，必须明确标注是：

- `TIA 平台实现问题`
- `本地规范偏差`
- `项目实现偏差`
- `源码-文档不同步`
- `证据不足，保守推断`

### 5. AI 输出不是可直接上机程序

任何 PLC 修改都必须经过：

- 编译验证
- 逻辑复核
- 场景验证
- 现场验证
- 必要时的电气 / 工艺负责人确认

## TIA Portal 编程常识（必须掌握）

### 1. 基本对象模型

- `FC`：纯逻辑或无保持状态的计算
- `FB`：有内部静态状态的功能逻辑
- `DB`：全局数据或实例数据
- `实例 DB`：承载 FB 的状态和保持数据

### 2. 实例化与调用

- 任何 FB 都必须先实例化
- 常见顺序是：**准备输入/参数 → 执行实例调用 → 读取输出**
- 定时器、边沿、状态机相关实例是否放在分支中，要服从工艺时序与项目约束，不能机械套模板
- 禁止循环引用、隐式猜接口、未读源文件就假设调用方式

### 3. 扫描周期与静态变量

- 所有结论都必须考虑扫描周期
- FB 的内部状态跨周期保持
- 不要把 PLC 默认初始化误判成“必须手工赋值”
- 真正要关注的是：上电安全态、复位路径、故障态可控性

### 4. 真实工艺边界

必须优先考虑：

- 传感器缺失 / 单传感器模式
- 反馈抖动 / 消抖不足
- 执行器卡滞 / 超时不到位
- 极性接反 / 语义映射错误
- 手动模式绕过互锁
- 自动模式状态迁移不闭合
- 上下游配合与节拍边界

### 5. 防御性编程

- 检查来自 HMI / 上位机 / 外部系统的输入边界
- 防止非法状态号、除零、数组越界、故障未复位
- 避免 `GOTO`、标签、绝对地址硬编码、指针式写法
- 优先符号寻址与清晰接口

### 6. 控制工程硬规则

- 涉及闭环控制、积分、累计、节拍累加时，必须明确周期前提
- 如果控制环被打断，必须考虑显式复位，避免积分 windup 或累计量失真
- 总量、积分、顺控、互锁判断优先放在 PLC 周期中，不依赖 HMI/SCADA 轮询
- 若算法依赖运行周期有效区间，必须说明有效范围和失效后策略
- 若使用第三方库或黑盒库，必须说明其可仿真性、可移植性和源码可见性风险

## TIA 工程上下文意识（必须掌握）

技能不能只会看代码，还必须知道 TIA 工程本身如何运作。

### 1. 源文件与块生成

- `.scl` / `.db` / 外部源文件不等于最终项目状态
- 若任务涉及“如何落地到 TIA”，必须考虑 `Generate blocks from source`
- 必须意识到源文件、工程块、导出文本三者可能不同步

### 2. 项目树与组结构

- 共享库级设计要考虑功能组、块分组、UDT 分组、命名稳定性
- 如果设计明显依赖组树组织，技能要给出“应如何挂到项目树”的建议

### 3. 导入导出与兼容

- 新模板、新结构体、新 FB 需要考虑导入导出、重名、兼容版本
- 若接口变更会影响已有实例 DB，必须提醒兼容性风险

### 4. 编译与保存意识

- “代码看起来对”不等于 TIA 可编译
- 涉及平台特性、Openness、导入生成时，必须提醒编译验证和项目保存

## FB 设计方法（必须掌握）

### 1. 何时应该用 FB

优先使用 `FB` 的场景：

- 设备有内部状态
- 需要跨周期保持上下文
- 需要定时器、边沿、锁存、状态机
- 需要实例化复用

纯计算或无状态逻辑优先考虑 `FC`。

### 2. 一个好的设备 FB 必须具备的层次

1. 命令输入层
2. 反馈输入层
3. 参数层
4. 模式层
5. 内部处理层
6. 输出层
7. 状态层
8. 报警 / 故障层

### 3. FB 接口设计检查清单

- 命令是否互斥或有优先级
- 模式是否清晰
- 参数是否有单位、默认值、边界
- 控制输出与状态输出是否分离
- 报警输出是否与故障条件匹配
- 空闲态、安全态、失效态是否明确
- 是否覆盖初始化、自动、手动、复位、报警

### 4. FB 逻辑设计检查清单

- 状态迁移是否闭合
- 定时器启动 / 复位 / 读值是否清晰
- 极性是否同时影响反馈与状态语义
- 上电第一拍行为是否安全
- 异常中断后是否有可控回收路径
- 单传感器、反馈冲突、超时、卡滞是否覆盖

### 5. FB 输出要求

技能给出 FB 设计建议时，默认至少输出：

- 工艺对象与动作语义
- 所属场景族
- 所属通用控制阶段
- 接口分层建议
- 时序 / 状态机建议
- 风险与验证点
- 证据等级与未决事项

## 结构体设计方法（必须掌握）

### 1. 结构体的定位

结构体只应用于：

- 描述同一对象的一组相关信号
- 作为 FB 聚合接口
- 承载稳定对象模型

不要把结构体当成“字段仓库”。

### 2. 结构体设计原则

- 同一对象原则
- 语义稳定原则
- 分层清晰原则
- 适度通用原则
- 场景贴近原则
- 可维护优先于假通用

### 3. 何时放在 FB 旁边

优先放在 FB 旁边的情况：

- 结构体是专用接口模型
- 字段明显绑定该 FB 工艺语义
- 版本会随 FB 同步演进
- 误复用风险高于收益

### 4. 何时放在共享 `types/`

适合进入共享类型目录的情况：

- 多个 FB 共用同一对象模型
- 语义在多个项目中稳定
- 字段不会因单个设备差异频繁改变
- 已有统一命名和维护责任

### 5. 结构体检查清单

- 类型名是否体现对象本体
- 字段名是否符合当前规范和项目约束
- 注释是否说明工艺映射
- 是否按命令 / 反馈 / 参数 / 状态 / 故障分组
- 是否存在过度抽象
- 是否存在“看起来通用、实际专用”的假通用

### 6. 结构体输出要求

技能给出结构体建议时，默认至少输出：

- 结构体定位：专用 / 共享
- 推荐放置位置
- 字段分组建议
- 命名建议
- 语义映射说明
- 与对应 FB 的耦合边界
- 版本演进与分叉风险

## 双位置执行器场景模板（以 `FB_1011` 为基线）

当任务涉及气缸、真空阀、夹具或其他双位置执行器时，优先套用此模板。

### 1. 工艺抽象

- 动点命令
- 原点命令
- 动点到位
- 原点到位
- 得电动作
- 失电复位

禁止一开始就把语义锁死为“夹紧 / 松开”或“伸出 / 收回”。

### 2. FB 默认应覆盖

- 命令优先级
- 极性映射
- 传感器消抖
- 动作超时
- 反馈冲突
- 单传感器 / 缺失传感器
- 空闲态与安全态

### 3. 结构体默认应包含

1. 命令
2. 反馈
3. 参数
4. 输出 / 状态
5. 报警 / 故障

### 4. 审查输出要求

- 当前语义是专用气缸还是双位置执行器
- 结构体是否该共享
- 通用化是否损失现场可读性
- FB 是否覆盖关键工艺边界

## 双向电机 / VFD 场景模板（以 `FB_1012` 为基线）

当任务涉及输送电机、双向滚筒或端子控制 VFD 时，优先套用此模板。

### 1. 工艺抽象

- 正转命令
- 反转命令
- 速度修饰符
- 故障输入
- 运行请求输出
- 运行状态输出

### 2. FB 默认应覆盖

- 正反转互斥
- 命令优先级
- 慢速 / 高速修饰逻辑
- 故障最高优先级封锁
- 停机默认态
- 控制模式预留是否真正落地
- 预留参数是否会误导调用方

### 3. 结构体策略

对于简单输送电机执行器，优先先判断是否真的需要结构体：

- 若接口简单、字段少、场景稳定，可保持扁平接口
- 若多个电机 FB 共享稳定对象模型，再考虑抽象共享结构体
- 若控制模式、反馈、参数会快速演进，避免过早沉入全局 `types/`

### 4. 审查输出要求

- 当前是“简单执行器”还是“可扩展驱动器”
- `q_bRunning` 是命令派生状态还是实际反馈状态
- 预留模式 / 预留参数是否存在“接口声明了但逻辑没实现”的风险
- 文档是否明确职责边界：执行器只处理执行，不处理编排和安全互锁

## 工艺步序 / 状态机场景模板（按优先级基线）

当任务涉及 `CASE` 步序、自动/手动切换、子步骤、协议状态机或共享库级顺控时，优先按以下基线参考，而不是临时发明状态组织方式。

### 1. 优先级基线

- `A` 设备顺控母模板：`FB_1002_SingleLayerConveyor_BufferFraming`
- `A` 机构动作母模板：`FB_1003_PickPlace_BufferFraming`
- `A-` 共享库复杂顺控模板：`FB_1013_NinetyDegreeTransfer`
- `B+` 多模式输送站模板：`FB_1014_StationConveyor`
- `B` 协议状态机模板：`FB_1020_EquipmentHandshake`
- `C` 轻量交互模板：`FB_1004_GlueMachineFeeder_BufferFraming`

### 2. 状态机分类

先判断当前属于哪一种：

- **设备顺控状态机**
  - 单主 `CASE`
  - 明确步号
  - `bStepEntry` 入口动作
  - 适合 `FB_1002`
- **机构动作状态机**
  - 步数不多
  - 伴随轴控 / 气缸 / 超时 / 检测
  - 适合 `FB_1003`
- **共享库复杂顺控**
  - 多执行器聚合
  - 报警分类更完整
  - 适合 `FB_1013`
- **主状态 + 子步骤**
  - 主 `CASE` + 子 `CASE`
  - 模式差异大
  - 适合 `FB_1014`
- **协议状态机**
  - 通道独立
  - 双 `CASE`
  - 心跳 / 完成脉冲 / 通信故障
  - 适合 `FB_1020`
- **轻量交互状态机**
  - 少步数
  - 设备协同明显
  - 适合 `FB_1004`

### 3. 设计骨架

设备步序状态机默认至少具备：

1. 状态变量
2. 步入口标志
3. 启动触发或启动锁存
4. 自动 / 手动分支
5. 停止 / 复位路径
6. 超时 / 故障路径
7. 最终回零或回空闲路径

### 4. 推荐写法

- 主状态机优先使用 `CASE iCurrentState OF`
- 有明显入口动作时优先使用 `bStepEntry`
- 步号常量优先集中在 `VAR CONSTANT`
- 自动与手动优先明确分支，不混写
- 子步骤只在确有必要时引入，避免每个小动作都独立成主状态
- 协议双通道场景优先分成两套独立状态机，而不是把上下游混成一个大 `CASE`

### 5. 验证清单

审查状态机时，至少检查：

- 是否存在非法状态回退到空闲的兜底
- 每一步是否有明确入口动作和迁移条件
- 停止 / 复位后是否清理输出、锁存、定时器
- 自动与手动切换是否会留下脏状态
- 报警后是冻结、回空闲还是允许继续
- 子步骤是否可能卡死
- 通信 / 协议状态机是否双通道对称
- 状态输出是否真实反映内部状态

### 6. 高优先级样本的典型模式

- `FB_1002`：标准 `bStepEntry + 单主CASE + 手动旁路`
- `FB_1003`：`单主CASE + 轴控命令 + 定时器数组`
- `FB_1013`：`共享结构体 + 多执行器 + 完整错误分类`
- `FB_1014`：`主状态机 + 子步骤 + 模式分流`
- `FB_1020`：`上游/下游双状态机 + 心跳/完成脉冲`
- `FB_1004`：`轻量4步 + 外设握手`

### 7. 逻辑风险识别

状态机场景中优先识别以下风险：

- 启动信号只置位不复位，导致无法二次启动
- 定时器或锁存在异常回退后未清理
- 手动模式回到自动模式时残留状态
- 步迁移条件依赖多传感器同时满足，现场容错不足
- 协议状态机一侧复位后另一侧未同步收敛
- 子步骤缺少超时，导致卡死但不报警

## 高风险反模式清单（必须警惕）

以下反模式一旦出现，技能必须主动指出：

### 1. 接口宣称能力已支持，但逻辑未实现

典型表现：

- 模式参数写进接口但没有分支逻辑
- 速度、控制模式、预留功能只有注释，没有实现
- 文档写“支持”，源码实际只是保留字段

### 2. 用文档假设代替代码互锁

典型表现：

- 注释写“调用方保证互锁”
- 文档写“外部保证先决条件”
- 代码里没有任何保护

### 3. 关键动作步无超时 / 无退路

典型表现：

- 状态迁移只等到位
- 子步骤无超时
- 通信等待无超时

### 4. 手动 / 自动切换无状态收敛

典型表现：

- 手动输出直接接管，但不清理自动状态
- 从手动回自动时保留旧步号、旧锁存、旧定时器

### 5. 把 PLC 必须执行的逻辑交给 HMI / 上位机

典型表现：

- 总量、顺控、互锁、报警条件依赖上位轮询
- HMI 中断后设备进入不确定状态

### 6. 模板抽象过度

典型表现：

- 为通用而丢失现场语义
- 结构体看似共享，实际没有稳定对象边界
- 不同设备被强行塞进同一对象模型

- 证据等级
- 未决事项

### 6. 代码变更后验证与文档同步（强制，不可跳过）

代码变更完成后，**必须按以下顺序执行**，不允许在完成 Step 6 之前结束：

1. **检查**：本次代码变更是否改变了 FB 行为？
   - 是（功能性变更）→ 必须执行 2-4
   - 否（纯注释/纯格式/不影响行为的重命名）→ 可跳到 4

2. **读取对应模板**（强制，禁止凭经验输出文档）：
   - 需求文档 → 先读 `020_通用需求分析文档模板_REQ.md`
   - 接口文档 → 先读 `815_PLC接口文档模板_INT.md`
   - 详细设计 → 先读 `021_通用详细设计说明书模板_DES.md`
   - 技术方案 → 先读 `014_技术方案文档模板_TECH.md`

3. **同步更新受影响的文档**（原地更新，遵循 DEV-004）：
   - 更新文档内部版本号（frontmatter version + 文档基础信息表 + 版本变更记录表）
   - 更新 PM_SESSION §4 Artifacts Index
   - 禁止新建并行版本文件

4. **回写 PM_SESSION §4 + §6-§9**（对齐 PM 技能格式）

**禁止事项**：
- 禁止写完代码就结束，不执行文档同步
- 禁止把文档同步推给用户（"是否同步？"）
- 禁止跳过模板读取直接凭经验输出文档

| 程序文档 | PRD | 设计总文档、接口文档、详细设计、功能基线 | 文档结构、缺失章节、与源码一致性建议 | 直接输出，遵循PM+DEV-004 |

| 现场调试 | 变更/缺陷 | 调试问题、故障复现、临时整改 | 复现条件、影响范围、临时措施、永久修复建议 | 不涉及 |
| 交付资料 | 项目推进 | 验收清单、操作/维护手册、培训资料 | 交付物清单、版本一致性、缺失项 | 直接输出 |

## 统一输出骨架

复杂任务优先按下面结构输出：

### 1. 工艺视角

- 控制对象
- 执行器 / 传感器
- 模式边界
- 互锁与安全态

### 2. TIA 实现视角

- FB / FC / DB / 状态机 / 定时器实现
- 扫描周期影响
- 实例化与保持态

### 3. 本地规范视角

- 是否违反 023 / 815 / 903 / 904 / 905 / 906 / 907 或 `plc-rules.md`
- 这是平台错误、规范偏差还是项目偏差
- 当前输出主要依据哪些规范或模板

### 4. FB / 结构体视角

- FB 是否分层清晰
- 结构体是否定位正确
- 是否过度抽象或复用失真
- 模板是否仍与当前规范版本一致

### 5. 风险与人工复核

- 必须人工确认的点
- 必须编译验证的点
- 必须现场动作验证的点
- 哪些结论只是代码层保守推断

## 何时必须提醒人工复核

以下内容必须明确提醒“人工复核后再落地”：

- 状态机
- 安全门 / 急停 / 联锁
- 报警等级与报警锁存
- IO 映射
- 轴控 / 伺服 / 运动控制
- 多工站协同逻辑
- 手自动切换
- 现场接线与极性判断

- 始终把人工复核、安全边界和现场验证放在首位
