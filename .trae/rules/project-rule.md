# 全局开发规则

## 规则层级

本工作空间采用三层规则架构：

1. **全局规则**（本文件）：适用于所有项目的通用开发准则
2. **技术栈规则**：针对特定技术栈的详细规范
   - PLC: `0100_PLC自动化/.trae/rules/plc-rules.md`
   - Python: `01_Project自动化项目管理/.trae/rules/python-rules.md`
3. **项目级规则**：单个项目的特殊约定

**冲突处理**：当全局规则与技术栈规则冲突时，以技术栈规则为准。

- `-w` 必须放在子命令之前；详细用法见 `pm-workflow` 技能

## 虚拟环境激活（强制）

所有技能在执行 `RunCommand` 运行 Python 相关命令前，**必须先激活工作空间虚拟环境**：

1. **检测顺序**：从工作空间根目录向上查找 `.venv/`、`venv/`、`.env/` 目录
2. **激活命令**（PowerShell）：
   ```powershell
   & "<工作空间根>\.venv\Scripts\Activate.ps1"
   ```
3. **验证激活**：激活后运行 `python --version` 和 `pip --version`，确认指向 `.venv` 内的 Python
4. **激活失败处理**：若 `.venv` 不存在或激活失败，**必须立即报告用户**，说明：
   - 未找到虚拟环境
   - 当前使用的是全局 Python（路径）
   - 可能导致工具（auto-pm、specmgr 等）不可用
   - 建议用户创建虚拟环境或在已有 venv 中安装依赖
5. **当前工作空间 venv 路径**：`c:\Users\fubai\Documents\My_Workspace\.venv\`

**禁止**在未激活虚拟环境的情况下运行 `auto-pm`、`specmgr`、`pip install`、`python` 等命令。

## 一、编码前准备

1. **方案描述**：编写任何代码之前，必须详细描述方案，包括功能、实现方式、依赖项等。如果需求不明确，必须先与项目负责人沟通确认需求，禁止在未确认需求的情况下假设需求。

2. **任务分解**：当任务复杂、需要修改或编写的文件较多时，必须先停下来进行分解，每个任务只负责一个功能模块。

## 二、编码过程

3. **规范遵循**：编码时必须遵循当前工作目录对应的技术栈编码规范：
   - PLC/SCL: 遵循905编程规范（命名、语法、代码结构）
   - Python: 遵循210编程规范（命名、风格、架构）
   - 不确定时，查阅对应技术栈的规则文件

4. **质量要求**：代码必须满足：
   - 可维护性：函数/功能块单一职责，命名清晰，注释充分
   - 可扩展性：避免硬编码，使用配置/常量，预留扩展接口
   - 可测试性：关键逻辑可独立测试，避免全局状态依赖

## 三、编码后验证

5. **问题预判**：编码完成后，列出可能出现的问题和解决方法，并建议用相应的测试用例进行验证。

6. **Bug修复**：当发现bug时，首先编写能重现bug的代码，确认bug的存在，然后不断测试代码直到bug被修复。

7. **后台任务监控**：启动后台测试/构建任务后，禁止被动等待通知。必须：①设置预期完成时间；②分段主动轮询（timeout=120s）；③超过预期时间未完成时立即读日志看进度，进度停滞即停止并诊断根因；④给用户明确时间预期。详见 `fullstack-engineer` 技能"后台任务监控纪律"章节

## 四、持续改进

8. **规则迭代**：每次被纠正后，必须重新审视对话，确认是否需要在本规则中添加新规则，这样才能保证不再发生类似的情况。

## 安全红线

- 禁止在代码中硬编码密钥、Token、密码等敏感信息
- 禁止将敏感信息文件（如 \*.key, \*.token, \*.secret）提交到版本库
- 禁止在日志中输出敏感信息

## 版本管理

- 提交信息必须遵循 `git-commit-message.md` 规范
- 每次提交应该是原子性的（一个逻辑变更一次提交）
- 禁止提交无法编译/运行的代码

## 迭代文档同步规则（强制）

1. **进度基线强制**：任何迭代 spec 必须包含"当前开发进度基线"章节，记录代码实际进度（代码规模、版本号现状、路线图完成度、里程碑核查），作为后续开发的起点
2. **迭代后同步**：迭代完成后必须同步更新以下文档：
   - pyproject.toml 版本号（与 CHANGELOG 最新条目一致）
   - CHANGELOG.md（新增版本条目）
   - PRD 路线图（新增版本章节）
   - PM_SESSION（§2 Current Focus 与 §8 Handoff Notes 版本号必须一致）
3. **版本号一致性**：pyproject.toml 版本号必须与 CHANGELOG 最新条目一致；PM_SESSION §2 与 §8 版本号必须一致
4. **里程碑核查**：里程碑迭代计划的"已完成"标注必须经过代码核查（文件行数、方法存在性、测试通过数），禁止仅凭声明标记完成
5. **变更记录**：每次迭代必须在项目 `00_项目基础信息/` 下维护变更记录文件，记录本次迭代的所有变更条目
6. **台账对账强制**：每次 CHG 闭环后必须执行 `auto-pm -w "<工作空间根>" ledger reconcile <项目ID>`，台账有差异时禁止升级版本号或开始新 CHG。每个迭代结束（版本号升级前）执行全量对账 `ledger reconcile <项目ID> --auto-fix`

## GUI 测试模式规则（强制）

- **正常 GUI 测试禁止使用 offscreen 模式**，必须使用可见窗口模式（`GUI_VISIBLE=1` 或不设置 `QT_QPA_PLATFORM=offscreen`）
- 仅当用户特别要求时才使用 offscreen 模式（如 CI 无显示器环境、批量回归）
- 理由：offscreen 模式无法验证真实字体渲染/DPI 缩放/多显示器场景，且会掩盖部分交互问题；默认按真实使用场景测试
- 适用范围：所有 GUI 测试（pytest tests/gui/、scripts/gui_plc_full_test.py、tests/ui/ 中的 GUI 相关测试）

## 禁止事项

- 禁止跳过方案描述直接编码
- 禁止忽略已有规范自行发明新的编码风格
- 禁止提交包含敏感信息的代码
- 禁止在 GUI 测试中默认使用 offscreen 模式（必须可见，除非用户特别要求）
