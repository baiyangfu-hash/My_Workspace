## 3. 技术方案概述

### 3.1 项目背景

auto-pm 旨在统一管理 PLC/Python 多技术栈项目，取代旧工具 pm-mgr (SW-2026-007) 和 plc-check。项目需要解决以下问题：

- **多技术栈管理**: PLC 和 Python 项目结构差异大，需要统一入口
- **项目脚手架**: 新项目需符合规范（LSP-907/210规范），手动创建易出错
- **变更管理**: 变更单需遵循 PM-042 V2.2.0 状态机，手动管理易遗漏门禁
- **规范检查**: PLC 项目需符合 LSP-907 结构规范，需自动化检查和修复
- **GUI 可用**: CLI 适合自动化，但日常管理需要可视化界面
- **多角色适配**: PM/PLC 工程师/Python 工程师/规范编辑者关注点不同，需同一界面按角色呈现

### 3.2 技术选型论证

本项目选择技术栈时，综合考虑以下因素：
- **Python 生态成熟度**: 优先选择社区活跃、文档完善的库
- **开发效率**: 减少样板代码，聚焦业务逻辑
- **可维护性**: 类型安全、代码质量工具链完善
- **部署简便**: 尽量减少外部依赖，便于内网部署
- **原生桌面体验**: GUI 需承载八大功能模块，要求原生窗口性能与系统集成能力

## 4. 技术选型

### 4.1 CLI 框架: Click vs Typer vs argparse

| 维度 | Click | Typer | argparse |
|------|-------|-------|----------|
| 学习曲线 | 中等 | 低 | 低 |
| 功能丰富度 | 高 | 高（基于Click） | 中 |
| 类型注解支持 | 间接 | 原生 | 无 |
| 子命令组 | 原生支持 | 原生支持 | 需手动实现 |
| 社区生态 | 成熟 | 新兴 | 标准库 |
| 文档质量 | 优秀 | 优秀 | 一般 |

**决策: Click**

**理由**:
- Click 是 Typer 的底层，功能更稳定
- Click 的子命令组（@click.group）适合多技术栈插件架构
- Click 的 context 机制便于传递 workspace_root
- Rich 与 Click 集成良好

### 4.2 数据模型: Pydantic v2 vs dataclass vs attrs

| 维度 | Pydantic v2 | dataclass | attrs |
|------|-------------|-----------|-------|
| 类型验证 | 原生 | 无 | 需额外配置 |
| 序列化 | model_dump() | 需手动 | 需额外库 |
| 性能 | 高（Rust核心） | 高 | 高 |
| JSON Schema | 原生 | 无 | 无 |
| 学习曲线 | 中等 | 低 | 中等 |

**决策: Pydantic v2**

**理由**:
- 类型验证原生支持，减少运行时错误
- model_dump() 便于序列化（GUI Service 层返回 DTO）
- JSON Schema 生成便于接口文档
- pydantic-settings 复用配置管理

### 4.3 数据库: SQLite vs JSON file vs TinyDB

| 维度 | SQLite | JSON file | TinyDB |
|------|--------|-----------|--------|
| 查询性能 | 高（索引） | 低（全量加载） | 中 |
| 并发支持 | WAL模式 | 无 | 文件锁 |
| 依赖 | 标准库 | 标准库 | 第三方 |
| 事务支持 | 原生 | 无 | 无 |
| 数据量 | 大 | 小 | 中 |

**决策: SQLite (WAL 模式)**

**理由**:
- Python 标准库内置，无需额外依赖
- WAL 模式支持并发读，适合 GUI + CLI 同时访问
- 索引加速查询，项目数量大时性能稳定
- 事务支持保证数据一致性

### 4.4 GUI 框架: PySide6 vs pywebview vs tkinter（V2.0 新增）

| 维度 | PySide6 | pywebview | tkinter |
|------|---------|-----------|---------|
| 技术栈 | Qt (C++) | HTML/CSS/JS | Tcl/Tk |
| 原生桌面体验 | 优秀（窗口/菜单/托盘） | 一般（嵌入式 WebView） | 一般 |
| 授权协议 | LGPL（商用友好） | BSD-3 | PSF |
| 组件丰富度 | 极高（Qt 全套控件） | 依赖前端库 | 低 |
| 多角色适配 | 原生（QStackedWidget + Tab） | 需自实现路由 | 难 |
| 八大模块承载 | 强（QMainWindow + QSplitter） | 中（单 WebView 切换） | 弱 |
| 信号槽机制 | 原生（QObject.signal） | JS Bridge | command 回调 |
| 主题切换 | QSS（Qt Style Sheets） | CSS | tk_setPalette |
| 包体积 | 大（100MB+） | 小 | 小（标准库） |
| 测试支持 | pytest-qt | 需 Selenium | 难 |
| 生态成熟度 | 极高（Qt 30 年） | 中 | 高（标准库） |

**决策: PySide6**

**理由**:
- **原生桌面体验**: QMainWindow 提供原生窗口装饰、系统托盘、快捷键集成，符合内网工具使用习惯
- **LGPL 授权**: 商用友好，无 GPL 传染性，便于内网部署和二次开发
- **Qt 生态成熟**: 30 年工业级验证，控件丰富（QTableView/QTreeView/QStackedWidget），文档完善
- **承载八大模块**: QMainWindow + QSplitter + QStackedWidget 架构稳定承载项目列表/项目工作区/变更中心/规范中心/模板管理/报告中心/系统设置/对话框
- **多角色适配**: QStackedWidget + Tab 容器天然支持按角色切换可见页面，信号槽机制实现角色-Tab 映射
- **测试友好**: pytest-qt 提供 QTest 调用，支持 GUI 自动化测试（已在 dev 依赖中引入）
- **性能优势**: C++ 内核，渲染速度快，适合处理大量项目卡片和变更单列表
- **从 pywebview 迁移原因**: pywebview 在承载八大模块时出现路由复杂、JS Bridge 序列化开销大、多角色切换困难等问题，详见 7.1

### 4.5 模板引擎: Copier + Jinja2

| 维度 | Copier | Cookiecutter | Jinja2 |
|------|--------|--------------|--------|
| 增量更新 | 原生支持 | 不支持 | 需手动 |
| 问题交互 | 原生 | 原生 | 无 |
| 模板继承 | 支持 | 不支持 | 支持 |
| 社区活跃度 | 中 | 高 | 高 |

**决策: Copier + Jinja2**

**理由**:
- **增量更新**是核心需求：项目创建后可应用模板更新
- 问题交互（copier.yml）便于定义项目变量
- Jinja2 模板语法成熟，团队熟悉
- Copier 内部使用 Jinja2，二者协同无冲突

### 4.6 终端输出: Rich vs plain print

**决策: Rich**

**理由**:
- 表格输出美观（项目列表/变更单列表/检查结果）
- 彩色输出提升可读性（PASS/WARN/FAIL 状态）
- 进度条支持（扫描进度）

### 4.7 配置管理: pydantic-settings vs python-dotenv

**决策: pydantic-settings**

**理由**:
- 与 Pydantic v2 统一，类型安全
- 支持 .env 文件和环境变量
- 配置验证原生支持

- Repository 层封装 SQL，Service 层封装业务规则
- DB 初始化失败时，Service 层回退到文件系统扫描（见 main_window._init_db）


```
                             │

        ┌────────────────────┼────────────────────┐
        ▼                                          ▼
┌─────────────────────────┐              ┌─────────────────────────┐
│  STATE_WORKSPACE        │              │  STATE_GLOBAL（全局页）  │
│  ProjectWorkspaceView   │              │  GlobalView 子页         │

            │                            │  - TemplatePage         │

            │                            │  - SettingsPage         │
            └────────────────────────────┴─────────────────────────┘
```

**状态转换规则**:

| 当前状态 | 触发动作 | 目标状态 | QStackedWidget 索引 |
|---------|---------|---------|---------------------|
| STATE_HOME | 双击项目卡片 | STATE_WORKSPACE | 1 |
| STATE_HOME | 点击侧边栏"变更/规范/模板/报告/设置" | STATE_GLOBAL | 2-6 |
| STATE_WORKSPACE | 点击侧边栏"项目" | STATE_HOME | 0 |
| STATE_WORKSPACE | 点击侧边栏其他项 | STATE_GLOBAL | 2-6 |
| STATE_GLOBAL | 点击侧边栏"项目" | STATE_HOME | 0 |
| STATE_GLOBAL | 点击侧边栏其他项 | STATE_GLOBAL | 2-6 |

**设计理由**:
- **项目为中心**: 90% 日常操作围绕具体项目展开，STATE_WORKSPACE 是核心状态
- **三态而非自由路由**: 限制状态数量降低复杂度，避免 pywebview 时代的路由爆炸问题
- **侧边栏全局可见**: 任意状态均可一键切换，无需返回首页中转
- **QStackedWidget 索引固定**: 索引与侧边栏项一一对应，状态机转换即索引切换

### 5.4 多角色适配机制

支持 4 类角色，通过"角色-Tab 映射"机制按需呈现界面：

| 角色 | 关注点 | 可见 Tab（ProjectWorkspaceView） | 可见全局页 |
|------|--------|----------------------------------|-----------|
| PM（项目经理） | 项目全貌、变更进度、文档完整性 | 概览/变更/检查/文档（全部） | 全部 |
| PLC 工程师 | PLC 规范检查、变更执行 | 概览/检查/文档 | 规范中心/模板管理 |
| Python 工程师 | Python 规范检查、变更执行 | 概览/检查/文档 | 规范中心/模板管理 |
| SpecEditor（规范编辑者） | 规范维护、模板更新 | 概览/文档 | 规范中心/模板管理/报告中心 |

**实现机制**:

```python
# 角色定义（伪代码，实际位于 ui/models 或 core/role_service）
class Role(Enum):
    PM = "pm"
    PLC_ENGINEER = "plc"
    PYTHON_ENGINEER = "python"
    SPEC_EDITOR = "spec_editor"

# 角色-Tab 映射表
ROLE_TAB_MAP: dict[Role, list[str]] = {
    Role.PM: ["overview", "change", "check", "doc"],
    Role.PLC_ENGINEER: ["overview", "check", "doc"],
    Role.PYTHON_ENGINEER: ["overview", "check", "doc"],
    Role.SPEC_EDITOR: ["overview", "doc"],
}

# 应用角色过滤
def apply_role_filter(workspace_view: ProjectWorkspaceView, role: Role) -> None:
    """根据角色隐藏不可见 Tab"""
    visible_tabs = ROLE_TAB_MAP.get(role, [])
    for tab_id, tab_widget in workspace_view.tabs.items():
        tab_widget.setVisible(tab_id in visible_tabs)
```

**设计理由**:
- **同一界面按角色裁剪**: 避免为每类角色开发独立界面，降低维护成本
- **角色切换零成本**: 切换角色即重新应用过滤，无需重启
- **权限边界清晰**: Tab 可见性是 UI 层裁剪，Service 层不做角色鉴权（内网工具信任用户）
- **可扩展**: 新增角色只需在 ROLE_TAB_MAP 添加映射，无需改 UI 代码

## 6. 数据真源策略（V2.0 新增）

### 6.1 三源并存设计

| 真源 | 路径 | 职责 | 写入方 | 读取方 |
|------|------|------|--------|--------|
| .copier-answers.yml | 项目根目录 | 项目元数据真源 | Copier(创建时)、auto-pm edit(更新时) | project list/show、技能 |
| PM_SESSION_*.md | 项目根目录 | 项目管理真源 | pm-workflow技能、auto-pm init | pm-workflow/plc-electrical-engineer/fullstack-engineer |
| .auto-pm/index.db | 工作空间根 | 索引缓存（可重建） | auto-pm sync | GUI优先读取 |

### 6.2 同步规则

1. **.copier-answers.yml → DB**: sync 时解析 .copier-answers.yml，更新 projects 表
2. **PM_SESSION → DB**: sync 时解析 PM_SESSION frontmatter，更新 projects 表的 phase 字段
3. **变更单文件 → DB**: sync 时解析 CHG-*.md 文件，更新 change_requests 表

### 6.3 冲突处理

- **.copier-answers.yml 与 PM_SESSION 冲突**: 以 .copier-answers.yml 为准（项目元数据真源）
- **DB 与文件系统冲突**: 以文件系统为准（DB 是缓存）
- **强制全量同步**: sync(force_full=True) 忽略 mtime，全量重建

### 6.4 双模式读取

ProjectService 同时支持两种读取模式，由是否注入 DatabaseManager 决定：

```python
class ProjectService:
    def __init__(self, workspace_root: str, db: DatabaseManager | None = None) -> None:
        self.workspace_root = os.path.abspath(workspace_root)
        self.db = db
        self._repo = ProjectRepository(db) if db else None

    def list_projects(self, scan_depth: int = 4) -> list[ProjectInfo]:
        """文件系统扫描模式（无 DB 或强制刷新时）"""
        ...

    def list_projects_cached(self) -> list[ProjectInfo]:
        """DB 缓存模式（GUI 默认）"""
        if self._repo is None:
            raise RuntimeError("未注入 DatabaseManager，无法使用缓存模式")
```

**MainWindow 初始化策略**（`main_window._init_db`）:
- DB 初始化成功 → 使用缓存模式，性能优
- DB 初始化失败 → 回退到文件系统扫描，功能不丢失

## 7. 关键技术决策

### 7.1 pywebview → PySide6 迁移

**背景**: V1.0.0 草稿选择 pywebview，V2.0.0 迁移到 PySide6。

**迁移原因**:

| 问题维度 | pywebview 表现 | PySide6 解决方案 |
|---------|---------------|-----------------|
| 八大模块承载 | 单 WebView 路由复杂，状态管理混乱 | QMainWindow + QStackedWidget 索引切换，状态机清晰 |
| 多角色适配 | 前端需自实现角色路由，重复逻辑 | QStackedWidget + Tab 可见性，原生支持 |
| JS Bridge 开销 | 序列化/反序列化开销大，大数据量卡顿 | 直接 Python 对象传递，无序列化 |
| 前后端通信 | JS Bridge 异步回调，调试困难 | Qt 信号槽同步/异步皆可，类型安全 |
| 测试支持 | 需 Selenium，CI 集成难 | pytest-qt 原生支持，已纳入 dev 依赖 |
| 原生体验 | WebView 嵌入，窗口装饰受限 | QMainWindow 原生窗口，系统集成完整 |
| 主题切换 | CSS 实现，但与系统主题不一致 | QSS + Qt 主题，与系统一致 |

**迁移决策**:
- 保留 pywebview 在 dependencies 中作为兼容依赖（过渡期）
- 新功能全部基于 PySide6 开发
- pywebview 相关代码（gui/api.py、前端资源）逐步废弃
- V2.1.0 计划移除 pywebview 依赖

**迁移收益**:
- UI 响应速度提升约 3 倍（无 JS Bridge 序列化）
- GUI 自动化测试覆盖率从 0 提升到目标 60%
- 八大模块切换无白屏，状态保持完整

### 7.2 增量扫描策略

#### 7.2.1 设计目标

- 避免全量扫描开销（工作空间可能有数十个项目）
- 保证缓存与文件系统一致性
- 支持 GUI 快速刷新

#### 7.2.2 file_mtime 判据

**原理**: 每个项目的标志文件（.copier-answers.yml / .plc.json / PM_SESSION_*.md）的修改时间（mtime）作为缓存有效性判据。

**扫描流程**:

```
1. 扫描文件系统，获取所有项目的标志文件 mtime
2. 查询 DB 缓存，获取已缓存项目的 file_mtime
3. 对比 mtime:
   - mtime 相同: 跳过（缓存有效）
   - mtime 不同: 重新解析并更新缓存
   - DB 有但文件系统无: 从缓存删除
   - 文件系统有但DB无: 新增到缓存
4. 记录扫描日志到 scan_log 表
```

#### 7.2.3 SyncService 设计

```python
class SyncService:
    def sync(self, force_full: bool = False) -> dict[str, Any]:
        """增量同步文件系统到 DB

        Args:
            force_full: True 强制全量扫描（忽略 mtime 判据）

        Returns:
            {projects_found, changes_found, duration_ms, status}
        """
```

#### 7.2.4 缓存一致性保证

- **写入时更新**: Service 层修改项目/变更单后，同步更新 DB 缓存
- **读取时校验**: GUI 读取缓存时，可选校验 mtime
- **手动同步**: GUI 工具栏提供"同步缓存"按钮，调用 sync(force_full=True)
- **DB 可重建**: index.db 是缓存非真源，删除后可重建

### 7.3 路径安全

#### 7.3.1 path_resolver 设计

**文件**: `auto_pm/change/path_resolver.py`

**功能**: 解析变更单文件路径，防止目录遍历攻击

**安全校验规则**:

1. **路径必须在 workspace_root 下**:
   ```python
   def resolve_change_path(workspace_root: str, project_id: str, change_number: str) -> Path:
       workspace = Path(workspace_root).resolve()
       target = (workspace / "04_变更管理" / f"{change_number}.md").resolve()
       if not str(target).startswith(str(workspace)):
           raise ValueError("路径越界: 不允许访问工作空间外的文件")
       return target
   ```

2. **项目编号格式校验**:
   - 必须匹配 `^[A-Z]{2,4}-\d{4}-\d{3}$`
   - 防止 `../` 注入

3. **变更单编号格式校验**:
   - 必须匹配 `^CHG-[A-Z]{2,4}-\d{4}-\d{3}$`
   - 防止 `../` 注入

4. **文件名安全**:
   - 禁止包含 `..`、`/`、`\` 等路径分隔符
   - 禁止以 `.` 开头（隐藏文件）

#### 7.3.2 攻击防护

| 攻击类型 | 防护措施 |
|---------|---------|
| 目录遍历 | Path.resolve() + startswith 校验 |
| 路径注入 | 正则校验 project_id/change_number 格式 |
| 符号链接攻击 | Path.resolve() 解析符号链接 |
| 文件名注入 | 禁止路径分隔符 |

### 7.4 编码崩溃修复方案（V2.0.1 新增）

**问题**: Windows GBK 环境下 `python -m auto_pm` 因 site 模块初始化失败而崩溃

**根因**: `.venv/Lib/site-packages/` 下存在含非 UTF-8 字节的 `.pth` 文件，Python site 模块默认使用系统编码（GBK）读取，导致 `UnicodeDecodeError` 崩溃

**方案**: 在 `__main__.py` 入口点强制设置 `PYTHONUTF8=1`，或在 pyproject.toml 的 `[project.scripts]` 入口点添加 UTF-8 强制初始化逻辑

**备选**: 排查 .venv/Lib/site-packages/ 下 .pth 文件中的非 UTF-8 字节，修复或删除问题 .pth 文件

**影响范围**: 所有 Windows 中文环境用户

### 7.5 检查器深度增强方案（V2.0.1 新增）

**问题**: plc check 仅验证文件存在性，不验证内容实质化

**方案**: 新增"文档实质化"检查项，扫描"待填写"/"待定义"等占位符比例

**阈值规则**:
- 占位符比例 > 70%: FAIL
- 占位符比例 30%~70%: WARN
- draft lifecycle 规范: WARN

**扩展规则**:
- 必填字段（REQ §3.1/§4.1）存在占位符: 直接 FAIL（不按比例判断）

**实现位置**: `auto_pm/plc/checker.py` 新增 `SubstanceChecker` 类

### 7.6 042/016 规范对齐技术决策（V2.0.2 新增）

**背景**: PM-042 V2.3.0 状态机定义 12 个状态（含 `archived`），PM-016 V1.1.0 定义 PLC/Python 两套变更管理目录路径，auto-pm 代码存在 19 项冲突。

**状态机对齐决策**:

| 决策点 | 方案 | 理由 |
|--------|------|------|
| `archived` 状态定义 | 添加到 `ChangeStatus` Literal + `STATUS_FLOW` + `STATUS_LABELS` | 对齐 PM-042 V2.3.0 §5.2 |
| `archived` 门禁 | 仅 `completed` 状态可归档 | 归档是已完成变更的后续操作 |
| `rejected→draft` 门禁 | 必须附 comment（修改原因） | 驳回后重新起草需记录原因 |
| `conditionally_approved→implementing` 门禁 | 必须附 comment（条件确认说明） | 有条件批准进入实施需确认条件已满足 |
| 审批环节名称 | 使用中文语义化标签（对齐 `STATUS_LABELS`） | 替代英文大写 `APPROVED/REJECTED` |

**状态推断优先级**（`parser.py._infer_status_from_approval`）:

```
驳回/拒绝 > 有条件通过 > 通过
```

**理由**: `☑通过` 是 `☑有条件通过` 的子串，必须先检查 `有条件通过` 再检查 `通过`，否则会误匹配。

**`archived` 状态推断说明**: `archived` 无法从审批章节推断（归档是验收后操作），需依赖 §3.4 变更状态字段显式读取。

### 7.7 Python 项目双路径搜索策略（V2.0.2 新增）

**背景**: PM-016 V1.1.0 定义 PLC 和 Python 项目使用不同的变更管理目录路径。

| 项目类型 | 变更管理目录 | 台帐目录 |
|---------|-------------|---------|
| PLC | `00_项目管理/04_变更管理/01_变更单/` | `00_项目管理/04_变更管理/04_变更记录/` |
| Python | `01_项目文档/03_执行过程/02_变更管理/01_变更单/` | `01_项目文档/03_执行过程/02_变更管理/04_变更记录/` |

**搜索策略**: 优先匹配已有目录

```python
_CHANGE_FILE_SEARCH_PATHS = [
    os.path.join("00_项目管理", "04_变更管理", "01_变更单"),  # PLC
    os.path.join("01_项目文档", "03_执行过程", "02_变更管理", "01_变更单"),  # Python
]

def _get_change_file_path(self, project_path, change_number):
    for rel_path in self._CHANGE_FILE_SEARCH_PATHS:
        base_dir = os.path.join(project_path, rel_path, f"CHG-{domain}")
        if os.path.isdir(base_dir):  # 优先匹配已有目录
            return os.path.join(base_dir, f"{change_number}.md")
    # 未匹配 → 默认使用 PLC 约定路径（新项目创建）
    return os.path.join(project_path, "00_项目管理", ...)
```

**设计理由**:
- **优先匹配已有目录**: 自动识别项目类型，无需显式传入 `stack` 参数
- **默认 PLC 路径**: 未匹配时使用 PLC 约定路径，因为 PLC 项目是主要使用场景
- **台帐同步**: `find_ledger_file` 采用相同策略，支持 PLC/Python 双路径台帐搜索

**影响范围**: `_get_change_file_path`、`_find_change_file`、`find_ledger_file` 三个函数
