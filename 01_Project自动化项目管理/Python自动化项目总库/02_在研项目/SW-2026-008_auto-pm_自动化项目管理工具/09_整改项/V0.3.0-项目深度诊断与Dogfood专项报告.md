## 1. 诊断结论摘要

本项目当前**不是“没有计划”**，而是进入了一个更危险的阶段：**代码、文档、计划、dogfood 闭环都各自有进展，但它们已经不再指向同一个事实基线**。

综合代码、文档、结构和实际命令核查，当前结论如下：

1. **代码本体质量明显提升**：项目已经具备较完整的分层结构、较高测试密度、明确的技术债清理轨迹，`auto_pm` 已经不是早期原型，而是可持续演进的产品雏形。
2. **项目管理真源发生分叉**：`PM_SESSION`、`.trae/specs/v2.1-change-management-enhancement/`、`docs/里程碑迭代计划_V2.1.md`、根目录 `里程碑迭代计划_V2.1.md` 四套文档对“当前进度”和“下一步计划”的描述互相冲突。
3. **dogfood 已经开始，但还不够“产品级”**：项目确实完成了一次自身变更流程演练，并且发现了真实产品缺陷；但缺陷没有被正式编排进唯一执行计划，说明 dogfood 还停留在“发现问题”，没有完全进入“制度化持续闭环”。
4. **存在真实产品可用性问题**：至少有 3 个问题不是文档不同步，而是会直接影响使用者体验或项目可信度。
5. **下一步计划需要修订，不建议原样照单推进**：不是推翻 V0.3.0 / V2.1 路线，而是需要先做一次“计划真源收口 + dogfood 缺陷入图 + 元数据真源修复”。

一句话判断：

> `auto-pm` 已经具备继续向 V0.3.0 / V2.1 推进的条件，但在进入 M1/M2/M3 前，必须先解决“计划真源冲突”和“dogfood 暴露出的产品级断点”，否则后续里程碑会继续在失真的基线上推进。

## 3. 项目现状总评

### 3.1 优势面

当前项目已经具备以下成熟特征：

- 包结构清晰：`cli / core / change / db / plc / ui / models / config / logging / utils` 分层明确。
- 核心服务抽象已经成型：`ProjectService`、`ProjectScanner`、`ChangeService`、`PlcService`、`SyncService` 的职责边界总体合理。
- 变更管理能力已经不只是“能生成 Markdown”，而是包含状态机、门禁、解析、更新、索引、GUI 入口和测试。
- 测试文化比多数内部工具成熟：技术债报告、元测试、ruff、mypy、pytest、GUI 测试、端到端验证都已进入常规话语体系。
- 文档体系比较完整：PRD、INT、DSN、TEC、CHG、PM_SESSION、spec/tasks/checklist、README 都存在且内容密度较高。

### 3.2 风险面

项目的主要风险已经从“不会做”转向“做得很多但真源失真”：

- 代码进度和文档进度并不同步。
- 不同文档对当前状态的判定互相冲突。
- dogfood 暴露出的问题没有完全进入后续里程碑编排。
- 自身作为 Python 项目的元数据治理还不够稳定，已经影响 `project show/list` 的真实输出。

这意味着：

> 现在最大的敌人不是技术实现难度，而是“团队会以为已经进入下一阶段，但底座事实并没有统一”。

## 4. 严重问题清单

以下问题按严重程度排序。

### P0-1 计划真源冲突，当前没有唯一可信执行面

这是当前最严重的问题。

存在至少四套互相冲突的状态描述：

- `PM_SESSION_SW-2026-008.md`：明确写的是 **V0.3.0 M0 已完成，M1/M2/M3 待启动**。
- `.trae/specs/v2.1-change-management-enhancement/spec.md`：写成 **M1-M4 已完成**。
- `.trae/specs/v2.1-change-management-enhancement/tasks.md`：又写成 **大批任务尚未勾选**。
- `docs/里程碑迭代计划_V2.1.md`：写成 **27/27 已完成**。
- 根目录 `里程碑迭代计划_V2.1.md`：又仍是 **27 项待开始**。

这不是普通的文档过时，而是“多个真源同时有效”的状态。

直接后果：

1. 无法判断下一步应该执行 M1，还是已经进入 M2/M3 收尾。
2. 无法判断哪些事项是真未做，哪些只是文档未同步。
3. 任何版本号、测试数、交付声明都可能继续漂移。

结论：

> 在当前状态下，任何继续往 M1/M2/M3 推进的动作，都有较大概率建立在错误基线之上。

### P0-2 Python 项目元数据真源与扫描器约定不一致，直接影响 `project show/list`

本次实测中执行：

```powershell
auto-pm -w "c:\Users\fubai\Desktop\My_Workspace" project show SW-2026-008
```

输出显示：

- `版本` 为空
- `阶段` 为空
- `描述` 为空

但项目根目录 `.copier-answers.yml` 实际存在：

- `project_name: auto-pm`
- `project_description: 自动化项目管理工具 - 统一CLI管理PLC/Python多技术栈项目`

根因分析：

1. `ProjectScanner.read_copier_answers()` 读取的是：
   - `version`
   - `description`
   - `phase`
2. 当前项目 `.copier-answers.yml` 中却使用了：
   - `project_description`
   - 且没有 `version`
   - 且没有 `phase`
3. 这导致扫描器能识别项目，但不能读到完整元数据。

这会带来两个后果：

1. CLI 使用者看到的项目信息失真。
2. GUI 项目卡片、列表、搜索、筛选的可信度下降。

这不是小瑕疵。对于一个“项目管理工具”来说，**自身项目元数据都无法稳定读取**，会直接削弱 dogfood 说服力。

### P0-3 dogfood 发现了真实缺陷，但没有正式编入唯一执行计划

当前 dogfood 已发现并记录：

- `BUG-001`：`verification_conclusion` 必须等于字面量“全部通过”
- `BUG-002`：台帐路径解析错误 / 中文路径导致异常

问题不在于“没发现 bug”，而在于：

1. 缺陷已经被写进 `PM_SESSION`、`CHG`、技术债报告；
2. 但它们没有被稳定映射进唯一的 M1/M2/M3 任务图；
3. 结果就是 dogfood 变成“发现问题的证明”，还没成为“驱动迭代的制度”。

这意味着 M4 Dogfooding 持续化虽然被写进了计划，但机制尚未真正落地。

### P1-1 dogfood 相关计划中存在“计划指向不存在或未实现能力”的现象

在 `.trae/specs/v2.1-change-management-enhancement/tasks.md` 中，M4 明确写到：

- 使用 `auto-pm change ledger` 创建版本变更台帐

但当前 `auto_pm/cli/change.py` 中实际只存在 4 个命令：

- `list`
- `show`
- `create`
- `transition`

也就是说，计划已经引用了一个**当前并不存在的 CLI 能力**。

这类问题非常关键，因为它说明：

> 当前计划文档已经开始脱离代码现实，自我引用一个还没实现的工具能力。

### P1-2 Python 项目的台帐创建路径仍偏 PLC 约定，跨栈 dogfood 仍不稳

`auto_pm/change/path_resolver.py` 中 `get_or_create_ledger_file()` 的逻辑是：

- 先查找已有台帐；
- 如果不存在，则**固定按 PLC 约定路径**创建：
  - `00_项目管理/04_变更管理/04_变更记录/01_版本变更台帐.md`

但同文件又已经定义了 Python/通用项目的搜索路径：

- `01_项目文档/03_执行过程/02_变更管理/04_变更记录`

这说明：

1. 代码在“查找”时承认 Python/通用项目路径；
2. 但在“自动创建”时仍默认 PLC 路径；
3. 这对 Python 项目的自用闭环会造成路径风格不一致。

这和 BUG-002 指向的是同一类问题：**跨技术栈路径约定还没有完全收口**。

### P1-3 验收门禁过硬编码，dogfood 体验不友好

`auto_pm/change/change_service.py` 对 `completed` 状态的前置门禁是：

```text
verification_conclusion 必须等于 "全部通过"
```

这会导致：

- 使用者无法写“全部通过（附说明）”
- 无法写“通过，存在观察项”
- 无法保留真实验收语义

这不是单纯的参数限制，而是**产品表达能力过窄**。

从项目经理和电气工程师视角看，这个问题会让真实验收记录变得不自然，最后逼着人去写“迎合工具的话”，而不是写“真实结果”。

### P1-4 版本号和阶段状态没有真正完成四端统一

当前可见状态为：

- `pyproject.toml`：`0.2.3`
- `CHANGELOG.md`：最新条目 `[0.2.3]`
- `PRD`：`V2.0.3`
- `PM_SESSION`：当前焦点已经写到 `V0.3.0 / V2.1.0`
- `CHG`：映射表中写了 `0.3.0 / V2.1.0 / V0.3.0（开发中）`

这说明：

1. 目标版本已在项目管理层面上抬升；
2. 但产品版本真源尚未同步完成；
3. 文档里已经开始混用“当前值”和“目标值”。

因此当前最准确的说法应当是：

> 项目正在从 `0.2.3 / V2.0.3` 向 `0.3.0 / V2.1.0` 过渡，但尚未完成正式版本切换。

而不是直接按“已进入 0.3.0”对外叙述。

## 5. Dogfood 专项诊断

## 5.1 已经做对了什么

本项目在 dogfood 上，已经做对了三件非常重要的事：

1. **真的用自己的变更单能力管理了自己**
   - `CHG-SCPT-2026-001.md` 不是样板，而是真实演练件。
2. **走过了完整生命周期**
   - 从 `draft` 到 `closed` 的链路已经跑通。
3. **不是“演示通过”，而是“演练出 bug”**
   - 这说明本次 dogfood 具备真实性，而不是只跑 happy path。

从产品成熟度角度，这一步非常重要。

因为很多内部工具失败，不是因为没有测试，而是因为**从来没有让工具真的服务于自己**。

## 5.2 还没做透的地方

当前 dogfood 仍有四个薄弱点：

### 1. 只有“一次样板闭环”，还不是“每次迭代必经机制”

虽然 `PM_SESSION` 已经写到：

- 每个里程碑完成后创建对应 `CHG-SCPT-2026-XXX.md`

但当前实际可见的仍然只有：

- `CHG-SCPT-2026-001.md`

这说明 dogfood 还处于单次验证阶段，还没有形成制度化节奏。

### 2. 缺陷发现和里程碑拆解之间没有强绑定

BUG-001 / BUG-002 已被发现，但没有清晰回答：

- 属于 M1 结构修正？
- 属于 M2 持久化？
- 属于 M3 GUI 增强？
- 还是应该新增一个 M0.5 / M1a？

这会导致缺陷虽然“被记录”，却不一定“被完成”。

### 3. dogfood 对象还是偏开发者视角

目前的 dogfood 核心演练点主要是：

- 状态流转
- 解析
- 台帐
- 验证结论

但从“电气工程师兼项目经理”的真实使用视角，还缺少以下问题的系统检查：

- 项目列表信息是不是一眼可信
- 新建变更单时字段是否自然
- 路径和台帐是不是跨 PLC/Python 都顺手
- 看板/列表/详情/审批记录是否真正减少管理成本

换句话说，当前 dogfood 偏“功能正确性”，还不够“工作流舒适性”。

### 4. dogfood 与发布门禁没有完全绑定

当前文档里多处强调：

- 版本号四端统一
- CHG 生命周期走完
- 测试全绿

但尚未看到一个真正强制的“发布门禁清单”，明确规定：

只有满足哪些项，才能宣布某里程碑完成。

如果没有这个门禁，dogfood 容易被当成“建议动作”，而不是“发布前必要动作”。

## 6. 对下一步计划的判断

## 6.1 当前计划是否需要推翻

**不需要推翻。**

V0.3.0 / V2.1 的主方向基本正确：

- M1：变更单结构修正
- M2：影响分析与审批记录持久化
- M3：GUI 变更管理增强

这个方向与当前产品短板是匹配的。

## 6.2 当前计划是否需要完善

**需要，而且是明显需要。**

至少应补 4 个内容：

### A. 增加“真源收口”前置动作

在 M1 前新增一个前置批次，建议命名：

- `M0.5 真源收口`

包含：

1. 明确当前唯一执行真源文档；
2. 归档或标记另外 2-3 份冲突计划文档；
3. 统一当前“实际状态”与“目标状态”的写法；
4. 明确哪些条目是已完成、哪些是待完成、哪些只是历史计划。

### B. 将 dogfood 缺陷正式映射到任务图

建议补充：

- `BUG-001` 归属 `M1` 或 `M2`
- `BUG-002` 归属 `M0.5` 或 `M1`
- `metadata 真源修复` 单列为一个明确任务
- `ledger CLI 能力缺口` 明确写成“实现”或“从计划移除”

### C. 将“元数据真源修复”提升为产品级任务

建议新增任务：

- 统一 Python 项目 `.copier-answers.yml` 字段契约
- 明确 `description / project_description` 的兼容策略
- 明确 `version` 的读取优先级
- 明确 `phase` 缺省值策略

因为这直接影响 `project list/show`、GUI 卡片、搜索和导入后的可信度。

### D. 把 dogfood 从“行为”升级为“门禁”

建议新增一个固定发布门禁章节：

- 变更单已创建并能被 `change list/show` 正确读取
- 至少走完一次核心生命周期
- 关键缺陷有记录、有归属、有状态
- 版本号四端一致
- 发布结论不是口头声明，而是有证据落点
