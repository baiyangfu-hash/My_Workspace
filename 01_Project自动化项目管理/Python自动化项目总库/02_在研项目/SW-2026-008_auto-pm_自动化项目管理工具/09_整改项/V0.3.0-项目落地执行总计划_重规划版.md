## 1. 结论先行

基于实际代码、现有文档、`09_整改项` 存量资料和本次 CLI 实测，当前最合理的推进方式不是：

- 直接按旧计划进入 `M1 章节结构修正`
- 然后继续 `M2 持久化`
- 再推进 `M3 GUI 增强`

而应该改成下面的主线：

1. **先收口真源**
2. **先修复产品自洽与 dogfood 暴露出的真实断点**
3. **先做到“能稳定自用”**
4. **再推进结构增强、持久化和 GUI 提升**
5. **最后做内部试运行和正式发布准备**

换句话说：

> 当前项目已经不是“功能不够多”，而是“现实状态、文档状态、计划状态和产品行为状态不在同一平面上”。  
> 所以第一优先级必须是“把平面拉齐”，不是继续往下堆功能。

## 9. Phase 4 M2 重构版：必要持久化

### 9.1 原则

这一阶段不做“为了架构好看而持久化”，只做对真实使用有价值的持久化。

### 9.2 本阶段建议只保留 3 类持久化

#### P4-01 审批记录持久化

- 原因：
  - 审批记录是项目经理最关心的追溯信息
- done_when：
  - 每次状态流转都能追溯审批人、意见、时间

#### P4-02 影响分析持久化

- 原因：
  - 影响范围、风险等级、缓解措施、传播链后续都要复用
- done_when：
  - 文件与 DB 至少在关键字段上同步

#### P4-03 解析到持久化结构的转换层

- 原因：
  - 避免 GUI 和后续统计直接依赖 Markdown 正则
- done_when：
  - parser 可稳定产出可落库结构

### 9.3 暂缓项

以下内容不作为 Phase 4 必须项：

- 为所有章节做过度结构化
- 做复杂迁移框架
- 做与当前使用场景无关的扩展表

### 9.4 验收门禁

- 至少有审批历史和影响分析两类数据可追溯
- 文件读写与 DB 持久化不冲突
- 状态流转、查看详情、后续 GUI 展示具备稳定数据来源

### 9.5 建议周期

- `1 ~ 2 天`

## 10. Phase 5 M3 重构版：GUI 变更管理增强

### 10.1 原则

GUI 不追求一次做全，先做真实会被使用的 3 类能力。

### 10.2 必做能力

#### P5-01 编辑变更单

- 目标：
  - GUI 可以改背景、必要性、参考依据、计划日期、紧急程度、关键影响分析字段
- done_when：
  - 使用者不必回退到手改 Markdown

#### P5-02 审批时间线

- 目标：
  - 项目经理一眼看到审批流转历史
- done_when：
  - 审批记录在 GUI 中可见且可理解

#### P5-03 列表筛选增强

- 目标：
  - 按状态、领域、项目、紧急程度筛选
- done_when：
  - 变更列表从“能看”变成“能管理”

### 10.3 可延期能力

以下内容不是 V0.3.0 的硬门槛，可排在后面：

- 高复杂度传播链图形化
- 过度炫技的可视化状态机
- 大范围 UI 重构

### 10.4 验收门禁

- 至少 1 个真实项目可通过 GUI 完成变更查看与编辑
- 审批时间线可用
- 列表筛选可用
- GUI 新能力不破坏现有 CLI 主路径

### 10.5 建议周期

- `1 ~ 2 天`
