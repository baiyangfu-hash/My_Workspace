## 4. 变更原因

**变更背景**:
DJ 模板（`plc-standard-project`）以 `DJ-2026-005` 标杆为蓝本重塑为“结构体整块传递 + 单一真源方案层 + 11页高保真 HMI 点表映射”后，驾驶舱的代码生成器（`generator.py`）、智能修复器（`repairer.py`）、语法分析器（`scl_linter.py`）及原型服务（`prototype_service.py`）需要同步跟进全面升级。

**变更必要性**:
1. **代码生成器架构落后**: 原代码生成器仍生成散装引脚代码，不支持结构体整块传递与 UDT 自动生成；
2. **智能修复器未覆盖新标准**: 无法自动收敛历史 `程序文档/` 至 `00_程序方案/`，缺少 `hmi_tag_mapping.json` 自动补齐；
3. **SCL Linter 存在误报**: 解包临时变量与结构体参数易触发命名警告；
4. **原型点表缺乏双向校验**: 需打通 HTML 原型 Tag、映射字典与 PLC DB 的闭环。

**参考依据**:
- `DEV-300` (Google SRE 可靠性规范)
- `LSP-905~908` (西门子 SCL 扩展生态标准)
- `PM-042 / PM-033` (变更管理与功能迭代流程)

## 5. 变更内容

### 5.1 变更前 (当前状态)
- SCL 代码生成器只支持生成单文件散装引脚代码；
- PLC 修复器仅修复旧版 4 件套，不处理 `00_程序方案/` 与 `hmi_tag_mapping.json`；
- SCL Linter 对结构体解包变量存在前缀误报；
- Prototype 检查器仅静态扫描 HTML 寄存器数量。

### 5.2 变更后 (目标状态)
- SCL 代码生成器支持生成基于 `VAR_IN_OUT io_st<Module>` 的 FB 与 `ST_<Module>` UDT；
- PLC 智能修复器支持自动迁移旧程序文档至 `00_程序方案/` 并补齐点表字典与 PRD 四件套；
- SCL Linter 全面识别结构体语法并消除解包误报；
- Prototype 服务实现 HTML Tag $\leftrightarrow$ 映射字典 $\leftrightarrow$ PLC 数据块三维对账。
