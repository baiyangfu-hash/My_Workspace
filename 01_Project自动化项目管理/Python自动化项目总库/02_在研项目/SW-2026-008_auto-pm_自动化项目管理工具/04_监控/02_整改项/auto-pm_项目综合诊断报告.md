## 一、项目是什么

**auto-pm** 是一个统一 CLI（+ PySide6/QML 桌面 GUI）工具，用于管理"PLC + Python 多技术栈项目"的工作空间，面向电气自动化工程师。核心能力：

- 项目全生命周期管理（新建/查看/编辑/删除/导入，基于 Copier 模板）
- PLC 项目规范检查与自动修复（LSP-907 规范）
- **变更管理**：12 状态机 + 门禁校验的完整变更单（CHG-*.md）流程，CLI 和 GUI 双通道
- 全局 Modbus TCP 联调工坊（读写功能码测试、波形趋势、并发扫描）
- SQLite 索引缓存加速查询 + 文件监听自动同步
- 桌面 GUI：项目中心式导航、变更中心可视化状态机/审批时间线/传播链
- 约束工作流引擎（自愈式流程守护，强制自身遵守 dogfooding 规则）

技术栈：Click + Rich（CLI）、Pydantic v2、PySide6 QML（GUI）、SQLite（WAL）、Copier+Jinja2（模板）、ruff + mypy(strict) + pytest（质量门禁）。

产品定位（引自 PRD）：**"界面层、业务层、项目数据层分离，通过稳定的变量/命令接口连接"**——把 PLC/HMI 的设计哲学搬到了软件架构上。五层架构：CLI/GUI → Application Facade → Core Service → DB Repository → Models。

## 二、诊断结论

### 2.1 总体评价

代码本身和质量门禁的严谨程度，在同类个人/小团队维护的工具里非常罕见：

- 最近一次全量回归（2026-07-25）：**1514 passed，2 skipped，0 failed**；CLI 测试 123 passed；GUI 可见模式集成测试 13 passed。
- mypy strict 模式下 149 个源文件 0 errors；ruff 基本 0 errors。
- 每一次改动都通过 `CHG-*.md` 变更单走完整闭环（draft → submitted → approved → implementing → completed → closed），**已闭环 72+ 次**（"dogfooding"，即工具管理自己的开发过程）。
- `PM_SESSION_SW-2026-008.md` 作为单一状态真源，记录每次迭代的三轨门禁结果（ruff / mypy / pytest）。

但深入代码和整个工作空间的实际使用痕迹后，发现**真正的风险不在代码质量，而在"验证"这一环缺失**——详见 2.3。

### 2.3 深层问题（源码 + 工作空间实际使用痕迹）

这一部分是通过实际 clone 代码、遍历整个工作空间的真实项目目录（而不只是读 auto-pm 自己的文档）得出的结论，是本报告最核心的发现。

#### 发现 1：真实项目几乎没有被这个工具接管

遍历整个工作空间 `0100_PLC自动化/` 目录，带 `.copier-answers.yml`（即真正被 auto-pm `project create`/`import` 纳管的标志文件）的项目**只有两个测试套件项目**（DJ-2026-097、DJ-2026-098）。而 PM_SESSION 里反复作为"真实项目验证依据"提及的 **DJ-2026-005**，以及 **DJ-2026-000**，都没有这个文件——它们不是被 auto-pm 创建或接管的，仍在用工具之外的方式管理。

也就是说，工具的项目管理能力目前主要是"在自己身上练手"，尚未在电气工程师日常维护的真实项目上跑起来。

#### 发现 2：版本号在往前走，但 PRD 自己定义的"验证"里程碑从未启动

PRD 自带的 30 周里程碑计划里：

| 里程碑 | 目标 | 状态 |
|--------|------|------|
| M6（Week 19-21） | 性能验证（FPS/内存/耗时基线） | ⏸ 未开始 |
| M7（Week 22-24） | 真实试用第一轮 | ⏸ 未开始 |
| M8（Week 25-27） | 问题闭环 + 可选 Web 评估 | ⏸ 未开始 |
| M9（Week 28-30） | V1.0 收口 | ⏸ 未开始 |

按计划，应该先完成 M6-M9 的验证工作再对外宣布 V1.0。但实际发生的是：中途插入了一条独立的"HTML 原型 V7 四阶段"专项（CHG-102~107），做完视觉重构后**直接把 pyproject 版本号打到了 V1.0.0**，随后又完成 Modbus 联调工坊、约束工作流引擎等新功能，把版本号推进到 V1.1.0。**M6/M7/M8 这几个"验证"里程碑被绕过了，版本号却一路向前**——目前的"发布"状态本质上是自我认定的，尚未经过真实使用场景检验。

#### 发现 3：治理系统本身在变成一个需要被治理的对象

`auto_pm/constraint/`（checker / guard / healer / workflow 四个模块）是近期新加的一套"自愈约束工作流引擎"，专门用来强制项目自己遵守自己定义的 CHG 流程。对照 PM_SESSION 的完成记录，可以看到相当比例的变更单在"修正流程自己"：

- CHG-SCPT-2026-135："PM_SESSION 真源同步"
- CHG-SCPT-2026-139：本身质量有问题，又出了一次"CHG-139 闭环质量回修"
- CHG-SCPT-2026-142/143：修的是测试断言数量没跟上约束定义数量的变化

这些改动不是面向电气工程师的功能价值，而是治理系统在自我维护。"72 次 dogfooding 闭环"是一个听起来很扎实的数字，但相当一部分闭环内容属于"流程为了合规而合规"，稀释了这个指标本该代表的信号。

此外，M5（Bridge 收口）早已被标记"已完成"，但 `system_bridge.py`/`change_bridge.py` 中仍留有 3 处 `TODO M5` 标注的未接入 UI 项——"里程碑完成"的判定标准本身也存在一定弹性。

### 2.4 结论

代码质量和门禁纪律是这个项目最扎实的部分，值得保留和学习；但当前最大的差距不是代码，而是**验证**——工具已经把自己的开发流程打磨得接近工业级严谨，却还没有拿真实的 PLC 项目验证过它对目标用户到底有没有用，同时治理系统的运行成本正在逐渐反噬本该投向产品验证的精力。

## 三、后续迭代方向建议

### 3.1 首要建议：暂停加新功能，把 M7（真实试用）补上

具体做法：挑一个正在真实推进的 PLC 项目（DJ-2026-005 是现成候选），用 `auto-pm project import` 正式接管进来，然后走一轮真实的变更单流程——不是给 auto-pm 自己开 CHG，是给这个真实项目开。这比再加 Modbus 新功能或做 Python V2.5 有价值得多。

PM_SESSION 里悬而未决的"specmgr / 变量表 / 插件系统谁先吸收"这个优先级问题，建议的答案是：**都先不做，先做 M7**。没有真实使用反馈时排的优先级本质上是猜测。

### 3.2 M6 性能验证按最小成本做

不需要做成一个大项目：拿几十个项目规模跑一次真实扫描，测一下 GUI 响应速度和 SQLite 缓存命中率，够用即可，避免为了"验证性能"这件事又造出一套新的性能测试基础设施。

### 3.3 清理表层问题

- 清理已提交到 git 的调试产物（`mypy_output*.txt`、`fix_*.py`、`debug_wb.py` 等），并在整个工作空间层面（不只 auto-pm 子项目）补充 `.gitignore` 规则，防止再犯。
- 给全量测试崩溃（`-1073741510`）单独开一个可复现的问题工单定位根因。

## 四、治理方案建议

### 4.1 值得保留的部分

- `PM_SESSION` 作为单一状态真源
- 三轨门禁（ruff + mypy + pytest）作为发布前置条件
- 版本号三件套（pyproject / CHANGELOG / 技术债报告）同步机制

这几项是这个项目质量显著高于同类个人项目的核心原因，不建议改动。

### 4.2 建议简化的部分

**不是所有改动都值得一份完整的 12 章节 CHG-*.md。** 目前大量出现"先改代码、后 retrofit 补单"的模式（CHG-134/135/136/142/143 均属此类），这其实是团队用行动证明——对于一行断言修复、文档同步这类内部维护性改动，完整流程太重，本能会绕过去再补票。

建议正式建立一个轻量通道：

- **内部维护性改动**（文档同步、测试断言修正、注释修正）：只需一行 CHANGELOG + commit message，不必开 CHG-*.md。
- **用户可见行为 / 架构级 / 跨模块影响的改动**：继续走完整的 12 章节闭环流程。

这样"dogfooding 闭环次数"能重新变成一个有意义的信号，而不是被大量流程自愈类改动稀释。

同时，建议把约束工作流引擎（`constraint`/`workflow` 模块）的进一步投入按下暂停键——它解决的是"防止团队违反自己定的规则"这个问题，优先级明显低于"这工具对电气工程师到底有没有用"，是比较典型的"为流程造流程"。

---

## 五、一句话总结

auto-pm 的代码质量和自律程度，在同类项目里少见地扎实；但当前最大的差距不在代码，而在验证——它需要停下来，先在一个真实项目上证明自己，而不是继续把精力投入到让自己的治理流程变得更复杂。
