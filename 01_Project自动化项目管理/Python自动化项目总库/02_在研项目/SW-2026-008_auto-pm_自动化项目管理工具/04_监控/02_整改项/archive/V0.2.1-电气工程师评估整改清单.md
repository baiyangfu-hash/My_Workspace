## P0 严重问题（工具自身生成的产物无法通过自身检查）

### P0-1 [严重] 工具创建的项目无法通过自身的 plc check

**现象**：使用 `project create --stack plc --mode standard-project` 创建的项目，立即执行 `plc check` 报 FAIL（fail=1），原因是"缺少 .plc.json 配置文件"。

**根本原因**：模板 `plc-standard-project` 将 `.plc.json` 生成在 `02_PLC程序/02_PLC程序/.plc.json`（嵌套子目录），但 `PlcChecker` 只在项目根目录查找 `.plc.json`，两者不一致。

**复现步骤**：
```
python -m auto_pm -w <workspace> project create --stack plc --mode standard-project --id DJ-2026-099 --name "测试" --business-line DJ
python -m auto_pm -w <workspace> plc check DJ-2026-099
# => .plc.json FAIL: 缺少 .plc.json 配置文件（LSP-907 §1.1）
```

**预期行为**：工具自身生成的项目骨架必须能通过自身的规范检查。

**建议修复方向**：
- 方案A（推荐）：`PlcChecker` 支持递归查找 `.plc.json`（与 `ProjectScanner` 保持一致）
- 方案B：模板将 `.plc.json` 生成在项目根目录
- 方案C：`PlcChecker` 读取 `.copier-answers.yml` 中的 mode 字段，按模式定位 `.plc.json`

**涉及文件**：
- `auto_pm/plc/checker.py` — `.plc.json` 查找逻辑
- `templates/plc-standard-project/` — `.plc.json` 生成位置

---

### P0-2 [严重] ChangeService 解析器无法解析工具自己生成的变更单

**现象**：`change create` 成功生成变更单文件（内容完整，§3/§4 章节齐全，字段已填充），但 `change show` 报"缺少 §3 变更基本信息章节"、"项目编号为空"、"业务性质为空"等警告，所有字段显示为"待补充"。

**根本原因**：`ChangeService` 的 Markdown 解析器（`change/parser.py`）无法识别自己生成的变更单章节结构，字段提取全部失败。

**复现步骤**：
```
python -m auto_pm -w <workspace> change create --pid DJ-2026-099 --domain PLC --nature REQ --scope MODULE --applicant "电气工程师" --background "测试" --necessity "验证"
python -m auto_pm -w <workspace> change show CHG-PLC-2026-001
# => 项目编号: (空) / 业务性质: (空) / 申请人: 待补充 / 变更背景: 待补充
# => WARNING: 变更单缺少§3变更基本信息章节
```

**预期行为**：工具生成的变更单必须能被自身的解析器正确解析。

**建议修复方向**：对照生成的 Markdown 文件结构（§3.0 编号与项目 / §3.1 技术领域 / §3.2 业务性质 / §3.3 影响范围 / §3.4 申请信息 / §4 变更原因），修正 `change/parser.py` 的章节匹配正则与字段提取逻辑。

**涉及文件**：
- `auto_pm/change/parser.py` — 变更单解析逻辑
- `auto_pm/change/generator.py` — 变更单生成逻辑（需与 parser 对齐）

### P0-3 [严重] change transition 门禁校验因解析器缺陷而失败

**现象**：`change transition CHG-PLC-2026-001 --to submitted` 失败，门禁校验报"§3.2 业务性质未填写"、"§3.3 影响范围未填写"、"§3.4 变更申请人未填写"、"§4 变更原因未填写"。但实际文件中这些字段都已正确填写。

**根本原因**：P0-2 的解析器缺陷导致 `TransitionGuardChecker` 读不到字段值，误判为未填写。

**复现步骤**：见 P0-2，执行 `change transition` 即可复现。

**预期行为**：字段已填写的变更单应能通过门禁校验并完成状态流转。

**建议修复方向**：修复 P0-2 后本问题自动解决。

**涉及文件**：
- `auto_pm/change/guard_checker.py` — 门禁校验逻辑（依赖 parser）

## 评估结论

auto-pm 0.2.1 在架构设计、模板质量、CLI 易用性方面表现优秀，但存在 **3 个 P0 级严重 Bug**（工具自身生成的产物无法通过自身检查/解析），这直接阻断了对 PLC 项目库的规范化管理流程。建议优先修复 P0 问题，使工具达到"自洽"状态（生成的项目能通过自身的检查、生成的变更单能被自身的解析器解析），再推进 P1/P2 优化。

作为电气工程师+项目经理，我对工具的总体评价：**架构扎实、模板专业、但自洽性不足**。修复 P0 后即可投入实际项目管理使用。
