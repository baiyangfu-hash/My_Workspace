# 技术方案文档（TEC）- auto-pm 架构重设计版

## 1. 方案结论

## 1.1 最终决策

本轮不采用“立刻全量 Web 重写”，也不继续接受“QML 页面直接扩展到更多 Service”的做法。

最终方案为：

> **采用“接口优先、运行时后置”的混合架构。**

含义是：

1. **当前运行时继续以 QML 桌面为主**
2. **HTML 只作为原型和方案讨论资产**
3. **先建立稳定的应用接口层**
4. **未来是否做 Web，建立在接口层稳定之后**

## 1.2 为什么这样选

因为当前项目的真实资产状态是：

- 后端能力已经很多，不能轻易推倒
- QML 页面也已经投入了较多实现
- 真正的问题不是“有没有前端”，而是“界面和业务之间没有稳定接口层”

如果现在直接切 Web，会发生两件事：

1. 重新做一遍 UI
2. 还要重新拆接口

这对当前阶段的 ROI 不高。

## 2. 备选方案比较

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A | 继续维持当前 QML + 大桥接类 | 改动最小 | 结构债继续累积 | 不采用 |
| B | 立即切 FastAPI + Web | 技术栈更通用 | 代价大、周期长、稳定性风险高 | 暂不采用 |
| C | QML 运行时 + HTML 原型 + Facade 接口层 | 可复用现有资产，且为未来 Web 铺路 | 需要先做结构收口 | **采用** |

## 3. 目标架构

## 3.1 技术视图

```text
HTML Prototype
       \
        > Interface Contract -> Application Facade -> Existing Services
       /
QML Runtime
```

## 3.2 电气工程师视角

更容易理解的表达是：

```text
界面层 = HMI
接口层 = 变量表 / 命令字 / 状态字
业务层 = PLC 逻辑
数据层 = 工程文件 / DB / 台账
```

也就是说：

- 界面不直接碰业务内部
- 业务重构时先守住接口
- 后面换一套界面，不该重做业务逻辑

## 4. 本次方案要复用的资产

## 4.1 直接复用

| 资产 | 处理方式 |
|------|---------|
| `ProjectService` | 直接复用 |
| `ChangeService` | 直接复用 |
| `DashboardService` | 直接复用 |
| `DocRefreshService` | 直接复用 |
| `AssetSummaryService` | 直接复用 |
| `PmSessionService` | 直接复用 |
| `spec` / `plc` 现有能力 | 直接复用 |
| 已有 QML 页面 | 保留并逐步接入新接口层 |
| 现有测试 | 作为回归保护网复用 |

## 4.2 重组复用

| 资产 | 处理方式 |
|------|---------|
| `QmlBridge` | 拆成多个桥接对象 |
| 现有 DTO | 统一到 contracts/dto |
| 页面调用路径 | 改成 QML -> Bridge -> Facade -> Service |
| 设计文档 | 全部收口到 `02_设计` |

## 4.3 暂不继续放大的资产

| 资产 | 原因 |
|------|------|
| 大一统桥接类 | 扩一页就加一批方法，不可持续 |
| 旧 QWidget 时代叙述 | 与当前代码基线不一致 |
| 直接 Web 化冲动 | 没有先把接口层稳定住 |

## 5. 关键技术决策

## 5.1 运行时决策

- **当前运行时**：QML
- **原型技术**：HTML + Markdown
- **Web 化状态**：备选，不立即进入实施

## 5.2 接口决策

- 先做本地进程内 Facade
- 先定义 DTO/Command/Event
- 不把 HTTP 当作第一阶段硬依赖

## 5.3 文档决策

- 设计类文档统一放 `02_设计`
- 治理/发布/试运行类文档继续留在 `00_项目基础信息`

## 5.4 计划决策

- 采用 30 周滚动计划
- 先完成架构收口，再做性能和试运行
- 架构演进按里程碑推进，而不是按“哪个技术栈更流行”推进

## 6. 实施策略

## 6.1 第一阶段：文档与接口定版

目标：

- 设计真源集中
- 接口模型成文
- HTML 原型形成讨论基础

## 6.2 第二阶段：应用层成形

目标：

- 建立 5 个 Facade
- 建立 contracts 目录
- 拆出桥接层边界

## 6.3 第三阶段：页面接线迁移

目标：

- 按域逐步从旧桥接方式迁到 Facade
- 先迁驾驶舱和项目工作台
- 再迁变更中心与规范中心

## 6.4 第四阶段：性能与试运行

目标：

- 建立 FPS、内存、加载时延基线
- 做真实试用
- 根据问题决定是否需要继续走 Web 试点

## 7. 风险与缓解

| 风险 | 说明 | 缓解 |
|------|------|------|
| Bridge 拆分时回归 | 现有页面依赖已很多 | 以域为单位迁移，逐页回归 |
| 文档重写但代码未跟 | 方案与实现可能再次分离 | 里程碑按实现同步回写 |
| 提前讨论 Web 过多 | 容易转移主线 | 以接口稳定度作为前置门槛 |
| Facade 变成新中间层负担 | 如果设计太重会增加复杂度 | 每个 Facade 只做聚合与编排，不重造领域规则 |

## 9. 技术判断

这份方案最重要的判断不是“QML 好还是 Web 好”，而是：

> **对 auto-pm 这种已经有大量后端能力和桌面实现的项目，先做接口层，比先换界面框架更值。**

这更稳，也更适合你现在的角色和项目阶段。
