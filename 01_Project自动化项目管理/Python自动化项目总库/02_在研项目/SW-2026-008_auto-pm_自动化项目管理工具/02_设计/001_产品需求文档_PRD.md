# 产品需求文档（PRD）- auto-pm 架构重设计版

## 1. 文档定位

本版 PRD 不再围绕“再做多少页面”展开，而是围绕一个更适合电气工程师理解和落地的核心原则展开：

> **界面层、业务层、项目数据层分离，通过稳定的变量/命令接口连接。**

这和 PLC 程序、HMI 画面、现场信号之间的关系是一致的：

- HMI 不直接写 PLC 内部实现细节
- HMI 通过变量地址、命令位、状态位与 PLC 通信
- PLC 内部逻辑可以重构，但外部接口要稳定

auto-pm 的新架构就按这个思路设计。

## 2. 产品定位

- **一句话定位**：面向电气工程师的本地项目作业台，用于统一管理 PLC/Python 项目、文档、变更、规范检查和交付证据。
- **产品形态**：本地桌面运行时 + HTML 原型设计资产 + Markdown 文档真源。
- **当前主线**：先把“界面”和“后端能力”彻底解耦，再决定是否需要 Web 化。

## 3. 目标用户

### 3.1 核心用户

1. **电气工程师**
   - 关注项目列表、工程资产、变更、规范检查、交付资料
   - 希望界面稳定、概念少、操作可视化

2. **兼任 PM 的工程师**
   - 关注里程碑、变更闭环、试运行、发布门禁、风险
   - 需要一套能持续推进的计划体系，而不是一次性原型

3. **懂一点 Python 的维护者**
   - 不希望直接面对大段 UI 桥接胶水代码
   - 希望新增页面时能按接口接入，而不是继续把逻辑堆进 `QmlBridge`

### 3.2 非核心用户

- 专业前端工程师
- 远程多用户协作团队
- 云端 SaaS 用户

这些不是当前阶段的主目标。

## 4. 当前问题定义

## 4.1 用户视角问题

1. 项目已经能跑，但**架构不好讲清楚**
2. 当前 GUI、Service、数据扫描、文档逻辑**边界不清**
3. 设计文档散落在 `00_项目基础信息` 与 `02_设计`，**设计真源不集中**
4. 电气工程师能理解“画面通过变量接口驱动逻辑”，但不容易理解“QML 直接绑多个 Python Service”
5. 未来如果要扩页面、换界面、做 Web 试点，当前结构的复用边界不够稳定

## 4.2 代码侧根因

1. `QmlBridge` 承担了过多职责：装配、DTO 转换、命令入口、状态暴露
2. 页面和领域服务之间缺少清晰的**应用层接口**
3. 文档历史包袱重，旧时代技术选型描述仍在干扰判断
4. 设计原型、实现原型、交付文档没有形成清晰链路

## 5. 新版需求目标

## 5.1 总目标

建立一套“**像 PLC 与 HMI 一样通过稳定接口耦合**”的软件架构，使 auto-pm 在不推倒现有核心能力的前提下，具备以下特性：

1. UI 可以重做，但业务逻辑尽量不重做
2. 业务逻辑可以扩展，但 UI 不需要直接知道内部细节
3. 桌面运行时先稳定，HTML 原型作为设计资产复用
4. 后续若真要做 Web，可在接口层之上演进，而不是从头再拆一遍

## 5.2 本轮必须达成

1. 设计文档统一收口到 `02_设计`
2. 明确新的目标架构与模块边界
3. 定义 UI 和业务层之间的命令/状态/DTO 接口
4. 给出可执行的里程碑与 30 周实施计划
5. 给出 HTML 原型和配套说明，便于持续讨论

## 5.3 本轮明确不做

1. 不立即把整套 QML 改成 Web 前端
2. 不在本轮引入 HTTP/REST 作为强制运行时依赖
3. 不重写现有 ProjectService、ChangeService、DB 层核心能力
4. 不把项目目标改成在线协作平台

## 6.2 界面和业务的接口模型

以 PLC/HMI 思路类比，界面只通过三类接口连接后端：

1. **状态接口**
   - 只读
   - 例如：项目摘要、变更状态、检查结果、缓存状态

2. **命令接口**
   - 带输入，触发动作
   - 例如：创建变更单、执行检查、刷新文档、重建索引

3. **事件接口**
   - 结果通知
   - 例如：刷新完成、检查失败、数据已更新、需要确认

## 7. 用户故事

### 7.1 电气工程师

- 作为电气工程师，我希望打开项目后先看到项目健康状态，而不是先理解内部技术结构。
- 作为电气工程师，我希望“刷新文档”“检查规范”“查看变更”是工作动作，不是技术动作。
- 作为电气工程师，我希望 UI 上的字段名尽量和工程资产、变量表、文档口径一致。

### 7.2 PM 视角

- 作为兼任 PM 的工程师，我希望每个阶段都有明确里程碑、输出物和验收口径。
- 作为 PM，我希望可以明确区分“方案文档”“治理文档”“试运行证据”。

### 7.3 后续维护者

- 作为维护者，我希望新增一个页面时，只需要接一个应用接口，不需要继续扩展上帝桥接类。
- 作为维护者，我希望未来要试做 Web 时，能复用同一套命令和 DTO 契约。

## 8. 成功标准

## 8.1 架构成功标准

1. 页面层不再直接耦合多个领域 Service
2. `QmlBridge` 被拆为更小的接口面
3. DTO/Command/Event 契约稳定成文
4. 文档真源集中在 `02_设计`

## 8.2 业务成功标准

1. 电气工程师可以按“驾驶舱 → 项目工作台 → 变更 → 检查 → 发布”顺序理解系统
2. 实际试用时，问题可被归类到“界面问题 / 接口问题 / 领域逻辑问题”
3. 未来讨论 Web 化时，不再从“界面框架”争论，而从“接口层是否稳定”判断

## 8.3 交付成功标准

1. 完成新的 PRD / INT / DSN / TEC
2. 完成里程碑与 30 周计划
3. 完成 HTML 原型和说明文档
4. PM_SESSION 与新文档索引同步

## 9. 约束条件

1. **优先复用已有资产**
   - `ProjectService`
   - `ChangeService`
   - `DashboardService`
   - `Spec` 相关能力
   - 已有 QML 页面
   - 已有测试资产

2. **避免一次性推倒重来**
   - 先拆接口，再决定运行时技术替换

3. **保持桌面单机可用**
   - 当前阶段仍以本地桌面使用场景为主

4. **文档先行**
   - 所有后续重构必须以 `02_设计` 为设计真源
