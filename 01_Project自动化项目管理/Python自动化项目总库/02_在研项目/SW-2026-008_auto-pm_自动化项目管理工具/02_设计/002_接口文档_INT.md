# 接口文档（INT）- auto-pm 架构重设计版

## 1. 设计原则

本项目新的接口设计原则只有一句话：

> **把 UI 当成 HMI，把业务系统当成 PLC 逻辑，二者通过稳定的命令、状态、事件接口连接。**

这意味着：

1. UI 不直接访问底层文件系统和仓储
2. UI 不直接拼接领域对象
3. UI 通过 DTO、Command、Event 与应用层交互
4. 未来若替换成 Web，只要接口不变，业务层可复用

## 2. 接口分层

## 2.1 表现层接口

- QML 页面
- HTML 原型
- 未来可能的 Web 页面

这些都属于“画面”，不直接持有业务规则。

## 2.2 应用接口层

这是本次重设计的关键层，负责把复杂后端能力整理成清晰的操作面。

建议拆成 5 组接口：

1. `WorkbenchFacade`
2. `ChangeFacade`
3. `SpecFacade`
4. `DeliveryFacade`
5. `SystemFacade`

## 2.3 领域服务层

复用现有核心能力：

- `ProjectService`
- `ChangeService`
- `DashboardService`
- `DocRefreshService`
- `AssetSummaryService`
- `PmSessionService`
- `Spec` 相关服务
- `PLC` 相关服务

## 3. 接口类型

## 3.1 状态接口

用于界面展示，特点是：

- 不改数据
- 尽量返回聚合后的 DTO
- 适合页面首次加载和刷新

典型示例：

- `get_dashboard_snapshot()`
- `list_project_cards()`
- `get_project_workspace(project_id)`
- `get_change_detail(change_id)`
- `get_spec_center_snapshot()`

## 3.2 命令接口

用于执行动作，特点是：

- 有输入
- 有返回结果
- 可能改变状态

典型示例：

- `create_change_request(command)`
- `transition_change(command)`
- `refresh_project_docs(command)`
- `run_spec_check(command)`
- `rebuild_index(command)`

## 3.3 事件接口

用于通知 UI：

- 数据已更新
- 操作成功
- 操作失败
- 需要确认

典型示例：

- `projects_changed`
- `workspace_changed`
- `change_flow_updated`
- `spec_check_completed`
- `operation_failed`

## 5. 命令契约

## 5.1 创建变更单

```text
CreateChangeCommand
- project_id: str
- title: str
- domain: str
- nature: str
- background: str
- necessity: str
- applicant: str
```

返回：

```text
CommandResult
- success: bool
- message: str
- payload: ChangeRequestDTO | None
- errors: list[ErrorDTO]
```

## 5.2 变更状态流转

```text
TransitionChangeCommand
- change_id: str
- target_status: str
- operator: str
- note: str | None
- allow_partial_verification: bool
```

## 5.3 文档刷新

```text
RefreshDocsCommand
- project_id: str
- dry_run: bool
- sections: list[str]
```

## 5.4 规范检查

```text
RunSpecCheckCommand
- target_path: str
- auto_fix: bool
- scope: str
```

## 6. 事件契约

## 6.1 统一事件结构

```text
UiEvent
- event_name: str
- level: info | warning | error | success
- source: str
- message: str
- payload: dict[str, Any] | None
```

## 6.2 推荐事件清单

| 事件名 | 触发时机 | 典型用途 |
|------|---------|---------|
| `dashboard_updated` | 驾驶舱刷新后 | 更新首页摘要 |
| `project_opened` | 进入项目工作台 | 切换页面上下文 |
| `project_workspace_updated` | 工程资产/文档刷新后 | 重绘工作台 |
| `change_created` | 变更单创建成功 | 刷新变更列表 |
| `change_transitioned` | 状态流转成功 | 更新时间线 |
| `spec_check_finished` | 检查完成 | 展示结果 |
| `operation_failed` | 任意命令失败 | 统一错误展示 |

## 7. 接口到实现的映射

## 7.1 目标映射

| 接口面 | 应用层职责 | 复用的现有能力 |
|------|-----------|---------------|
| `WorkbenchFacade` | 驾驶舱、项目列表、工作台聚合 | `DashboardService` `ProjectService` `AssetSummaryService` |
| `ChangeFacade` | 变更创建、流转、列表、详情 | `ChangeService` |
| `SpecFacade` | 规范概览、检查、索引 | `spec` 相关服务 |
| `DeliveryFacade` | 文档刷新、报告、发布收口 | `DocRefreshService` `ReportService` |
| `SystemFacade` | 缓存、索引、工作空间状态 | `PmSessionService` `db/sync` |

## 7.2 对当前 QML 的改造方向

当前 `QmlBridge` 不再继续扩成总入口，改为：

- `WorkbenchBridge`
- `ChangeBridge`
- `SpecBridge`
- `DeliveryBridge`
- `SystemBridge`

每个 Bridge 只暴露本域的 DTO、命令和事件。

## 8. 错误边界

接口层统一返回以下 4 类错误：

1. `validation_error`
2. `domain_error`
3. `integration_error`
4. `unexpected_error`

对 UI 的要求：

- 页面不能直接展示 traceback
- 页面必须展示可理解的中文错误信息
- 详细技术信息进入日志区或调试抽屉

## 9. 演进策略

## 9.1 第一阶段

- 先在本地进程内建立 Python Facade 接口
- QML 通过 Facade 访问能力

## 9.2 第二阶段

- 若未来需要 Web 化，可让 Facade 再挂一层 HTTP API
- 对 UI 来说，DTO/Command 不变

## 9.3 判定条件

只有在以下条件满足时才进入 HTTP 化：

1. 接口契约已稳定两轮以上
2. 真实试用证明多端化有价值
3. 桌面端不再是唯一目标场景
