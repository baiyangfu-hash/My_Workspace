# 详细设计说明书（DSN）- auto-pm 架构重设计版

## 1. 设计目标

本版详细设计的核心目标是，把当前“一个桥接层连接很多服务”的结构，重构为更接近工业控制系统分层的结构：

1. **画面层**：QML 页面 / HTML 原型
2. **接口层**：DTO、Command、Event、Bridge/Facade
3. **应用层**：工作台、变更、规范、交付、系统 5 个用例编排域
4. **领域层**：现有 Service 与规则
5. **基础设施层**：DB、文件系统、模板、扫描器、日志

## 2. 目标架构总图

```text
┌────────────────────────────────────────────────────────────┐
│ 表现层 Presentation                                        │
│ QML Runtime / HTML Prototype / 后续可选 Web               │
├────────────────────────────────────────────────────────────┤
│ 接口层 Interface                                           │
│ Bridge + Facade + DTO + Command + Event                   │
├────────────────────────────────────────────────────────────┤
│ 应用层 Application                                         │
│ Workbench / Change / Spec / Delivery / System             │
├────────────────────────────────────────────────────────────┤
│ 领域层 Domain                                              │
│ ProjectService / ChangeService / DashboardService / ...   │
├────────────────────────────────────────────────────────────┤
│ 基础设施层 Infrastructure                                  │
│ Repository / SQLite / File System / Scanner / Templates   │
└────────────────────────────────────────────────────────────┘
```

## 3. 各层职责

## 3.1 表现层

### QML Runtime

- 仍是当前主运行时
- 负责布局、输入、列表展示、状态展示
- 不直接调用底层领域服务

### HTML Prototype

- 只做方案设计与交互讨论
- 不承载运行时逻辑
- 用于快速讨论页面结构、状态覆盖、信息密度

### Web Runtime（未来可选）

- 不是当前实施目标
- 只有在接口层稳定后才考虑引入

## 3.2 接口层

接口层是本次重设计的重点，相当于 PLC 项目中的“变量接口层”。

它负责：

1. 把领域对象转换成 UI 可直接消费的 DTO
2. 把 UI 操作转换成命令对象
3. 把结果转换成统一事件与反馈
4. 隔离 UI 技术栈与领域实现

建议的结构：

```text
auto_pm/ui/contracts/
  dto/
  commands/
  events/

auto_pm/ui/bridges/
  workbench_bridge.py
  change_bridge.py
  spec_bridge.py
  delivery_bridge.py
  system_bridge.py
```

## 3.3 应用层

应用层不直接面向具体页面，而是面向“工作动作”。

建议新增：

```text
auto_pm/application/
  workbench_facade.py
  change_facade.py
  spec_facade.py
  delivery_facade.py
  system_facade.py
```

每个 Facade 只做三件事：

1. 调用一个或多个现有 Service
2. 聚合结果
3. 输出 DTO / CommandResult

## 3.4 领域层

领域层尽量复用当前资产，不做推倒重写。

优先复用：

- `auto_pm/core/project_service.py`
- `auto_pm/change/change_service.py`
- `auto_pm/core/dashboard_service.py`
- `auto_pm/core/doc_refresh_service.py`
- `auto_pm/core/asset_summary_service.py`
- `auto_pm/core/pm_session_service.py`
- `auto_pm/spec/*`
- `auto_pm/plc/*`

## 3.5 基础设施层

保持现有基础设施为主：

- SQLite
- repository
- 文件扫描
- 模板系统
- PM_SESSION
- CHANGELOG / CHG 文档

## 4. 关键模块设计

## 4.1 WorkbenchFacade

负责：

- 驾驶舱摘要
- 项目列表
- 项目工作台聚合
- 工程资产摘要

输入：

- `workspace_root`
- `project_id`

输出：

- `DashboardSnapshotDTO`
- `ProjectCardDTO`
- `ProjectWorkspaceDTO`

## 4.2 ChangeFacade

负责：

- 变更单创建
- 变更单列表与详情
- 状态流转
- 验证摘要

它对 UI 隐藏：

- Markdown 细节
- 台账文件更新细节
- 状态机门禁解析细节

## 4.3 SpecFacade

负责：

- 规范中心概览
- 检查结果聚合
- 漂移提示
- index/frontmatter/check/report 操作

## 4.4 DeliveryFacade

负责：

- 文档刷新
- 报告收口
- 发布门禁汇总
- 试运行结果聚合

## 4.5 SystemFacade

负责：

- DB/缓存状态
- 工作空间状态
- PM_SESSION 健康
- 索引重建

## 5. Bridge 拆分设计

## 5.1 当前问题

当前 `QmlBridge` 同时承担：

- 多个 service 注入
- property 暴露
- slot 命令入口
- DTO 转换
- 结果字符串拼装

这会带来两个后果：

1. 任何页面扩展都容易继续堆进去
2. 将来要切 Web 时，没有清晰的接口真源

## 5.2 目标结构

```text
QML Page
  ↓
Domain Bridge
  ↓
Application Facade
  ↓
Existing Services
```

### 推荐拆分

1. `WorkbenchBridge`
2. `ChangeBridge`
3. `SpecBridge`
4. `DeliveryBridge`
5. `SystemBridge`

### 保留一个顶层装配器

可保留轻量的 `UiBridgeRegistry` 或 `BridgeContainer`，只负责：

- 实例创建
- context property 注册
- 共享事件转发

不再承担具体业务逻辑。

## 7. 关键数据流

## 7.1 驾驶舱加载

```text
QML DashboardView
  -> WorkbenchBridge.loadDashboard()
  -> WorkbenchFacade.get_dashboard_snapshot()
  -> DashboardService + ProjectService
  -> DashboardSnapshotDTO
  -> QML 渲染
```

## 7.2 打开项目工作台

```text
QML ProjectListView
  -> WorkbenchBridge.openProject(project_id)
  -> WorkbenchFacade.get_project_workspace(project_id)
  -> ProjectService + AssetSummaryService + DocRefreshService
  -> ProjectWorkspaceDTO
  -> WorkspaceView 渲染
```

## 7.3 创建变更单

```text
QML ChangeDialog
  -> ChangeBridge.createChange(command)
  -> ChangeFacade.create_change_request(command)
  -> ChangeService.create_change_request(...)
  -> CommandResult(ChangeRequestDTO)
  -> QML 刷新列表 + 时间线
```

## 7.4 规范检查

```text
QML SpecCenterView
  -> SpecBridge.runCheck(command)
  -> SpecFacade.run_spec_check(command)
  -> Spec services
  -> SpecCheckResultDTO
  -> QML 显示结果 + 事件提示
```

## 8. 状态覆盖设计

每个页面至少覆盖以下状态：

1. `idle`
2. `loading`
3. `success`
4. `empty`
5. `warning`
6. `error`
7. `permission_denied`（若未来引入角色约束）

原因很直接：工业类工具最怕“只有正常路径，没有异常状态”。

## 9. 复用策略

## 9.1 直接复用

- 现有 service
- 现有 db/repository
- 现有 PM_SESSION 机制
- 现有变更管理状态机
- 已完成的 QML 页面
- 已有测试数据与部分测试逻辑

## 9.2 需要重组但不重写

- `QmlBridge`
- 页面到 service 的调用路径
- DTO 组织方式
- 设计文档真源位置

## 9.3 暂不复用为运行时核心

- 旧的 QWidget 时代叙述
- 旧的“UI 直接绑 service”扩展方式
- 任何把运行时直接等同于 HTML 原型的做法

## 11. 设计结论

本次详细设计的最终结论不是“改成 Web”或“继续 QML”，而是：

> **先把界面和业务之间的接口层做出来，再让运行时技术选择变成次一级问题。**

这比直接争论 QML、Web、FastAPI 更稳，也更适合当前这个项目的现实资产状态。
