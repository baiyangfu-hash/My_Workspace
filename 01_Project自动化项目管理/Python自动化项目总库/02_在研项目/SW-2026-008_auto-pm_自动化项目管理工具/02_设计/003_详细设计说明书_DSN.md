# 详细设计说明书（DSN）- auto-pm 架构重设计版

## 1. 设计目标

本版详细设计的核心目标是，把当前“一个桥接层连接很多服务”的结构，重构为更接近工业控制系统分层的结构：

1. **画面层**：QML 页面 / HTML 原型
2. **接口层**：DTO、Command、Event、Bridge/Facade
3. **应用层**：工作台、变更、规范、交付、系统 5 个用例编排域
4. **领域层**：现有 Service 与规则
5. **基础设施层**：DB、文件系统、模板、扫描器、日志

## 3. 各层职责

## 3.1 表现层

### QML Runtime

- 仍是当前主运行时
- 负责布局、输入、列表展示、状态展示
- 不直接调用底层领域服务

### HTML Prototype

- 只做方案设计与交互讨论
- 不承载运行时逻辑
- 用于快速讨论页面结构、状态覆盖、信息密度

### Web Runtime（未来可选）

- 不是当前实施目标
- 只有在接口层稳定后才考虑引入

## 3.2 接口层

接口层是本次重设计的重点，相当于 PLC 项目中的"变量接口层"。

它负责：

1. 把领域对象转换成 UI 可直接消费的 DTO
2. 把 UI 操作转换成命令对象
3. 把结果转换成统一事件与反馈
4. 隔离 UI 技术栈与领域实现

实际结构（已实现）：

```text
auto_pm/ui/contracts/
  dto/           # change_dto / delivery_dto / spec_dto / system_dto / workbench_dto
  commands/      # change_commands / spec_commands
  events/        # ui_events
  result.py      # CommandResult 统一返回

auto_pm/ui/qml/bridges/
  workbench_bridge.py   # 已实现
  change_bridge.py      # 已实现
  spec_bridge.py        # 已实现
  delivery_bridge.py    # 已实现
  system_bridge.py      # 已实现
```

## 3.3 应用层

应用层不直接面向具体页面，而是面向"工作动作"。

已实现（V0.9.1）：

```text
auto_pm/application/
  workbench_facade.py   # 已实现
  change_facade.py      # 已实现
  spec_facade.py        # 已实现
  delivery_facade.py    # 已实现
  system_facade.py      # 已实现
```

每个 Facade 只做三件事：

1. 调用一个或多个现有 Service
2. 聚合结果
3. 输出 DTO / CommandResult

## 5. Bridge 拆分设计

## 5.1 历史问题（已解决）

历史上 `QmlBridge` 同时承担：

- 多个 service 注入
- property 暴露
- slot 命令入口
- DTO 转换
- 结果字符串拼装

这曾带来两个后果：

1. 任何页面扩展都容易继续堆进去
2. 将来要切 Web 时，没有清晰的接口真源

> 状态：V0.9.0 已完成拆分，`QmlBridge` 已被 5 个 Domain Bridge 取代。

## 5.2 目标结构（已完成）

```text
QML Page
  ↓
Domain Bridge
  ↓
Application Facade
  ↓
Existing Services
```

### 已完成拆分

1. `WorkbenchBridge` — 已实现（`auto_pm/ui/qml/bridges/workbench_bridge.py`）
2. `ChangeBridge` — 已实现（`auto_pm/ui/qml/bridges/change_bridge.py`）
3. `SpecBridge` — 已实现（`auto_pm/ui/qml/bridges/spec_bridge.py`）
4. `DeliveryBridge` — 已实现（`auto_pm/ui/qml/bridges/delivery_bridge.py`）
5. `SystemBridge` — 已实现（`auto_pm/ui/qml/bridges/system_bridge.py`）

### 顶层装配器（已实现）

已保留轻量的 `auto_pm/ui/registry.py`，只负责：

- 实例创建

不再承担具体业务逻辑。

## 7. 关键数据流（已实现）

## 7.1 驾驶舱加载（已实现）

```text
QML DashboardView
  -> WorkbenchBridge.loadDashboard()
  -> WorkbenchFacade.get_dashboard_snapshot()
  -> DashboardService + ProjectService
  -> DashboardSnapshotDTO
```

## 7.2 打开项目工作台（已实现）

```text
QML ProjectListView
  -> WorkbenchBridge.openProject(project_id)
  -> WorkbenchFacade.get_project_workspace(project_id)
  -> ProjectService + AssetSummaryService + DocRefreshService
  -> ProjectWorkspaceDTO
  -> WorkspaceView 渲染
```

## 7.3 创建变更单（已实现）

```text
QML ChangeDialog
  -> ChangeBridge.createChange(command)
  -> ChangeFacade.create_change_request(command)
  -> ChangeService.create_change_request(...)
  -> CommandResult(ChangeRequestDTO)
  -> QML 刷新列表 + 时间线
```

## 7.4 规范检查（已实现）

```text
QML SpecCenterView
  -> SpecBridge.runCheck(command)
  -> SpecFacade.run_spec_check(command)
  -> Spec services
  -> SpecCheckResultDTO
  -> QML 显示结果 + 事件提示
```

## 8. 状态覆盖设计

每个页面至少覆盖以下状态：

1. `idle`
2. `loading`
3. `success`
4. `empty`
5. `warning`
6. `error`
7. `permission_denied`（若未来引入角色约束）

原因很直接：工业类工具最怕“只有正常路径，没有异常状态”。

## 11. 设计结论

本次详细设计的最终结论不是“改成 Web”或“继续 QML”，而是：

> **先把界面和业务之间的接口层做出来，再让运行时技术选择变成次一级问题。**

这比直接争论 QML、Web、FastAPI 更稳，也更适合当前这个项目的现实资产状态。
