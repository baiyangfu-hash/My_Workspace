# auto-pm 架构重设计方案 - 评审建议

## 0. 总体判断

这套文档（PRD / INT / DSN / TEC / 里程碑计划 / HTML 原型 / 原型说明）整体质量较高：

- 核心决策明确且自洽：**接口优先、运行时后置**，不做一次性 Web 重写，也不继续放任 `QmlBridge` 膨胀。
- 术语、DTO 命名、Facade/Bridge 拆分在 7 份文档之间高度一致，没有互相矛盾的描述。
- PLC / HMI 类比选得好，确实能降低电气工程师理解架构分层的门槛，这是本方案相对普通"技术选型文档"的加分项。

以下建议不是推翻方案，而是在评审前把几个容易在实施中"埋雷"的点提前挑出来。

---

## 1. 架构设计层面

### 1.1 Facade 有"重蹈 QmlBridge 覆辙"的风险

TEC 已经识别到"Facade 变成新中间层负担"这个风险，但缓解措施只有一句"每个 Facade 只做聚合与编排"，缺少可执行的判断标准。

**建议**：在 DSN 第 4 节补充一条硬性约束，例如：

- 单个 Facade 方法超过约 30-40 行，或出现多层业务分支判断，视为信号——说明规则该留在 Service 层，而不是写进 Facade。
- 每个 Facade 新增方法前，先问一句："这是编排已有能力，还是在实现新的业务规则？" 后者应该下沉到领域层。

否则几个月后 Facade 可能只是换了个名字继续膨胀，重复 `QmlBridge` 的问题。

### 1.2 DTO / Command 缺少版本化设计

INT 定义了较完整的 DTO / Command / Event 契约，但没有涉及字段演进策略。当前桌面单机场景下影响不大，但这套接口未来要支撑 M8 的"Web 化 go/no-go"判断——如果契约没有版本约定，一旦真的要挂 HTTP，第一件事就是被迫破坏性重构，这会削弱"先做接口层，后面挂 HTTP 不用重拆"这个核心论点的可信度。

**建议**：现在就在 `UiEvent` 和核心 DTO 里加一个 `schema_version` 字段（或类似机制），成本很低，但为后续演进留出退路。

### 1.3 事件接口的技术落地方式未说明

"状态 / 命令 / 事件"三分法概念清楚，但没有说明事件在 QML 侧具体如何实现——是 Qt Signal、回调注册，还是轮询？这个决策直接影响 Bridge 层的实现复杂度和后续可测试性。

**建议**：在 DSN 第 5 节补一小节，明确事件的技术承载方式（例如"事件通过 Qt Signal 转发，Facade 层本身不感知 QML 存在"），避免留到编码阶段才发现和现有 QML 机制冲突。

---

## 2. 里程碑与实施计划层面

### 2.1 9 个里程碑几乎等分 3 周一个，但工作量明显不均

M3（变更域：状态机、审批轨迹、验证摘要）和 M4（一次性落地 Spec + Delivery + System 三个域）明显比 M2（Workbench 域）更复杂，但都只分配了 3 周。

**建议**：

- 要么将 M4 拆分为两个更小的里程碑；
- 要么在计划中明确写出弹性空间，例如"若 M3/M4 延期，可从 M6 性能验证的窗口中借用 1-2 周"。

否则一旦前期延期传导下去，真正需要充裕时间的 M7（真实试用）和 M8（问题闭环）反而会被压缩——这两个环节依赖外部反馈周期，是最不适合被压缩的部分。

### 2.2 提到了"回归风险"但没有回退机制

风险表中"Bridge 拆分时回归"的缓解措施是"以域为单位迁移、逐页回归"，但没有说明如果某个域迁移后出现明显问题，如何快速切回旧路径。

**建议**：在迁移期保留一个轻量的 feature flag（新旧 Bridge 并存开关），支持按项目或按页面灰度切换。对单人或小团队维护尤其重要——避免出问题时卡在"改了一半、进退两难"的中间状态。

---

## 3. 文档与验收标准层面

### 3.1 成功标准偏定性，缺少可验证的量化指标

PRD 第 8.1/8.2 节的标准（如"电气工程师能按驾驶舱→工作台→变更→检查→发布顺序理解系统"）在评审时很难判定"达标"还是"未达标"。

**建议**：至少为架构类目标补充 1-2 个可量化指标，例如：

- `QmlBridge` 代码行数 / 方法数量（重构前 vs. M5 收口后的对比）
- 新增一个页面所需改动的文件数量（间接衡量接口面是否足够清晰稳定）

### 3.2 HTML 原型目前只完整呈现了"驾驶舱"

原型说明中提到要覆盖 6 个工作域的信息结构，但 `006_UI架构原型.html` 实际只详细展示了驾驶舱 + 接口层/数据流示意，变更中心、规范中心、报告与发布、系统设置仍停留在 PRD 的文字描述层面。

**建议**：如果这份原型要在 M0 阶段就冻结讨论，建议至少补一版变更中心的原型（复杂度最高、状态流转最容易产生分歧），避免真正的争议点被推迟到编码阶段才暴露。

---

## 4. 优先级排序建议

如果评审前时间有限，按性价比排序建议优先处理：

| 优先级 | 建议 | 理由 |
|------|------|------|
| 高 | DTO/Command 加 `schema_version` 字段 | 成本极低，直接关系到"接口优先"论点是否站得住 |
| 高 | Bridge 迁移增加回退/灰度机制 | 降低 M2-M5 迁移期的实际风险 |
| 中 | 重新校准 M3/M4 工作量，写明弹性空间 | 保护 M7/M8 的真实试用窗口不被压缩 |
| 中 | 为 Facade 膨胀设定硬性判断标准 | 防止重蹈 QmlBridge 覆辙 |
| 低 | 补充变更中心原型 | 提前暴露状态流转类分歧 |
| 低 | 成功标准量化 | 便于后续评审判定，非阻塞项 |

---

## 5. 结论

方案的核心判断（接口优先、复用现有资产、不做一次性 Web 重写）是站得住的，7 份文档之间的自洽性也做得不错。上述建议主要是为了让"接口层稳定"这个核心承诺在实施中真正兑现，而不是在几个月后变成新的技术债。
