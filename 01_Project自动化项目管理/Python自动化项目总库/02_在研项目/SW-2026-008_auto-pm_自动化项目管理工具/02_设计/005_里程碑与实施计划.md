# 里程碑与实施计划

## 1. 计划定位

本计划面向“架构收口 + 运行时解耦 + 真实试用验证”，周期按 **30 周** 设计。

30 周不是为了把时间拉长，而是为了给这个项目留出三类必要空间：

1. 架构整理时间
2. 稳定性回归时间
3. 真实试用和反馈吸收时间

## 2. 总体原则

1. **先接口，后界面替换**
2. **先试用证据，后重大技术切换**
3. **能复用就不重写**
4. **里程碑必须有可验证输出物**

## 3. 里程碑总览

| 里程碑 | 周期 | 目标 | 关键输出 |
|------|------|------|---------|
| M0 | Week 1-3 | 文档真源重组与架构冻结 | 新 PRD/INT/DSN/TEC、原型、计划 |
| M1 | Week 4-6 | 接口层骨架 | contracts + facade 目录 + 首批 DTO |
| M2 | Week 7-9 | Workbench 域落地 | 驾驶舱/项目工作台接到新接口 |
| M3 | Week 10-12 | Change 域落地 | 变更中心接到新接口 |
| M4 | Week 13-15 | Spec/Delivery/System 域落地 | 规范/报告/设置接到新接口 |
| M5 | Week 16-18 | Bridge 收口与回归稳定 | `QmlBridge` 拆分完成 |
| M6 | Week 19-21 | 性能验证 | FPS/内存/耗时基线 |
| M7 | Week 22-24 | 真实试用第一轮 | 试用记录与问题分类 |
| M8 | Week 25-27 | 问题闭环与可选 Web 评估 | 问题修复 + Web go/no-go |
| M9 | Week 28-30 | V1.0 收口 | 发布评估、门禁、交付 |

## 4. 详细计划

## M0：Week 1-3 文档真源重组与架构冻结

### 目标

- 把设计真源集中到 `02_设计`
- 完成新架构共识
- 完成 HTML 原型和说明

### 输出物

1. PRD
2. INT
3. DSN
4. TEC
5. 里程碑与实施计划
6. UI 架构原型

### done_when

- 文档路径已统一
- 团队能用“界面层 / 接口层 / 应用层 / 领域层 / 数据层”描述架构

## M1：Week 4-6 接口层骨架

### 目标

- 创建 contracts 目录
- 创建 facade 目录
- 把接口层从设计稿落到代码骨架

### 建议任务

1. 定义核心 DTO
2. 定义核心 Command/Result
3. 建立 5 个 Facade 骨架
4. 建立 BridgeContainer 或 Registry

### done_when

- 新页面开发不再要求直接往大 `QmlBridge` 里堆方法

## M2：Week 7-9 Workbench 域落地

### 目标

- 驾驶舱与项目工作台先切到新接口

### 建议任务

1. `WorkbenchFacade`
2. `WorkbenchBridge`
3. Dashboard DTO
4. Project Workspace DTO
5. 首页与工作台回归

### done_when

- 驾驶舱和项目工作台不再直接依赖旧总桥接逻辑

## M3：Week 10-12 Change 域落地

### 目标

- 变更中心切入新接口面

### 建议任务

1. `ChangeFacade`
2. `ChangeBridge`
3. 创建/流转命令对象
4. 变更详情 DTO
5. 时间线和验证摘要输出统一

### done_when

- 变更中心链路能以 Command/Result 表达完整动作

## M4：Week 13-15 Spec / Delivery / System 域落地

### 目标

- 规范中心、报告发布、系统设置进入新结构

### 建议任务

1. `SpecFacade`
2. `DeliveryFacade`
3. `SystemFacade`
4. 设置页/报告页/规范页统一接口

### done_when

- 主要全局页面全部脱离“直接绑多个 service”的扩展方式

## M5：Week 16-18 Bridge 收口与稳定化

### 目标

- 完成桥接层拆分
- 清理旧桥接遗留

### 建议任务

1. `QmlBridge` 减重
2. 清理过时说明
3. 更新 README 与设计图
4. 补足 bridge/facade 测试

### done_when

- `QmlBridge` 只保留装配或极少公共逻辑

## M6：Week 19-21 性能验证

### 目标

- 先拿到性能证据

### 建议任务

1. 万行变量表 FPS
2. 首屏加载时延
3. 大工作空间扫描时延
4. 内存基线记录

### done_when

- 有明确的性能报告，而不是体感判断

## M7：Week 22-24 真实试用第一轮

### 目标

- 让电气工程师按真实工作流试一轮

### 建议任务

1. 选试用项目
2. 试用场景脚本
3. 问题登记模板
4. 每周复盘

### done_when

- 至少形成一轮可归类的问题清单

## M8：Week 25-27 问题闭环与可选 Web 评估

### 目标

- 依据真实问题决定是否值得做 Web 试点

### 评估问题

1. 问题主要来自 UI 技术栈本身吗
2. 多端访问是刚需吗
3. HTTP/API 化是否会带来明确收益

### done_when

- 给出明确结论：`继续桌面主线` 或 `启动小范围 Web 试点`

## M9：Week 28-30 V1.0 收口

### 目标

- 完成 V1.0 发布评估

### 建议任务

1. 发布门禁检查
2. 试运行报告
3. 技术债梳理
4. 下一阶段 backlog 排序

### done_when

- 能形成一份面向实际使用的 V1.0 交付结论

## 5. 周度节奏建议

每周保持固定节奏：

1. 周初：确认本周目标与 done_when
2. 周中：实现 + 回归
3. 周末：更新 PM_SESSION + 问题复盘 + 下周预备

## 6. 风险控制点

| 周段 | 风险 | 控制方式 |
|------|------|---------|
| Week 4-9 | 接口定义过重 | Facade 只做编排，不复制领域规则 |
| Week 10-18 | 迁移回归 | 每个域迁移后做 focused regression |
| Week 19-24 | 性能/试用结果不理想 | 先分类问题，再决定是优化还是换技术 |
| Week 25-30 | 目标发散 | 以 V1.0 发布评估为唯一主线 |

## 7. 关键检查点

### Checkpoint A：Week 6

- 接口层骨架是否真正落地

### Checkpoint B：Week 12

- Workbench + Change 是否稳定迁移

### Checkpoint C：Week 18

- Bridge 是否已经收口

### Checkpoint D：Week 24

- 试用结果是否支持继续桌面主线

### Checkpoint E：Week 30

- 是否具备 V1.0 发布条件

## 8. 结论

30 周足够，但前提是：

1. 不在第 1 阶段就急着重做运行时
2. 真正以接口层为主线
3. 每个里程碑都必须有可验证输出物
