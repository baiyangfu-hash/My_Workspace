# 产品化收口与试用计划

> 2026-09-01 治理备注：本文是 `V1.1.x` 产品化阶段的历史计划。其“仓库边界、环境入口、治理负担”主线已被 `SYS-2026-001_WorkspaceGovernance` 驾驶舱迁移治理吸收；当前默认运行源码位于 `00_Infrastructure/auto_pm`，旧 `SW-2026-008` 目录保留为文档沉淀与回退来源。

## 1. 计划定位

本计划用于承接 auto-pm 当前阶段的产品化收口工作。

本轮主线不是继续扩展功能面，而是把项目从“功能强、流程重、主要适合作者本人使用的工程作业系统”，收敛为“环境可复现、边界清楚、流程轻重分级、可交给其他电气工程师试用的产品化工具”。

本计划覆盖未来 2-4 周，作为 `V1.1.x` 阶段的执行依据。

## 3. 总体策略

### 3.1 核心策略

1. 冻结大规模新功能，优先治理环境、门禁、文档和流程负担
2. 先澄清仓库边界和环境入口，再进行产品化表达
3. 保留 CHG / PM_SESSION / dogfooding 的价值，但降低日常摩擦
4. 把模块划分为 `core`、`optional`、`experimental` 三类，避免继续无边界膨胀
5. 先完成一次真实试用，再决定下一轮新增能力

### 3.2 非目标

- 本轮不启动大规模架构重写
- 本轮不推进 Web 化决策
- 本轮不继续扩张低频功能域
- 本轮不以“补齐所有历史问题”为目标

## 4. 阶段规划

## 4.1 阶段 0：冻结与基线确认

- 目标：确认当前真实状态，停止在不清晰边界上继续扩展
- 时间：0.5-1 天
- 任务：
  - 暂停新增功能，仅允许修复环境、门禁、文档和流程问题
  - 明确 `auto-pm` 当前 Git 边界与仓库策略
  - 解释 `git status` 为何显示外部 PLC 项目文件变化
  - 形成当前基线评估文档，沉淀版本、未提交改动、可运行命令和阻断项
- 交付物：
  - `00_项目管理/03_执行/当前基线评估.md`
- 验收标准：
  - 能明确回答仓库边界是什么
  - 能明确回答当前未提交修改包含哪些范围
  - 能明确回答当前门禁是否可运行，以及失败原因是什么

## 4.2 阶段 1：环境可复现性修复

- 目标：任何 AI、任何新机器、未来的维护者，都能按统一入口完成环境准备与健康检查
- 时间：1-2 天
- 任务：
  - 统一唯一受支持的开发环境路径，默认采用“项目内 `.venv` + Python 3.11”
  - 在 `uv` 与 `pip` 中确定唯一主安装路径，避免双轨文档
  - 修正 `README.md` 的安装路径与初始化步骤
  - 新增开发环境文档，说明 Windows 下初始化与排障步骤
  - 修复 `Taskfile.yml` 对裸 `python` 的依赖
  - 增加 `doctor` 级别环境健康检查入口
- 验收标准：
  - 新开 PowerShell 后可通过一条命令完成环境健康检查
  - `ruff check auto_pm/` 可运行
  - 快速测试入口可运行
  - 安装说明不再依赖隐含的作者本地环境

## 4.3 阶段 2：治理体系减负

- 目标：保留治理价值，降低日常使用摩擦
- 时间：2-3 天
- 任务：
  - 将 `PM_SESSION` 主文件收口到 ≤150 行，只保留活跃快照
  - 把历史内容归档到专用历史目录
  - 清理 `pm-workflow/SKILL.md` 的重复头部与重复说明
  - 将 CHG 流程明确分为“轻量 / 标准 / retrofit”三类
  - 为轻量变更单提供最小填写模板
  - 为 retrofit 设置占比监控与复盘阈值
- 验收标准：
  - `PM_SESSION` 主文件 ≤150 行
  - `pm-workflow/SKILL.md` 不再出现明显重复段
  - 小改动不再需要走论文式变更单

## 4.4 阶段 3：产品边界收口

- 目标：防止 auto-pm 继续膨胀为边界模糊的巨型工具
- 时间：2-4 天
- 任务：
  - 明确模块边界：`core / optional / experimental`
  - 梳理命令树，把高频命令前置，低频命令下沉
  - 为 Modbus、prototype 等低频能力评估插件化方向
  - 建立模块成熟度表：可用 / 试用 / 实验 / 暂停维护
  - 在 README 中直接呈现功能边界与模块状态
- 验收标准：
  - 新用户能快速分辨哪些能力稳定、哪些能力试验性强
  - 后续新增功能必须先声明归属模块级别

## 4.5 阶段 4：工程质量硬化

- 目标：让质量依赖自动化而不是仅依赖纪律
- 时间：3-5 天
- 任务：
  - 修复当前已知小问题，并核实哪些仍真实存在
  - 建立分层测试入口：`test-fast` / `test-cli` / `test-qml` / `test-full`
  - 把环境相关测试写入 `tmp_path` 或项目测试缓存
  - 减少 GUI 测试对全量回归的阻塞
  - 重新实测 ruff / mypy / pytest 并回写真实状态
- 验收标准：
  - 快速测试入口稳定通过
  - 测试不依赖用户 `home` 目录写权限
  - `PM_SESSION` 中的门禁声明来自实际运行结果
  - 已知待修复项减少到 0 个 P0 / P1

## 4.6 阶段 5：真实试用与产品化反馈

- 目标：从“作者自己好用”进入“真实电气工程师可试用”
- 时间：1-2 周
- 任务：
  - 选择 `DJ-2026-100_电气部门试用样例` 作为准真实试用场景
  - 设计 5 个核心试用任务
  - 输出 1 页试用说明
  - 建立结构化反馈表
  - 根据反馈分级为 P0 / P1 / P2 / P3
- 验收标准：
  - 至少完成 1 个真实或准真实用户试用
  - 形成 1 份试用报告
  - 下一轮变更来自真实反馈，而不是想象式扩展
