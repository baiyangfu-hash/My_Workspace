# V0.4.0 Week 2 单机设备模板 PoC 第二批迭代计划

> 状态真源：`PM_SESSION_SW-2026-008.md`
> 本轮决策：继续在 `plc-standard-project` 上增量扩展，不先拆独立 `plc-single-machine` 模板

## 1. 当前开发进度基线

- Week 1 已按方案 A 收口：首页继续保留项目列表页驾驶舱横幅。
- Week 2 第一批已完成 4 个关键元数据字段链路：`project_type`、`equipment_type`、`plc_vendor`、`plc_model`。
- 当前 `project create`、`.copier-answers.yml`、`.plc.json`、`project show`、GUI 新建项目对话框、项目概览页已能读写和展示上述字段。
- 代码发布基线保持为 `0.3.8`，本轮属于 `V0.4.0` 主线下的执行准备，不触发版本切换。
- `plc check` 对该 Python 项目仍会报 PLC 目录缺失，这一现象记录为口径风险，不作为本轮模板 PoC 的阻断项。

## 2. 本轮目标

将单机设备模板 PoC 从“元数据已通路”推进到“模板差异成形”，让团队可以基于现有 `plc-standard-project` 快速验证单机项目的目录、文档和样例资产是否足够支撑后续 Week 3 资产台帐能力。

## 3. 范围边界

### 3.1 本轮包含

- 在 `plc-standard-project` 内补齐单机设备项目的最小目录差异。
- 明确单机模板所需的文档骨架和示例资产占位。
- 完成至少 1 次真实创建验证，确认创建结果与 `project show`/GUI 展示口径一致。
- 形成是否需要拆分独立模板的判定标准，而不是凭直觉做结构分叉。

### 3.2 本轮不包含

- 不立即创建独立 `plc-single-machine` 模板。
- 不做数据库 schema 迁移。
- 不进入 Week 3 的 PLC 资产读取与检查实现。
- 不同步推进 `V2.2~V2.5` 中长期 backlog。

## 4. 执行策略

### 4.1 决策

- 先扩现有模板，避免在 PoC 尚未收敛时过早引入模板分叉维护成本。
- 以“真实创建样例可用”作为第二批的核心验收口径，而不是仅完成静态目录设计。
- 本轮结束时输出“继续沿用单模板”或“准备拆独立模板”的明确判据，供后续 Week 2 收口时决策。

### 4.2 判定标准

若以下 3 条同时满足，则暂不拆模板：

1. 单机目录差异可以通过现有模板增量表达，且不引入难以维护的条件分支。
2. 文档骨架和示例资产不会明显影响其他 PLC 项目类型。
3. `project create` 创建后的产物对使用者而言已经足够直观，不需要模板名级别的独立认知。

若任一条件不满足，则在 Week 2 收口时升级为独立模板决策项。

## 6. 风险与依赖

- `projects` 表尚未新增独立列，4 个 Week 2 字段仍通过 `extra` 透传；本轮可接受，但若后续要做筛选/统计，需再评估 schema 迁移。

- 模板条件分支若过多，会削弱 `plc-standard-project` 的可维护性；需在实现前保持“最小增量”原则。
- Week 3 资产能力依赖本轮预埋的目录/文件命名口径，本轮若命名失控，会把问题带入后续资产读取。
