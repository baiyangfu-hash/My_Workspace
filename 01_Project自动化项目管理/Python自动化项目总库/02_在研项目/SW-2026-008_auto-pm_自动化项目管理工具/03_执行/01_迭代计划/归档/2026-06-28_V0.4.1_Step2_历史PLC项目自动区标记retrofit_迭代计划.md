## 2. 本轮目标

为历史 PLC 项目提供 `auto-pm doc inject <project_id> [--dry-run|--json]` 命令，自动检测缺失的 AUTO_PM:BEGIN/END 标记并在锚点标题后插入完整 marker block（含资产数据填充），让历史项目立即可用 `doc refresh` 持续维护。同时通过 CHG-074 dogfooding 闭环验证变更管理流程对"新增 CLI 命令 + 新增服务 + 新增测试"中等规模变更的支撑能力。

## 3. 范围边界

### 3.1 本轮包含

- 新增 `DocInjectService` 类（`auto_pm/core/doc_inject_service.py`），独立于 `DocRefreshService`，通过组合复用其 builder 方法和 `_locate_target_docs` / `_load_asset_data`
- 新增 `auto-pm doc inject <project_id> [--dry-run|--json]` CLI 子命令
- 注入逻辑核心：
  - 对每个目标文档（016 和 015），遍历 3 个 marker key
  - 若 marker 已存在，跳过并报告（避免重复注入）
  - 若 marker 不存在，查找锚点标题；找到则在锚点后第一个空行处插入完整 marker block（BEGIN/END 标记 + 资产数据填充内容）；找不到则报告 issue 跳过
- `--dry-run` 预览模式：仅输出将注入的内容，不写入
- `--json` JSON 输出模式：返回结构化 `DocInjectResult`
- 边界处理：项目不存在 / 非 PLC 项目 / 锚点缺失 / 已存在 marker 跳过 / 文档读取失败
- 单元测试覆盖：标准注入（无 marker）/ 部分 marker 已存在 / 锚点缺失 / dry-run / 原手工内容保留 / JSON 输出
- CLI 集成测试：dry-run / 实际写入 / 创建后注入
- 创建 CHG-SCPT-2026-074 走 dogfooding 第 7 次闭环（draft→closed）

### 3.2 本轮不包含

- **不修改 `DocRefreshService` 的现有行为**（保持向后兼容，只组合复用）
- **不修改 `doc refresh` 命令**（保持单一职责：替换已有标记内容）
- **不扩展到 Python 项目**（Python 项目无 PLC 文档标记需求）
- **不批量处理多个项目**（一次只处理一个项目，避免误操作）
- **不强制注入**（锚点缺失时报告 issue，不强行 append 到文档末尾）
- **不进入 V0.4.1 Step 3**（Python 项目 `plc check` 不适用口径补齐）
- **不偿还 TD-A02 / TD-TC01**

## 4. 执行策略

### 4.1 决策

- **职责分离**：`DocRefreshService` 只替换已有标记内容（安全操作）；`DocInjectService` 只插入新标记（结构性修改）。两者通过组合复用相同的 `_build_*_block` 方法，避免代码重复
- **插入策略**：找到锚点标题（如 `## 2. IO 总览`）后的第一个空行处，插入完整 marker block（BEGIN 标记 + 资产数据填充内容 + END 标记）。原手工内容保留在 END 标记之后，**不丢失**
- **数据填充**：注入时立即用工程资产数据（`io_points.csv` / `program_blocks.yml` / `communications.yml`）填充内容，与 `doc refresh` 行为一致。用户若不想用资产数据，可手工删除标记区块
- **锚点匹配**：用前缀正则匹配（如 `^##\s+2\.\s*IO` 匹配 `## 2. IO 总览` / `## 2. IO 概览` 等变体），提高历史文档兼容性
- **dogfooding 先行**：CHG-074 在实施前创建并流转到 `approved`，实施完成后流转到 `closed`

### 4.2 数据流

```
DocInjectService.inject_markers(project, dry_run)
    ↓
    asset_data = self._refresh_service._load_asset_data(project.path)
    target_docs = self._refresh_service._locate_target_docs(project.path)
    ↓
    For each (doc_path, block_builders) in target_docs:
        content = read_file(doc_path)
        For each (block_key, builder_name) in block_builders:
            if self._has_marker(content, block_key):
                skip + report "marker 已存在"
            else:
                anchor_pos = self._find_anchor(content, block_key)
                if anchor_pos is None:
                    report issue "锚点缺失: <heading>"
                else:
                    body = getattr(self._refresh_service, builder_name)(project, asset_data)
                    block = f"<!-- AUTO_PM:BEGIN {block_key} -->\n{body}\n<!-- AUTO_PM:END {block_key} -->\n"
                    content = self._insert_after_anchor(content, anchor_pos, block)
        write_file(doc_path, content) if changed and not dry_run
```

## 6. 风险与依赖

- **锚点标题变更风险**：历史项目的 PLC 文档可能修改了锚点标题（如把 `## 2. IO 总览` 改为 `## 2. IO 概览`）。缓解：用宽松正则前缀匹配（`^##\s+2\.\s*IO`），找不到时报告 issue 不强行注入
- **手工内容丢失风险**：原手工内容会被推到 END 标记之后，但用户运行 `doc refresh` 后只刷新 BEGIN/END 之间的内容，原手工内容不会被破坏。仍需在文档中明确告知用户
- **dogfooding 风险**：第7次闭环，规模稍大（新命令+新服务+测试），但流程已稳定6次，风险可控
- **依赖**：本轮依赖 `DocRefreshService._build_*_block` 方法的稳定性（不修改原服务，通过组合复用）；依赖 `write_file` 的原子写入能力（V0.3.8 TD-T11 已修复）
- **测试可见性**：offscreen 模式下不涉及 UI 测试，本轮无相关风险
