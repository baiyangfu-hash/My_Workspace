# V9.0 需求对齐文档

## 1. 文档目的

本文档基于HTML UI原型和代码诊断结果，对齐每个UI模块的交互流程和数据依赖，明确开发优先级和需要修复的后端问题。

## 2. UI模块交互流程与数据依赖

### 2.1 项目总览 Dashboard

**交互流程**:
1. 用户打开工具 → 显示空状态引导页
2. 用户点击"选择工作空间" → 弹出目录选择对话框
3. 选择目录后 → 调用 `mount_workspace(path)` → 触发 `workspace_opened` 事件
4. 前端收到事件 → 调用 `get_dashboard_stats(path)` 获取统计概览
5. 同时调用 `get_dashboard_data(path)` 获取项目列表
6. 渲染统计卡片 + 项目卡片网格

**数据依赖**:

| UI元素 | 数据字段 | API调用 | 后端Service | 数据来源 |
|--------|----------|---------|-------------|----------|
| 项目总数 | total_projects | get_dashboard_stats(wsPath) | WorkspaceDashboardService | 扫描工作空间目录 |
| 平均健康度 | avg_health_score | get_dashboard_stats(wsPath) | WorkspaceDashboardService | _compute_health_score() |
| 文档完成率 | avg_doc_coverage | get_dashboard_stats(wsPath) | WorkspaceDashboardService | spec_count/8*100 |
| 待处理变更单 | pending_changes | get_dashboard_stats(wsPath) | WorkspaceDashboardService | ChangeServiceV2查询 |
| 命名冲突 | naming_conflicts | get_dashboard_stats(wsPath) | WorkspaceDashboardService | detect_naming_conflicts() |
| 项目名称 | projects[].name | get_dashboard_data(wsPath) | WorkspaceDashboardService | .plc_project.json |
| 项目类型 | projects[].project_type | get_dashboard_data(wsPath) | WorkspaceDashboardService | .plc_project.json |
| 健康度评分 | projects[].health_score | get_dashboard_data(wsPath) | WorkspaceDashboardService | _compute_health_score() |
| 文档完成率 | projects[].doc_coverage | get_dashboard_data(wsPath) | WorkspaceDashboardService | spec_count/8*100 |
| 规范合规率 | projects[].spec_compliance | get_dashboard_data(wsPath) | WorkspaceDashboardService | FB_/FC_前缀比例 |
| 最后更新 | projects[].last_updated | get_dashboard_data(wsPath) | WorkspaceDashboardService | 文件mtime |

**需修复的后端问题**:
- P1: APIGateway每次new Service实例 → Dashboard缓存丢失 → 每次全量扫描
- TD-5: WorkspaceDashboardService无缓存 → 大型工作空间性能差

### 2.2 项目详情页

**交互流程**:
1. 用户从Dashboard点击项目卡片 → 调用 `get_project_overview(path)` 获取项目概览
2. 渲染五块信息卡片 + 变更台账
3. 用户切换到"项目结构"Tab → 调用 `list_directory_tree(path)` 获取文件树
4. 用户切换到"变更管理"Tab → 跳转到变更管理中心

**数据依赖**:

| UI元素 | 数据字段 | API调用 | 后端Service | 数据来源 |
|--------|----------|---------|-------------|----------|
| 项目名称 | business_identity.project_name | get_project_overview(path) | ProjectService | .plc_project.json |
| 项目编号 | business_identity.project_code | get_project_overview(path) | ProjectService | .plc_project.json |
| 业务线 | business_identity.business_line | get_project_overview(path) | ProjectService | .plc_project.json |
| PLC平台 | tech_environment.plc_platform | get_project_overview(path) | ProjectService | .plc_project.json |
| CPU型号 | tech_environment.cpu_model | get_project_overview(path) | ProjectService | .plc_project.json |
| FB/FC/DB/OB数量 | engineering_scale.* | get_project_overview(path) | ProjectService | 扫描ST文件 |
| 健康度评分 | project_status.health_score | get_project_overview(path) | ProjectService | DiagnosticService |
| 文档完成率 | project_status.doc_coverage | get_project_overview(path) | ProjectService | 文件存在性检查 |
| 变更台账 | changes[] | list_change_requests(path, limit=8) | ChangeServiceV2 | CHG-*.md文件 |
| 文件树 | tree | list_directory_tree(path) | ProjectService | os.scandir() |

**需修复的后端问题**: 无（当前数据链路通畅）

### 2.3 变更管理中心

**交互流程**:
1. 用户进入变更管理中心 → 调用 `list_change_requests(path, filters)` 获取变更列表
2. 用户点击"新建变更单" → 打开4步向导
3. Step1: 选择项目 → 从Dashboard数据获取项目列表
4. Step2: 二维分类 → 前端本地枚举（ChangeDomain/ChangeNature/ChangeScope）
5. Step3: 变更信息 → 前端表单
6. Step4: 预览确认 → 调用 `create_change_request_v2(params)` ❌IPC链路断裂
7. 用户点击"推进状态" → 调用 `transition_change_status_v2(change_id, new_status, reason)`

**数据依赖**:

| UI元素 | 数据字段 | API调用 | 后端Service | 数据来源 | 状态 |
|--------|----------|---------|-------------|----------|------|
| 变更列表 | items[] | list_change_requests(path, filters) | ChangeServiceV2 | CHG-*.md | ✅可用 |
| 创建变更单V2 | - | create_change_request_v2(params) | ChangeServiceV2 | 写入CHG-*.md | ❌IPC断裂 |
| 状态流转 | - | transition_change_status_v2(id, status, reason) | ChangeServiceV2 | 更新CHG-*.md | ✅可用 |
| 变更统计 | statistics | get_change_statistics(path) | ChangeServiceV2 | 聚合计算 | ✅可用 |
| 导出报告 | - | export_change_report(params) | ChangeServiceV2 | 生成Markdown | ✅可用 |

**需修复的后端问题**:
- P2: 前端IPC.call('create_change_request_v2')的域名前缀拼接与WebViewBridge方法名不一致
- 修复方案: 在WebViewBridge中添加 `change_create_change_request_v2` 别名方法，或修改前端IPC调用方式

### 2.4 规范检查面板

**交互流程**:
1. 用户选择项目 → 调用 `get_checkers()` 获取检查器列表
2. 用户勾选检查器 → 点击"运行检查"
3. 调用 `run_spec_check(path, checker_ids)` → 返回检查结果
4. 渲染违规列表 + 修复建议

**数据依赖**:

| UI元素 | API调用 | 后端Service | 状态 |
|--------|---------|-------------|------|
| 检查器列表 | get_checkers() | SpecCheckerService | ✅可用 |
| 运行检查 | run_spec_check(path, ids) | SpecCheckerService | ✅可用 |

### 2.5 诊断面板

**交互流程**:
1. 用户选择项目 → 点击"运行诊断"
2. 调用 `run_diagnosis(path)` → 返回诊断报告
3. 渲染健康度评分 + 问题列表

**数据依赖**:

| UI元素 | API调用 | 后端Service | 状态 |
|--------|---------|-------------|------|
| 运行诊断 | run_diagnosis(path) | DiagnosticService | ✅可用 |

## 3. 开发优先级与依赖关系

### 3.1 优先级排序

| 优先级 | 模块 | 前置条件 | 依赖修复 |
|--------|------|----------|----------|
| **P0-1** | APIGateway单例化 | 无 | 修复P1 |
| **P0-2** | IPC调用链路统一 | P0-1完成 | 修复P2 |
| **P0-3** | get_templates补全 | 无 | 修复P3 |
| **P1-1** | Dashboard缓存机制 | P0-1完成 | 修复TD-5 |
| **P1-2** | 变更管理V2创建修复 | P0-2完成 | 验证P2修复 |
| **P1-3** | Mock数据格式对齐 | P0-1完成 | 修复P4 |
| **P2-1** | 变更管理完整UI | P1-2完成 | - |
| **P2-2** | Dashboard性能优化 | P1-1完成 | - |
| **P3-1** | 增强功能 | P2完成 | - |

### 3.2 依赖关系图

```
P0-1 APIGateway单例化 ──→ P1-1 Dashboard缓存 ──→ P2-2 Dashboard优化
    │
    └──→ P0-2 IPC链路统一 ──→ P1-2 变更V2修复 ──→ P2-1 变更完整UI ──→ P3-1 增强

P0-3 get_templates补全 (独立)

P1-3 Mock数据对齐 (依赖P0-1)
```

## 4. 需修复的后端问题及对前端的影响

| # | 后端问题 | 影响的前端模块 | 影响描述 | 修复后前端需调整 |
|---|----------|---------------|----------|-----------------|
| P1 | APIGateway每次new Service | Dashboard | 每次刷新全量扫描，3秒指标无法达成 | 无需调整，后端修复即可 |
| P2 | IPC调用链路断裂 | change-wizard.js | V2创建变更单不可用 | 可能需调整IPC调用方式 |
| P3 | get_templates缺失 | document-editor.js | 文档生成不可用 | 无需调整，后端补全即可 |
| P4 | Mock数据格式不一致 | 所有模块 | Mock/真实模式切换崩溃 | 无需调整，后端对齐即可 |
| TD-5 | Dashboard无缓存 | Dashboard | 大型工作空间加载慢 | 无需调整，后端添加缓存即可 |
