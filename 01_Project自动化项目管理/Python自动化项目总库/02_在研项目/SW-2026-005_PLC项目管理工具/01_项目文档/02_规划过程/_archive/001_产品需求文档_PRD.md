# 产品需求文档（PRD）- V6.1.0 实用性重构版

## 1. Executive Summary

### 1.1 Problem Statement

**现状问题**: 用户反馈"现在的功能有哪个可以用？可以合理的使用？我没发现哪里可以正常在项目中使用"

**根本原因分析**:
1. **功能碎片化**: V2.1~V4.0 版本累计了 15+ 功能模块，但缺乏清晰的主线流程引导
2. **实用性不足**: 虽然技术架构完整（60+ IPCBridge API, 15个Service模块），但用户无法在真实工作流中找到切入点
3. **缺少核心场景**: 没有针对 PLC 工程师日常工作的"第一屏"体验——打开工具后能立即看到什么、能做什么
4. **变更管理缺失**: Git 对 PLC 程序的变更追踪粒度不够（一个工作空间多个项目 Git 就乱掉了），但现有 ChangeService 仅提供基础 CRUD

### 1.2 Proposed Solution

**V6.1.0 核心策略**: 聚焦两大实用功能，打造"打开即用"的第一屏体验

| 优先级 | 功能模块 | 解决的核心痛点 | 用户价值 |
|--------|----------|----------------|----------|
| **P0** | **项目总览 Dashboard** | 一眼看到所有 PLC 项目状态 | 健康度/文档完成度/规范合规率一目了然 |
| **P0** | **变更管理 Center** | PLC 程序变更细节追踪 | 弥补 Git 不足，遵循 PM-042 规范的完整变更流程 |

**设计原则**:
- ✅ **保留手动选择工作空间**（不自动扫描，尊重用户习惯）
- ✅ **变更管理模块参考全局规范 PM-042 和 CHG-040 实现**
- ✅ **先完善 PRD 文档，再实施开发**（避免盲目编码）
- ✅ **每个功能必须有明确的"使用场景→操作步骤→预期结果"闭环**

### 1.3 Success Criteria（可量化验收标准）

| 维度 | 指标 | 目标值 | 测量方法 |
|------|------|--------|----------|
| **功能性** | 项目总览能在 3 秒内展示工作空间全貌 | ≤ 3 秒 | 计时测试 |
| **功能性** | 变更单从创建到归档的全流程可走通 | 100% 路径覆盖 | 手工走查 + 自动化测试 |
| **易用性** | 新用户能在 5 分钟内完成第一个变更单创建 | ≤ 5 分钟 | 用户测试 |
| **规范性** | 变更单数据结构 100% 符合 CHG-040 模板 | 100% 字段覆盖率 | 数据模型对比检查 |
| **兼容性** | 不破坏现有 IPCBridge API 的向后兼容性 | 0 breaking changes | API 回归测试 |

## 2. User Experience & Functionality

#### 主要用户: PLC 工程师（电气工程师）

| 属性 | 描述 |

#### US-02: 创建变更单（P0）

**作为** PLC 工程师，
**我希望** 在修改 PLC 程序后，能快速创建符合 PM-042 规范的变更单，
**以便** 记录本次变更的原因、内容、影响范围并获得审批。

**Acceptance Criteria:**

| 编号 | 验收标准 | 优先级 | 验证方法 |
|------|----------|--------|----------|
| AC-02.1 | 变更单表单包含 CHG-040 模板的全部必填字段（编号/领域/性质/范围/申请人/原因/内容） | Must | 字段清单核对 |
| AC-02.2 | 技术领域支持 7 种选择（ELEC/MECH/PLC/HMI/SCPT/DOCU/SAFE），默认选中 PLC | Must | 表单验证 |
| AC-02.3 | 业务性质支持 5 种选择（REQ/DEF/OPT/CFG/EMRG），默认选中 DEF | Must | 表单验证 |
| AC-02.4 | 影响范围支持 5 级多选（LOCAL/MODULE/SYSTEM/CROSS/SAFE），默认选中 LOCAL | Must | 表单验证 |
| AC-02.5 | 变更编号自动生成，格式为 `CHG-[领域]-YYYY-XXX`（如 CHG-PLC-2026-001） | Must | 自动化测试 |
| AC-02.6 | 变更单保存为 Markdown 文件，存放在 `{project}/01_项目管理/04_变更管理/01_变更单/` 目录下 | Must | 文件系统检查 |
| AC-02.7 | 保存成功后自动更新版本变更台帐（追加一行引用记录） | Should | 台帐文件检查 |

**变更单创建流程:**

```
用户点击[新建变更单]
    ↓
ChangeRequestDialog.show()
    ├── Step 1: 选择关联项目（从当前工作空间项目列表中选择）
    ├── Step 2: 填写二维分类
    │   ├── 技术领域（单选，默认 PLC）
    │   ├── 业务性质（单选，默认 DEF）
    │   └── 影响范围（多选，默认 LOCAL）
    ├── Step 3: 填写变更信息
    │   ├── 变更原因（文本框，必填）
    │   ├── 变更前状态（涉及文件/参数/截图）
    │   ├── 变更后状态（目标文件/预期效果）
    │   └── 影响分析（可选，CROSS/SAFE 时必填）
    ├── Step 4: 预览并确认
    │   ├── 显示完整变更单预览（Markdown 渲染）
    │   ├── 自动编号显示（如 CHG-PLC-2026-003）
    │   └── [保存草稿] 或 [提交审批]
        ↓
ChangeService.create_change_request(params)
    ├── 验证必填字段
    ├── 生成变更编号（查询同领域最大序号+1）
    ├── 渲染 CHG-040 模板 → Markdown 内容
    ├── 写入文件系统 `{project}/.../CHG-PLC-2026-003.md`
    ├── 更新版本变更台帐
    └── 返回成功 + emit("change_request_created")
        ↓
UI 刷新:
    ├── Dashboard 待处理变更单计数 +1
    ├── 变更列表新增一条记录
    └── Toast 提示 "变更单 CHG-PLC-2026-003 已创建"
```

#### US-03: 变更单状态流转（P0）

**作为** PLC 工程师 / 项目经理，
**我希望** 能跟踪变更单从创建到归档的完整生命周期，
**以便** 掌握变更进度、及时审批或处理异常。

**Acceptance Criteria:**

| 编号 | 验收标准 | 优先级 | 验证方法 |
|------|----------|--------|----------|
| AC-03.1 | 支持 PM-042 定义的 12 种状态：pending_analysis → analyzing → ... → completed → archived | Must | 状态机测试 |
| AC-03.2 | 状态转换遵循规范流程（不能跳跃，拒绝/打回需记录原因） | Must | 业务规则测试 |
| AC-03.3 | 变更列表支持按状态筛选（待评估/审批中/实施中/已完成等） | Should | 交互测试 |
| AC-03.4 | 审批操作记录审批人/意见/时间，且不可删除只能追加 | Must | 数据完整性测试 |
| AC-03.5 | 验收不通过时可回退到实施中状态，并记录回退原因 | Should | 异常流程测试 |

**状态流转图（遵循 PM-042 §5.2）:**

```
pending_analysis (待评估)
    ↓ [开始评估]
analyzing (评估中)
    ↓ [评估通过] / [评估拒绝 → rejected]
pending_approval (待审批)
    ↓ [开始审批]
approving (审批中)
    ↓ [审批通过] / [审批拒绝 → rejected]
pending_implementation (待实施)
    ↓ [开始实施]
implementing (实施中)
    ↓ [实施完成]
pending_acceptance (待验收)
    ↓ [开始验收]
accepting (验收中)
    ↓ [验证通过] / [验证不通过 → implementing]
completed (已完成)
    ↓ [归档] / [关闭]
archived (已归档) / closed (已关闭)

rejected (已拒绝) → closed (已关闭)
```

### 3.2 Integration Points（与现有 Service 层的集成方式）

#### 3.2.1 项目总览集成

| 现有 Service | 集成方式 | 复用能力 |
|-------------|----------|----------|
| `ProjectService.load_workspace_from_path()` | 直接调用 | 工作空间加载 |
| `ArtifactRegistryService.scan_workspace_subprojects()` | 直接调用 | 子项目识别 |
| `LibraryService.get_library_summary()` | 直接调用 | 共享库统计 |
| `WorkspaceService.get_workspace_statistics()` | 直接调用 | 汇总统计 |
| `DiagnosticService.run_diagnosis()` | 按需调用 | 健康度评分（缓存结果） |
| `SpecCheckerService.run_checks()` | 按需调用 | 规范合规率（缓存结果） |

**性能优化策略:**
- 首次加载工作空间时触发后台预计算（线程池异步执行）
- 健康度/合规率结果缓存 5 分钟，避免重复计算
- 大型工作空间（>20 项目）采用懒加载：先显示骨架屏，数据就绪后填充

#### 3.2.2 变更管理集成

| 现有 Service | 集成方式 | 改动范围 |
|-------------|----------|----------|
| `ChangeService` | **升级为 ChangeServiceV2** | 扩展方法签名，保持向后兼容 |
| `DocumentService` | 直接调用 | 变更单 Markdown 渲染与保存 |
| `ProjectService` | 直接调用 | 关联项目信息读取 |
| `TemplateService` | 直接调用 | 加载 CHG-040 模板 |

**向后兼容保证:**
```python
# 旧 API 保持可用（标记为 @deprecated）
class ChangeService:
    @deprecated("Use ChangeServiceV2 instead")
    def create_change_request(self, params): ...
```

```python
class ChangeRequest:
```
