# 技术设计文档（DES）- V1.4.0

## 1. 概述

### 1.1 文档目的

本文档基于 PRD V8.0.0，定义 PLC 项目管理工具的完整技术方案，包括架构、模块设计、接口定义、数据模型和开发路线。

### 1.2 技术路线

**先 Service 后 UI**：先实现纯 Python Service 层（可用 CLI 验证），再补 UI。

| 阶段 | 交付物 | 验证方式 |
|------|--------|----------|
| Phase 1a | Service 层 + CLI | 命令行调用验证 |
| Phase 1b | UI 层 (PyWebView) | 浏览器交互验证 |
| Phase 2 | 变更管理 Service + UI | 端到端验证 |

**UI 框架选择**: PyWebView（延续现有方案，但简化 IPC 层）

### 1.3 设计原则

1. **数据来自文档**: 所有展示数据从 Markdown 文件解析，0 个硬编码
2. **Service 独立于 UI**: Service 层不依赖 PyWebView，可独立测试
3. **规范是基准**: 工具按规范校验数据，不符合规范的数据必须修正，工具不迁就非规范格式
4. **最小依赖**: 仅依赖 Python 标准库 + pywebview，不引入数据库/ORM

## 4. 解析器设计

### 4.1 ProjParser（立项表解析器）

**输入**: `*_项目立项表_PROJ-*.md` 文件路径
**输出**: `ProjectInfo` 数据对象

**解析策略**:

1. **章节定位**: 按 `## N. 标题` 正则匹配章节
2. **表格解析**: 解析 Markdown 表格为 `{字段名: 值}` 字典
3. **字段匹配**: 按 `**加粗字段名**` 匹配表格第一列
4. **容错处理**:
   - 字段缺失 → 返回 `"待补充"`
   - 值为 `（待补充）`/`（待扫描统计）` → 返回 `"待补充"`
   - 表格格式异常 → 跳过该字段

**核心解析逻辑**:

```python
class ProjParser:
    """立项表 Markdown 解析器"""

    # 章节标题 → 解析方法映射
    SECTION_MAP = {

        "4": "parse_tech_environment",     # §4 技术环境

        "6": "parse_engineering_status",   # §6 工程状态
        "7": "parse_change_ledger",        # §7 变更台账
        "附录 A": "parse_appendix_a",       # 附录A 资源与风险
    }

    def parse(self, file_path: str) -> ProjectInfo:
        """解析立项表文件，返回 ProjectInfo"""
        ...

    def _split_sections(self, content: str) -> dict[str, str]:
        """按 ## N. 标题 拆分章节"""
        ...

    def _parse_table(self, section_text: str) -> dict[str, str]:
        """解析 Markdown 表格为 {字段名: 值} 字典"""
        ...

    def _clean_value(self, value: str) -> str:
        """清理字段值：去除加粗标记、占位符等"""
        ...
```

**表格解析规则**:

立项表中的表格格式为:

```markdown
| 字段 | 内容 |
|------|------|
| **项目名称** | DJ-2026-005 边框缓存机 V1.0.0 |
| **业务描述** | 边框缓存机是一种... |
```

解析步骤:
1. 按 `|` 分割每行
2. 跳过表头行和分隔行 (`|---|---|`)
3. 第一列去除 `**` 加粗标记作为 key
4. 第二列作为 value
5. value 中去除 Markdown 格式（加粗、链接等）

### 4.2 ChgParser（变更单解析器）

**输入**: `CHG-*.md` 文件路径
**输出**: `ChangeRequest` 数据对象

**解析策略**:

1. 与 ProjParser 相同的章节定位 + 表格解析
2. **领域提取**: 从文件路径 `CHG-{DOMAIN}/` 提取 domain
3. **影响范围提取**: 解析 `☑` 标记的行
4. **状态推断**: 从 §8 审批结论推断当前状态
5. **规范校验**: 解析完成后校验结构完整性，违规项输出 WARNING 日志

**规范校验规则**（`_validate_spec_compliance`）:

| 校验项 | 规则 | 违规级别 |
|--------|------|----------|
| §3 章节存在 | 必须有 §3 变更基本信息 | WARNING |
| §3 子章节完整 | 必须包含 3.0~3.4 | WARNING |
| §4 章节存在 | 必须有 §4 变更原因 | WARNING |
| §8 章节存在 | 必须有 §8 变更审批 | WARNING |
| 枚举值合法 | domain/nature/scope 必须在 spec_constants 允许值内 | WARNING |
| 必填字段非空 | change_number、project_id 不能为空 | WARNING |

**注意**: 解析时不抛异常，仅记录警告。不符合规范的变更单应修正数据源，而非让解析器跳过。

**状态推断规则**:

| 审批结论 | 实施记录 | 验证结论 | 推断状态 |
|----------|----------|----------|----------|
| 无审批 | 无 | 无 | draft |
| 有审批，通过 | 无 | 无 | approved |
| 有审批，驳回 | - | - | rejected |
| 有审批，通过 | 有实施记录 | 无 | implementing |
| 有审批，通过 | 有实施记录 | 部分通过 | implementing |
| 有审批，通过 | 有实施记录 | 全部通过 | completed |
| 有审批，通过 | 有实施记录 | 全部通过 + 关闭 | closed |

### 5.3 变更管理全流程门禁

**设计意图**: 变更管理不是简单的状态机，而是规范驱动的标准工作流。每个流转节点都有门禁条件，门禁条件来自 CHG-040 规范，不满足条件不允许流转。

#### 5.3.1 流转门禁表

| 流转 | 前置条件（变更单必须已填写的内容） | 审批要求 |
|------|------|------|
| draft → submitted | §3 全部子章节(3.0~3.4)已填写 + §4 变更原因非空 | 无（申请人自己提交） |
| submitted → under_review | 无额外条件 | 系统自动进入 |
| under_review → approved | §8.1 至少一条审批记录 + approver 非空 | 由 §3.3 影响范围决定（见下表） |
| under_review → conditionally_approved | §8.1 至少一条审批记录 + approver 非空 + comment 非空（附条件） | 同 approved |
| under_review → rejected | §8.1 至少一条审批记录 + approver 非空 + comment 非空（附原因） | 同 approved |
| approved → implementing | §7 实施计划至少一条任务 | 无 |
| conditionally_approved → implementing | §7 实施计划至少一条任务 + 附加条件已满足 | 无 |
| implementing → completed | §9 至少一条实施记录 + §10.1 至少一条验证项 + §10.2 验证结论为"全部通过" | 无 |
| completed → closed | 无额外条件 | 无 |
| rejected → draft | 无额外条件 | 无（退回修改） |

#### 5.3.2 审批要求（由 §3.3 影响范围决定）

| 影响范围 | 审批人角色 | 说明 |
|----------|-----------|------|
| LOCAL | 项目经理 | 仅单个POU/画面/IO点 |
| MODULE | 项目负责人 | 单个设备/单条线 |
| SYSTEM | 技术总监 | 多模块联动/联锁逻辑 |
| CROSS | 高层管理层 | PLC+HMI+电气多领域联动 |
| SAFE | 安全负责人 + 高层联合 | 急停/SIL/安全功能 |

> **注**: 当前阶段（Phase 1）工具仅校验 approver 非空，不校验审批人角色权限（角色权限体系需与组织架构集成，Phase 2 考虑）。

#### 5.3.3 门禁校验实现

```python
# src/models/spec_constants.py 新增

class TransitionGuardError(ValueError):
    """变更单内容不满足流转前置条件"""

# src/services/change_management_service.py 新增

def _check_transition_guards(self, cr: ChangeRequest, target_status: str) -> None:
    """检查流转门禁条件

    读取变更单当前内容，校验是否满足目标状态的前置条件。
    不满足则抛 TransitionGuardError，列出所有未满足的条件。
    """
    guards = TRANSITION_GUARDS.get(target_status, [])
    violations = []
    for guard in guards:
        if not guard.check(cr):
            violations.append(guard.message)
    if violations:
        raise TransitionGuardError(
            f"变更单 {cr.change_number} 不满足 '{target_status}' 的门禁条件:\n"
            + "\n".join(f"  - {v}" for v in violations)
        )
```

#### 5.3.4 门禁校验与规范校验的关系

| 校验类型 | 触发时机 | 失败行为 | 目的 |
|----------|----------|----------|------|
| 规范校验 (SpecViolationError) | 创建时 + 解析时 | 创建拒绝 / 解析WARNING | 数据格式合法 |
| 门禁校验 (TransitionGuardError) | 状态流转时 | 流转拒绝 | 流程合规 |
| 结构校验 (_validate_spec_compliance) | 解析时 | WARNING日志 | 文档结构完整 |

三者互补，共同确保变更管理全流程符合 CHG-040 规范。

## 7. Bridge 层设计

### 7.1 WebViewBridge

**功能**: 将 Service 层方法暴露给前端 JS 调用。

```python
class WebViewBridge:
    """PyWebView IPC 桥接层"""

    def __init__(self, workspace_root: str):
        self._overview_svc = ProjectOverviewService(workspace_root)
        self._change_svc = ChangeManagementService(workspace_root)

    # ---- 项目总览 API ----

    def get_workspace_projects(self) -> list[dict]:
        """返回所有项目概览（序列化为 dict）"""
        projects = self._overview_svc.get_workspace_projects()
        return [asdict(p) for p in projects]

    def get_project_detail(self, project_id: str) -> dict:
        """返回项目详情"""
        info = self._overview_svc.get_project_detail(project_id)
        return asdict(info)

    def get_project_changes(self, project_id: str) -> list[dict]:
        """返回项目变更单列表"""
        changes = self._overview_svc.get_project_changes(project_id)
        return [asdict(c) for c in changes]

    def refresh_cache(self, project_id: str | None = None) -> None:
        """强制刷新缓存"""
        self._overview_svc.refresh(project_id)

    # ---- 变更管理 API ----

    def create_change_request(self, project_id: str, **fields) -> dict:
        """创建变更单"""
        cr = self._change_svc.create_change_request(project_id, **fields)
        return asdict(cr)

    def list_change_requests(self, project_id: str, **filters) -> list[dict]:
        """列出变更单"""
        changes = self._change_svc.list_change_requests(project_id, **filters)
        return [asdict(c) for c in changes]

    def get_change_request(self, change_number: str) -> dict:
        """获取变更单"""
        cr = self._change_svc.get_change_request(change_number)
        return asdict(cr)

    def transition_status(self, change_number: str, new_status: str, **kwargs) -> dict:
        """状态流转"""
        cr = self._change_svc.transition_status(change_number, new_status, **kwargs)
        return asdict(cr)
```

**与旧版 APIGateway 的关键区别**:
- 旧版: 每次请求新建 Service 实例 → 缓存丢失
- 新版: Bridge 持有 Service 单例 → 缓存有效
- 旧版: 域路由分发 `_dispatch(domain, method)` → 命名不一致
- 新版: 直接方法调用 → 无命名问题

## 8. 缓存策略

### 8.1 缓存机制

```python
# ProjectOverviewService 内部缓存
self._cache: dict[str, tuple[float, ProjectInfo]] = {}
# key: 立项表文件路径
# value: (文件mtime, 解析结果)

def _get_or_parse(self, file_path: str) -> ProjectInfo:
    current_mtime = os.path.getmtime(file_path)
    if file_path in self._cache:
        cached_mtime, cached_data = self._cache[file_path]
        if cached_mtime == current_mtime:
            return cached_data  # 缓存命中
    # 缓存未命中或文件已修改，重新解析
    data = self._parser.parse(file_path)
    self._cache[file_path] = (current_mtime, data)
    return data
```

**特点**:
- 基于 mtime 判断，不使用 TTL
- 文件修改后自动失效
- 手动刷新: `refresh()` 方法强制清除缓存
- 变更单文件同理缓存

### 14.3 SPA 路由设计

**路由表**：

| 路由 | 模块 | 说明 |
|------|------|------|
| `#/dashboard` | dashboard.js | 总览页（默认路由） |
| `#/detail/:projectId` | detail.js | 项目详情页 |
| `#/change` | change.js | 变更管理中心 |
| `#/change/:changeNumber` | change.js | 变更单详情（变更管理页内子视图） |

**路由机制**：
- 基于 `window.onhashchange` 监听路由变化
- `app.js` 维护当前路由状态，切换时调用目标模块的 `render()` 方法
- 每个模块暴露统一接口：`{ render(container, params), destroy() }`
- 页面切换时先调用旧模块 `destroy()` 清理事件监听，再调用新模块 `render()`

```javascript
// app.js 路由核心逻辑
const routes = {
  '/dashboard':  { module: DashboardModule,  params: {} },
  '/detail':     { module: DetailModule,     params: {} },
  '/change':     { module: ChangeModule,     params: {} },
};

function navigate(hash) {
  const [route, ...paramParts] = hash.replace('#', '').split('/');
  const params = paramParts.join('/');  // e.g. "DJ-2026-005" or "CHG-PLC-2026-001"
  const match = routes['/' + route];
  if (!match) return navigate('/dashboard');  // 未知路由回首页

  if (currentModule) currentModule.destroy();
  currentModule = match.module;
  currentModule.render(contentContainer, params);
  updateNavActive(route);
}
```

### 14.4 Bridge API 封装层（api.js）

**设计意图**：统一 Bridge 调用方式，处理异步等待、错误解析、加载状态。

```javascript
// api.js
const Api = {
  _ready: false,

  async _ensureReady() {
    if (this._ready) return;
    await new Promise(resolve => {
      if (window.pywebview && window.pywebview.api) {
        this._ready = true; resolve();
      } else {
        window.addEventListener('pywebviewready', () => {
          this._ready = true; resolve();
        });
      }
    });
  },

  async _call(method, ...args) {
    await this._ensureReady();
    const api = window.pywebview.api;
    const result = await api[method](...args);
    // Bridge 返回 {error, message} 表示错误
    if (result && result.error) {
      throw { type: result.error, message: result.message };
    }
    return result;
  },

  // 项目总览
  getWorkspaceProjects()    { return this._call('get_workspace_projects'); },
  getProjectDetail(id)      { return this._call('get_project_detail', id); },
  getProjectChanges(id)     { return this._call('get_project_changes', id); },
  refreshCache(id)          { return this._call('refresh_cache', id || null); },

  // 变更管理
  createChangeRequest(pid, fields)  { return this._call('create_change_request', pid, fields); },
  listChangeRequests(pid, filters)  { return this._call('list_change_requests', pid, filters); },
  getChangeRequest(num)             { return this._call('get_change_request', num); },
  transitionStatus(num, status, kw) { return this._call('transition_status', num, status, kw); },
};
```

```
用户点击流转按钮（如"提交审批"）
  → JS 调用 Api.transitionStatus(number, newStatus, {approver, comment})
  → 成功：刷新详情，显示成功 Toast
  → 失败（TransitionGuardError）：
    → 弹出模态框，标题"门禁条件未满足"
    → 逐条列出未满足的条件（从 error.message 解析）
    → 每条条件旁显示对应章节名称（如"§4 变更原因"）
    → 关闭模态框后用户可手动编辑变更单文件补充内容
  → 失败（SpecViolationError）：
    → 弹出提示"状态流转不合法"，显示具体原因
```
