## 1. 需求定义

### 1.1 问题陈述

**现状**: SW-2026-005 当前只有2个P0功能（项目总览+变更管理），plc-init/plc-check 虽已实现但仅限 CLI，且缺少自动修复和文档标准化能力。

**痛点**: 对 `0100_PLC自动化/` 全量扫描结果显示：

| 项目 | pass | warn | fail | 主要问题 |
|------|------|------|------|----------|
| SysLib | 2 | 1 | 6 | 缺PRD目录、缺标准目录结构 |
| DJ-2026-000 | 3 | 0 | 6 | 缺PRD目录、缺标准目录结构 |
| DJ-2026-005 | 4 | 0 | 4 | 缺.plc.json(根目录)、缺04_变更管理 |
| FB_1011 | 6 | 1 | 0 | PASS（仅warn无.plc.json） |
| FB_1012 | 1 | 3 | 3 | 缺PM_SESSION/REQ/TEC，PRD命名不标准 |
| FB_1013 | - | - | - | 未扫描到（depth不足） |
| FB_1014 | - | - | - | 未扫描到（depth不足） |

**根因**:
1. 无工具强制执行 LSP-907 规范，项目结构靠人工维护
2. PRD 文档命名不统一（标准命名 vs 带版本号命名）
3. 缺失文档无自动检测和补全机制
4. PLC 技能每次检查需消耗大量上下文重复读取规范

**用户核心诉求**: "我需要PLC管理工具来迭代增加功能，减少技能的上下文"——工具应承载更多标准化逻辑，AI技能只做决策判断。

### 1.2 目标

将「PLC项目标准化管理」提升为第三个核心功能模块，与项目总览、变更管理并列：

| 优先级 | 功能 | CLI | GUI | 核心价值 |
|--------|------|-----|-----|----------|
| **P0** | 结构合规检查 | ✅ 已有 | 新增 | 一眼看到所有项目的合规状态 |
| **P0** | 项目初始化 | ✅ 已有 | 新增 | 向导式创建标准项目骨架 |
| **P1** | 自动修复 | 新增 | 新增 | 一键补全缺失目录/文件/配置 |
| **P1** | 文档标准化 | 新增 | 新增 | 检测并修正非标准命名 |

### 1.3 成功标准

| 维度 | 指标 | 目标值 |
|------|------|--------|
| **合规率** | `plc-check --all` 全PASS项目数 | ≥80% |
| **修复效率** | 从检测到修复完成 | ≤3次点击/命令 |
| **上下文节省** | PLC技能规范检查时读取规范文件次数 | 减少50% |
| **GUI覆盖** | 标准化管理功能在GUI中可用 | 4个子功能全部可用 |

### 1.4 非目标

- 不做 SCL 代码规范检查（由 PLC 技能 + LSP 插件负责）
- 不做 SCL 代码自动生成/修改
- 不做 PRD 文档内容生成（只生成模板骨架）
- 不替代 PLC 技能做代码评审

## 2. 功能设计

### 2.1 结构合规检查（plc-check）

**现状**: CLI 已实现，7项检查（.plc.json/PM_SESSION/PRD目录/PRD文档/目录结构）。

**扩展点**:

| 扩展项 | 说明 |
|--------|------|
| 扫描深度 | 默认 depth=2 改为 depth=4，覆盖 SysLib/actuator/FB_xxx 三级嵌套 |
| 项目识别 | 新增 FB_前缀识别（已修复）、.scl文件存在性识别、PRD目录存在性识别 |
| 检查项扩展 | 新增：.plc.json libraries 路径有效性、PRD文档命名规范性检查 |
| 批量报告 | CLI 输出汇总表（项目数/通过/警告/失败/合规率） |

**CLI 命令**（已有，增强）:
```
plc-check [项目路径]              # 单项目检查
plc-check --all [--depth N]       # 批量扫描
plc-check --all --json            # JSON输出（供GUI消费）
```

**GUI 交互**:
- 独立标签页「标准化管理」
- 顶部：合规性仪表盘（总项目数/通过/警告/失败/合规率环形图）
- 中部：项目列表表格（项目名/类型/状态/通过数/警告数/失败数/操作按钮）
- 底部：选中项目的检查详情面板（逐项 pass/warn/fail + 修复建议）

### 2.2 项目初始化（plc-init）

**现状**: CLI 已实现，支持 standard 和 syslib_fb 两种项目类型。

**扩展点**:

| 扩展项 | 说明 |
|--------|------|
| SysLib FB 初始化 | 新增 syslib_fb 类型的初始化模板（FB_xxx.scl + PRD四件套 + PM_SESSION） |
| 库引用自动计算 | 根据项目位置自动计算 libraries 相对路径 |
| GUI 向导 | 4步向导：项目类型 → 编号/名称 → 库引用 → 确认创建 |

**CLI 命令**（已有，增强）:
```
plc-init <项目编号> <项目名称> [--type standard|syslib_fb] [--description ...] [--dry-run]
```

**GUI 交互**:
- 标签页内「新建项目」按钮 → 弹出向导模态框
- Step 1: 选择项目类型（标准项目 / SysLib功能块）
- Step 2: 填写编号+名称+描述
- Step 3: 预览将创建的文件列表（dry-run）
- Step 4: 确认创建 → 进度条 → 完成提示

### 2.3 自动修复（plc-repair）★新增

**功能**: 自动修复 plc-check 发现的 FAIL 项。

**修复规则表**:

| 检查项 | FAIL 原因 | 修复动作 | 破坏性？ |
|--------|-----------|----------|----------|
| .plc.json | 缺失 | 生成模板 .plc.json（含 libraries 自动计算） | 否 |
| .plc.json | 字段不完整 | 补全缺失字段（name/description/version） | 否 |
| .plc.json libraries | 路径无效 | 重新计算相对路径 | 否 |
| PM_SESSION | 缺失 | 生成 PM_SESSION 模板 | 否 |
| PRD 目录 | 缺失 | 创建 PRD/ 目录 | 否 |
| PRD/REQ | 缺失 | 生成 REQ 模板 | 否 |
| PRD/INT | 缺失 | 生成 INT 模板 | 否 |
| PRD/DSN | 缺失 | 生成 DSN 模板 | 否 |
| PRD/TEC | 缺失 | 生成 TEC 模板 | 否 |
| LSP-907 目录 | 缺失 | 创建标准目录（02_PLC程序/通用ST程序及变量表 等） | 否 |
| PRD 文档命名 | 非标准 | 重命名为标准格式 | **是，需确认** |

**安全策略**:
- 所有修复默认执行，仅破坏性操作（文件重命名）需用户确认
- 修复前自动备份被重命名的文件（.bak 后缀）
- dry-run 模式：只显示将要执行的修复动作，不实际执行
- 修复日志：记录所有修复操作到 PM_SESSION §6

**CLI 命令**:
```
plc-repair <项目路径> [--dry-run]           # 单项目修复
plc-repair --all [--dry-run]                # 批量修复
plc-repair <项目路径> --rename-confirm      # 确认文件重命名
```

**GUI 交互**:
- 检查结果面板中，每个 FAIL 项旁有「修复」按钮
- 底部有「一键修复全部」按钮
- 点击修复 → 弹出确认对话框（列出修复动作）→ 执行 → 刷新检查结果
- 破坏性操作（重命名）单独弹出确认，显示原文件名→新文件名

### 2.4 文档标准化（plc-standardize）★新增

**功能**: 检测并修正 PRD 文档的非标准命名。

**命名规范**（LSP-907 + SysLib FB 标准）:

| 标准文件名 | 允许的非标准格式（自动识别） |
|------------|------------------------------|
| `需求分析文档_REQ.md` | `需求文档_PRD-*.md`, `*_REQ.md` |
| `接口文档_INT.md` | `接口文档_IFC-*.md`, `*_INT.md` |
| `详细设计说明书_DSN.md` | `详细设计说明书_DSN-*.md`, `*_DSN.md` |
| `技术方案文档_TEC.md` | `技术方案文档_TEC-*.md`, `*_TEC.md` |

**标准化流程**:
1. 扫描 PRD/ 目录下所有 .md 文件
2. 匹配非标准命名模式
3. 生成重命名计划（原路径 → 新路径）
4. 用户确认后执行重命名
5. 同步更新文档内的关联引用（如 DSN 中引用 IFC 的文件名）

**CLI 命令**:
```
plc-standardize <项目路径> [--dry-run]      # 检测并预览标准化建议
plc-standardize <项目路径> --apply          # 执行重命名
plc-standardize --all --dry-run             # 批量检测
```

**GUI 交互**:
- 检查结果面板中，WARN 项（命名不匹配）旁有「标准化」按钮
- 点击后弹出重命名预览（原文件名 → 新文件名）
- 确认后执行，自动更新关联引用

## 5. 风险与约束

| 风险 | 等级 | 缓解措施 |

## 6. 与 PLC 技能的协作模型

**目标**: 工具承载标准化逻辑，技能只做决策判断。

| 场景 | 工具职责 | 技能职责 |
|------|----------|----------|
| 项目结构检查 | plc-check 自动执行7项检查 | 整合结果到验证报告 |
| 项目初始化 | plc-init 创建标准骨架 | 审查骨架是否符合工艺需求 |
| 自动修复 | plc-repair 补全缺失文件 | 确认修复不破坏现有逻辑 |
| 文档标准化 | plc-standardize 重命名文件 | 确认重命名不影响文档引用 |
| SCL 代码评审 | 不参与 | 完全由技能负责 |
| 规范合规判断 | 提供结构化数据 | 基于数据做合规结论 |

**技能上下文节省**:
- 之前：PLC技能每次检查需读取 LSP-907 规范 + 扫描目录 + 逐项判断（~5000 token）
- 之后：PLC技能调用 plc-check 获取结构化结果（~500 token），节省 90%
