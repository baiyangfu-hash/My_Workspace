## 1. 计划目标

本计划用于指导 `SW-2026-005` 当前主线的测试设计、测试执行、缺陷回归和发布验收，重点覆盖以下目标：

- 验证产品已按“**Trae伴生式 PLC 工作空间治理工具**”定位落地，而非继续按单项目主工具演进
- 验证 `Workspace / Child Project / Shared Library / Spec Directory` 模型在识别、加载、治理、跳转和汇总链路上完整闭环
- 验证 `GLM5.1` 执行顺序对应的代码落点与测试落点一致，避免“实现顺序正确但回归口径缺失”
- 验证 GUI 入口、项目打开行为、伴生跳转、跨项目治理、共享库治理、聚合报告、文档同步等主链路无回归
- 建立面向 Python 研发、PM 管理、PLC 交付三方都可复用的验收口径

## 4. 测试策略

### 4.1 总体策略

采用“**低依赖优先、自动化为主、GUI 验证补位、验收双口径闭环**”的策略：

1. 单元测试验证识别规则、治理算法、状态流转、异常分支
2. 集成测试验证 Service 到 Controller 到 UI 的调用链和对象协作
3. GUI 测试验证导航、项目打开、状态提示、项目树展示与伴生跳转入口
4. 回归测试验证已修复关键问题不复现
5. 验收测试用 PLC 与 PM 两套口径确认是否满足交付标准

### 4.2 低依赖策略

本项目当前主线强调“工作空间治理”而非“硬件联调”，测试计划采用如下低依赖实施原则：

| 策略编号 | 策略 | 说明 | 验证方式 |
|---|---|---|---|
| LDS-01 | 文件系统仿真优先 | 通过临时目录、伪造 `workspace.json`、`.plc.json`、DJ 三标记构造测试资产，不依赖真实大型项目库 | `pytest` 临时目录 + 夹具 |
| LDS-02 | Service 层独立验证 | 识别、扫描、聚合、冲突检测优先在 Service 层完成测试，不依赖 GUI 事件链 | `test_workspace.py` / `test_library_governance.py` / `test_workspace_governance.py` |
| LDS-03 | 外部打开能力可替身 | `Trae CLI`、系统默认打开、Excel 打开等能力通过 mock/stub 验证，不要求测试机必须安装全部外部工具 | `test_companion.py` |
| LDS-04 | GUI 只测入口与映射 | GUI 测试重点验证入口、映射、状态反馈和信号连通，不在 GUI 层重复验证全部业务细节 | `test_gui_navigation.py` + 手工 GUI 冒烟 |
| LDS-05 | 文档与报告做结构验证 | 对 CHG/IFC/聚合报告优先校验字段、文件生成、回写结果与路径，不强依赖人工内容审阅 | `test_sync_engine.py` / `test_chg_ifc_generator.py` |
| LDS-06 | 伴生降级必须可测 | 任何依赖 Trae 的能力都必须存在降级链路，测试必须覆盖“Trae 成功”和“Trae 不可用”两种情况 | `TC-C07` / `TC-C08` / `TC-C09` |
| LDS-07 | 不引入未来依赖 | 不把 `pygls`、TIA、在线 PLC 通信等储备方向依赖混入当前测试基线 | 范围检查 + 发布前审查 |

### 4.3 分层测试策略

| 测试层级 | 目标 | 主体 | 工具/方式 | 进入标准 | 退出标准 |
|---|---|---|---|---|---|
| 单元测试 | 验证单模块逻辑正确 | Service / Checker / Parser / Model | `pytest` | 模块可独立实例化 | 核心断言全部通过 |
| 集成测试 | 验证模块交互正确 | Controller + Service + 事件流 | `pytest` + mock | 单元测试稳定 | 关键链路无异常 |
| GUI 测试 | 验证入口、映射、打开链路与可用性 | MainWindow / ProjectTree / 导航 | 自动化 + 手工 | 集成测试稳定 | P0 GUI 链路全部通过 |
| 回归测试 | 验证历史问题不复现 | 全主线 | 自动化为主 | 缺陷已修复 | 指定 Bug 未复现 |
| 验收测试 | 验证 PM/PLC 交付口径 | 项目经理 / 测试负责人 | 测试矩阵 + 报告审查 | 前序测试通过 | 满足双口径标准 |

### 4.4 P0/P1/P2 优先级矩阵

| 优先级 | 判定口径 | 典型范围 | 代表场景 | 执行要求 | 发布影响 |
|---|---|---|---|---|---|
| P0 | 阻断“启动-打开-导航-检查”主链，或导致程序崩溃/错误分支 | GUI 启动、主窗口初始化、项目打开、工作空间识别、导航映射、核心菜单入口 | 程序无法启动；工作空间打开失败；主窗口空白；菜单 `Ctrl+O/F5/F6` 无效；诊断/规范检查双击跳转崩溃 | 每轮必须优先执行并保留截图/日志/失败堆栈 | 任一未关闭即“不通过” |
| P1 | 主流程可继续但关键能力明显受损，影响用户完成治理任务 | 伴生跳转降级、诊断面板、规范检查面板、聚合报告、共享库治理 | 诊断能开面板但无法执行；规范检查可启动但结果列表/详情区异常；异常目录打开后状态栏与树不同步 | 在 P0 通过后立即执行；修复后必须做专项复测 | 未接受的 P1 不允许“通过” |
| P2 | 有替代路径，不阻断主流程，但影响效率、可观测性或局部体验 | 非关键提示文案、局部统计、主题切换、次要按钮、结果展示细节 | 统计数字展示偏差；状态栏提示不友好；最近项目菜单刷新延迟；导出提示信息不完整 | 可并入回归批次执行；建议版本前清理 | 可带条件放行，但需登记风险与 workaround |

## 6. GLM5.1 任务分派测试计划

### 6.1 分派原则

`GLM5.1` 的开发顺序在主线文档中已被固定为：

`constants -> artifact_registry_service -> project_service -> project_controller -> tests`

测试计划必须对这条分派链做同步验证，确保：

- 实现顺序符合低依赖拆解
- 每一层都有独立可验证输出
- 上一层失败不会把问题扩散到下一层
- 文档更新与代码更新同步

### 6.2 GLM5.1 分派矩阵

| 分派阶段 | 对应代码落点 | 核心目标 | 主要风险 | 测试重点 | 对应用例/文件 |

## 11. 缺陷分级与回归要求

### 11.1 缺陷分级

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 阻断发布 | 程序无法启动、工作空间无法打开、打开走错分支、关键 GUI 断路 |
| P1 | 严重影响主流程 | 共享库识别错误、伴生跳转全部失效、聚合报告字段缺失 |
| P2 | 有替代路径 | 个别统计不准、个别摘要文案错误、局部 UI 提示不友好 |
| P3 | 轻微问题 | 展示类文案、样式或非关键提示问题 |

### 11.2 必回归问题

- `BUG-OPEN-001`：无法打开现有 DJ 项目
- 工作空间打开错误提示残留问题
- ToolBox 与 TabWidget 映射错误类问题
- 伴生跳转失败后无降级问题
- 共享库误判、命名冲突漏检、聚合报告缺字段问题

### 11.3 回归规则

- 所有 P0/P1 缺陷修复后必须补对应自动化或结构化回归用例
- 不允许仅通过人工口头确认关闭主线缺陷
- 缺陷关闭前必须至少完成一次“修复后重跑 + 相关场景抽检”

### 11.4 失败判定

出现以下任一情况，本轮测试应直接判定为失败或阶段失败：

- `P0` 用例存在 1 项失败、阻塞或未执行且无批准豁免
- GUI 启动、主窗口初始化、项目打开、导航映射、诊断/规范检查主链出现崩溃、卡死、错误分派
- 工作空间或 DJ 单项目打开后出现“状态栏成功但项目树为空”之类的假成功态
- 诊断面板或规范检查面板无法启动后台任务、无法展示结果、无法执行源码跳转
- 自动化结果、手工证据、文档口径三者互相矛盾，无法形成唯一结论

### 11.5 复测条件

出现以下情况时，必须触发专项复测或阶段回归：

- 修改 `main.py`、`main_window.py`、`menu_manager.py`、`project_controller.py`、`navigation_controller.py`、`diagnostic_panel.py`、`spec_check_panel.py`
- 修复任何 `P0/P1` 缺陷，必须复测“原失败用例 + 相邻功能 + 至少一轮主链冒烟”
- 调整工作空间识别、项目加载、伴生跳转、Dock 装配、线程执行逻辑
- 变更运行依赖或测试环境，如 `PyQt5`、`openpyxl`、配置文件结构、默认目录结构
- 文档或验收口径发生变更，需复测相关结论项并同步更新证据
