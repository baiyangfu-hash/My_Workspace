## 3. 补充计划

### 3.1 计划目标

- 补充缺失的规范内容到全局规范文件
- 确保全局规范与项目实际使用的规范保持一致
- 提高规范的可操作性和实用性
- 为项目命名规范添加最佳实践和具体举例

### 3.2 补充内容

#### 3.2.1 项目命名规范
- **项目编号格式**：业务线代码-年份-序号（如SW-2026-004）
- **项目名称格式**：小写字母，单词之间用下划线分隔（如python_project_management_tool）
- **最佳实践**：
  - 使用描述性名称，准确反映项目功能
  - 避免使用缩写，除非是广泛认可的缩写
  - 保持名称简洁，避免过长
  - 确保名称在组织内部唯一
- **具体举例**：
  - 良好示例：`python_web_api`、`data_analysis_tool`、`machine_learning_model`
  - 不良示例：`py_api`、`data_tool`、`ML_model`

#### 3.2.2 代码格式规范
- 缩进规则：4个空格
- 行长度限制：100个字符
- 长行换行规则
- 空行使用规则：函数之间2行，类之间3行

#### 3.2.3 注释规范
- 文件注释：模块文档字符串格式
- 类注释：类文档字符串格式
- 函数注释：函数文档字符串格式，包含Args、Returns、Example
- 行内注释：使用#号，位置规则

#### 3.2.4 类型注解规范
- 基本类型注解
- 复杂类型：Optional、List、Dict、Tuple等
- 类型导入规则

#### 3.2.5 错误处理规范
- 异常捕获：捕获特定异常
- 异常抛出：使用自定义异常
- 错误日志：详细记录错误信息

#### 3.2.6 导入规范
- 导入顺序：标准库 → 第三方库 → 本地模块
- 导入分组：按类型分组

#### 3.2.7 代码组织规范
- 文件结构：导入 → 常量 → 类 → 函数
- 类组织：特殊方法 → 公共属性 → 公共方法 → 私有方法

#### 3.2.8 最佳实践
- 避免全局变量
- 使用上下文管理器
- 使用列表推导式

#### 3.2.9 代码审查检查清单
- 命名检查
- 格式检查
- 注释检查
- 类型检查
- 错误处理检查
