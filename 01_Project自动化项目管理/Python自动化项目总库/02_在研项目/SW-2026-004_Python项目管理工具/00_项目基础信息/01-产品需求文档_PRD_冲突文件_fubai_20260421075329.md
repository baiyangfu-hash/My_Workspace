# 自动化项目管理工具产品需求文档 (PRD)

## 1. 产品概览

自动化项目管理工具是一个专为自动化领域设计的全生命周期管理系统，支持多种技术栈（PLC、Python、上位机等）和多种业务线（软件开发、单机设备、自动化整线、系统升级、维保项目），旨在解决项目管理标准化、效率提升、质量保证和版本控制的核心痛点。

**核心价值**：
- 标准化项目管理流程，确保项目规范执行
- 提高开发效率，减少手动操作和重复工作
- 确保项目质量，通过完善的测试和监控机制
- 简化版本控制，避免版本混乱和冲突
- 提供插件系统，支持功能扩展和定制
- 规范管理，确保项目遵循最新的行业标准和内部规范
- 多技术栈支持，统一管理不同技术平台的项目

**目标市场**：
- 企业内部自动化开发团队
- PLC自动化工程师
- Python软件开发团队
- 自动化项目管理人员
- 中小型自动化集成公司
- 设备制造商
- 系统升级和维护团队

## 2. 核心功能

### 2.1 总库管理

| 功能模块 | 功能描述 | 用户价值 |
|---------|---------|----------|
| **总库创建与配置** | 创建和配置项目总库，设置总库基本信息和参数 | 统一管理自动化项目，建立标准化的项目集合 |
| **项目导入与管理** | 将现有项目导入总库，支持项目的添加、删除、更新操作 | 方便项目管理，实现项目的集中化管理 |
| **项目分类管理** | 对总库中的项目进行分类管理，支持自定义分类 | 项目组织清晰，便于查找和管理 |
| **项目搜索与过滤** | 支持根据项目名称、类型、状态等条件搜索和过滤项目 | 快速定位项目，提高工作效率 |

| 功能模块 | 功能描述 | 用户价值 |

## 3. 核心流程

### 3.1 总库管理流程

1. **总库创建**：用户创建总库，设置名称、路径、描述等基本信息
2. **项目导入**：用户导入现有项目或创建新项目到总库
3. **项目分类**：用户创建分类结构，将项目分配到对应分类
4. **项目搜索**：用户根据条件搜索和过滤项目
5. **项目管理**：用户对项目进行编辑、删除、移动等操作

### 3.2 模板管理流程

1. **模板创建**：用户创建项目模板，定义目录结构、文件模板和配置参数
2. **模板分类**：按业务线（SW/DJ/ZD/XT/WX）、编译器、适用场景对模板进行分类
3. **模板版本管理**：管理模板版本，支持版本更新和回滚
4. **模板应用**：根据模板创建新项目，自动生成分录结构和文件
5. **模板更新**：更新模板内容，同步到使用此模板的项目

### 3.3 项目变更管理流程

1. **变更发起**：用户提交变更申请，描述变更内容和原因
2. **变更审批**：审批人审核变更申请，评估影响
3. **变更执行**：执行变更操作，记录变更历史
4. **版本管理**：创建项目版本，添加标签和描述
5. **版本比较**：比较不同版本间的差异
6. **版本回滚**：在需要时回滚到之前的版本

### 3.4 统一构建与部署流程

1. **构建配置**：用户配置构建参数，如Python版本、测试命令等
2. **构建执行**：系统执行构建操作，生成构建结果
3. **构建验证**：系统验证构建结果，检查构建是否成功
4. **部署配置**：用户配置部署目标和参数
5. **部署执行**：系统将构建结果部署到目标环境
6. **部署验证**：系统验证部署结果，确保部署成功

### 3.5 规范管理流程

1. **规范检查**：系统检查项目引用的全局规范是否有更新
2. **更新评估**：用户评估规范更新的影响和必要性
3. **规范同步**：系统将规范同步到最新版本
4. **版本管理**：记录规范的版本变更历史
5. **应用验证**：验证规范更新后项目的兼容性

## 5. 非功能性需求

### 5.1 性能需求

- **响应时间**：总库管理操作响应时间小于2秒，项目搜索和过滤操作响应时间小于1秒，统计分析操作响应时间小于3秒
- **并发处理**：支持至少100个并发用户
- **项目管理能力**：支持管理至少1000个项目而不影响性能

### 5.2 可靠性需求

- **系统稳定性**：系统连续运行24小时无故障
- **数据一致性**：数据存储采用事务机制，确保数据一致性
- **数据备份**：支持自动和手动数据备份
- **数据恢复**：支持数据恢复功能

### 5.3 安全性需求

- **用户认证**：支持用户认证和授权机制
- **权限控制**：支持基于角色的权限控制
- **数据加密**：数据传输采用加密机制
- **安全防护**：防止SQL注入、XSS等安全漏洞

### 5.4 兼容性需求

- **Python版本**：支持Python 3.8+版本的项目
- **框架兼容**：兼容主流的Python框架（如Django、Flask、PyQt5等）
- **PLC平台**：支持西门子Step7/TIA Portal等主流PLC编程平台
- **上位机开发**：支持Python上位机、HMI开发
- **多技术栈**：支持PLC、Python、上位机等多种自动化技术栈的混合项目
- **操作系统**：支持Windows、Linux、MacOS等主流操作系统

### 5.5 可扩展性需求

- **模块化设计**：采用模块化设计，模块间低耦合
- **插件机制**：支持插件机制，便于扩展功能
- **第三方集成**：支持第三方工具集成

### 5.6 易用性需求

- **用户界面**：提供直观的图形化用户界面
- **操作流程**：操作流程符合用户习惯
- **帮助文档**：提供详细的操作指引和帮助文档
- **快捷键**：支持快捷键和批量操作

## A.2 跨机器部署能力 [V2.5.7]

### FR-PATH-001: 相对路径支持

**功能描述**：
将默认的项目路径从绝对路径改为相对路径 `./Projects`（相对于EXE所在目录），实现解压即用的零配置部署。

**核心特性**：

| 特性 | 说明 |
|------|------|
| **默认路径** | `./Projects`（EXE所在目录下的Projects子目录） |

| **跨盘符支持** | 可部署到C:、D:、E:等任意盘符 |
| **跨机器支持** | 可在不同Windows机器间直接复制使用 |
| **USB便携** | 可从U盘直接运行 |

**技术实现要点**：
- 使用 `sys._MEIPASS` 或 `os.path.dirname(sys.executable)` 获取EXE所在目录
- 所有内部路径基于EXE所在目录进行相对路径解析
- 兼容PyInstaller冻结环境和普通Python环境

**用户价值**：
- 部署效率提升90%以上（无需逐机配置）
- 降低运维成本，减少配置错误
- 支持现场快速部署和演示

### FR-PATH-002: 路径优先级链路

**功能描述**：
建立4级降级策略的路径解析链路，确保在各种环境下项目路径始终可用。

**4级降级策略**：

| 优先级 | 路径来源 | 适用场景 | 说明 |
|-------|---------|---------|------|
| **P1（最高）** | 用户自定义配置路径 | 用户明确指定了项目根目录 | 尊重用户显式配置 |
| **P2** | 环境变量 `PROJECT_ROOT` | 企业统一下发环境变量 | 支持企业级统一管理 |
| **P3** | EXE相对路径 `./Projects` | 标准解压即用场景 | 默认推荐方式 |
| **P4（最低）** | 当前工作目录 | 兜底方案 | 开发调试时使用 |

**PyInstaller冻结环境兼容性**：

| 环境 | `sys.executable` | `sys._MEIPASS` | 推荐策略 |
|------|-----------------|-----------------|---------|
| PyInstaller冻结（单文件） | EXE完整路径 | 临时解压目录 | 使用 `dirname(sys.executable)` |
| PyInstaller冻结（目录） | EXE完整路径 | 同exe目录 | 使用 `dirname(sys.executable)` |
| 普通Python环境 | Python解释器路径 | 不存在 | 使用当前工作目录或配置 |

**用户价值**：
- 极大提升系统的环境适应能力
- 在各种异常情况下仍能正常工作
- 方便开发和调试阶段的灵活切换

## A.3 数据库自愈机制 [V2.5.9]

### FR-DBH-001: 启动时自动清理旧绝对路径

**功能描述**：
系统启动时自动检测并清理数据库中存储的旧绝对路径引用，将其转换为相对路径或当前有效的路径。

**触发时机**：
- 应用程序主窗口初始化时
- 首次打开数据库连接时

**处理逻辑**：

```
1. 检测数据库中的路径字段（project_path, repo_path 等）
2. 判断路径类型：
   - 若为绝对路径且不存在 → 标记为需清理
   - 若为绝对路径且存在 → 保持不变
   - 若为相对路径 → 保持不变
3. 对需清理的路径：
   - 尝试基于当前EXE目录进行相对路径重建
   - 若重建成功则更新数据库
   - 若重建失败则标记为"路径失效"
4. 生成自愈报告，记录所有变更
```

**用户价值**：
- 解决跨机器/跨目录移动后路径失效问题
- 减少手动修复数据库的工作量
- 提升系统的鲁棒性和容错能力

### FR-DBH-002: 分类幂等补全

**功能描述**：
当检测到项目引用的分类ID在分类表中不存在时，自动创建缺失的分类记录，确保数据一致性。

**补全规则**：

| 场景 | 处理方式 |
|------|---------|
| 分类ID不存在 | 自动创建该分类，名称为"自动恢复_分类ID"，父分类为根分类 |
| 分类名称为空 | 使用分类ID作为名称 |
| 循环引用检测 | 检测并阻断循环引用，设置父分类为根分类 |
| 批量补全 | 对所有缺失分类一次性补全，避免重复操作 |

**幂等性保证**：
- 多次执行结果一致
- 已存在的分类不会被覆盖或修改
- 补全操作可回滚（通过变更日志）

**用户价值**：

| #2 | `app_config.json` (应用配置) | GUI界面显示、关于对话框 |
| #3 | `app_config.json` (打包配置) | 打包脚本读取、ZIP文件名生成 |

**同步机制**：

```python
# version.py 作为主源头
__version__ = "2.5.9"

# app_config.json 从 version.py 读取或由打包脚本同步
{
  "version": "2.5.9",  # 必须与 version.py 一致
  ...
}
```

**用户价值**：
- 消除版本号不一致导致的混乱
- 确保用户看到的版本与实际运行的版本一致
- 便于问题追溯和版本管理

### FR-VER-002: package.py 打包前自动校验

**功能描述**：
`package.py` 打包脚本在执行构建前，强制执行三处版本号一致性校验，不一致则立即终止打包流程。

**校验流程**：

```
package.py 执行开始
    ↓
读取 version.py → 获取 VER_PYTHON
    ↓
读取 app_config.json (应用) → 获取 VER_CONFIG_APP
    ↓
读取 app_config.json (打包) → 获取 VER_CONFIG_PKG
    ↓
比对三者是否完全一致？
    ├── 是 → 继续打包流程
    └── 否 → 终止并输出错误信息：
        ❌ 版本号不一致！
          version.py:       2.5.9
          app_config(应用): 2.5.8  ← 不匹配
          app_config(打包): 2.5.9
        请先统一版本号后重试。
```

**错误处理**：
- 非零退出码（exit code = 1）
- 详细的不一致信息输出
- 建议修复命令或步骤

**用户价值**：
- 在构建环节拦截版本号不一致问题
- 避免发布错误的版本
- 强制开发者保持版本号规范
