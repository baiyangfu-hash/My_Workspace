## 5. 版本详细变更说明

### V2.1.0 版本详细变更 - 变更管理模块工程化升级 ⭐

#### 变更概述
- **变更日期**: 2026-04-12
- **变更类型**: 架构升级 (重大)
- **变更人**: AI Assistant
- **审批人**: 项目负责人
- **规范依据**: DJ-2026-014项目最佳实践 → 043/041/040 V2.1.0规范

#### 变更背景
在DJ-2026-014三段式玻璃输送线控制系统项目中实践验证了**变更管理规范V2.1.0精简工程版**，发现原V1.x实现存在以下问题：
1. 分类体系单一（仅6种软件类型，无法覆盖ELEC/MECH/PLC等工程领域）
2. 台帐采用内嵌详情模式（违反Single Source of Truth原则）
3. 无分级审批机制（所有变更走同一审批流）
4. 目录结构不符合043规范（05_变更管理 vs 04_变更管理）

#### 变更内容 (5大模块, ~1200行代码)

**1️⃣ 常量层升级 (constants.py)**
```python
# 新增枚举: Domain(7) + Nature(5) + Scope(5) + ApprovalLevel(5)
class Domain(Enum):    # ELEC, MECH, PLC, HMI, SCPT, DOCU, SAFE
class Nature(Enum):    # REQ, DEF, OPT, CFG, EMRG
class Scope(Enum):     # LOCAL, MODULE, SYSTEM, CROSS, SAFE
class ApprovalLevel(Enum):  # PROJECT_MANAGER, LEAD, TECH_DIRECTOR, EXECUTIVE, SAFETY_OFFICER

# 迁移映射 (向后兼容)
CHANGE_TYPE_TO_DOMAIN_MAP = {"code": Domain.SCPT, "需求": Domain.REQ, ...}  # 17项
IMPACT_LEVEL_TO_SCOPE_MAP = {"low": Scope.LOCAL, "medium": Scope.MODULE, ...}  # 6项
```

**2️⃣ 数据模型重写 (change.py)**
- 新增字段: `domain`, `nature`, `scope`, `priority`, `content_before`, `content_after`
- 新增字段: `related_changes`(JSON), `propagation_chain`(Text), `approval_level`, `reviewer`
- Helper方法: `generate_change_id()`, `migrate_from_v1()`, `needs_reviewer()`, `to_v2_dict()`
- 保留旧字段: `type`, `impact` (nullable, 兼容)

**3️⃣ 服务层重构 (change_service.py)**

| 方法 | 改动 |
|:----:|:-----|
| `_generate_change_content()` | 完全重写 → 符合040 V2.0.0模板(§1~§10) |
| `_generate_ledger_content()` | **完全重写** → 符合041 V2.1.0引用模式(4D统计+超链接+传播链矩阵) |
| `export_change()` | 路径修正: `05_变更管理/01_变更单/` → `04_变更管理/01_变更单/CHG-{DOMAIN}/` |
| `generate_ledger()` | 路径修正: `05_变更管理/03_变更记录/` → `04_变更管理/{项目}_版本变更台帐.md` |
| `get_statistics()` | 扩展: 2D(status+type) → **4D(+domain+nature+scope)** |
| `check_propagation_required()` | **新增**: 判断是否需要填写传播链(SYS/CROSS/SAFE) |
| `suggest_related_domains()` | **新增**: 智能建议关联领域(11条规则) |

**4️⃣ DAO层扩展 (change_dao.py)**
- 新增: `list_by_domain()`, `list_by_nature()`, `list_by_scope()`, `find_propagation_chain()`
- 重写: `get_statistics()` 支持4D维度查询

**5️⃣ UI层升级 (change_manager.py)**
- 表格: 6列 → **9列** (序号/→链接/领域/性质/范围/标题/优先级/状态/日期)
- 筛选器: 仅状态 → **+领域(7选1)+性质(5选1)+范围(5选1)**
- 详情显示: V1.x字段(type/impact) → V2.1.0字段(domain/nature/scope/priority/approval_level/reviewer)
- 台帐路径: 2处同步更新为V2.1.0路径

**6️⃣ 目录模板更新 (constants.py - DEFAULT_TEMPLATES)**
- 9个模板的 `05_变更管理` 全部改为 `04_变更管理`
- TPL-PLC-STD-001: 6子目录 → 8子目录 (+7个CHG-{DOMAIN} + README)
- README内容: 符合043 V2.1.0规范 (二维分类表+SST原则+分级审批表)

#### 核心架构变化

```
V1.x (软件视角):
┌─────────────┐    ┌──────────────┐
│ type: 需求变更 │    │ impact: 高     │
│ (6种固定选项) │    │ (自由文本)     │
└─────────────┘    └──────────────┘

V2.1.0 (工程视角):
┌─────────────────────────────────────────┐
│ domain: PLC (WHO - 哪个专业?)           │
│ nature: DEF  (WHY - 为什么变?)          │
│ scope:  SYSTEM (WHERE - 影响到什么程度?) │
│ → 自动匹配: approval_level=技术总监      │
│ → 自动判断: needs_reviewer=True         │
│ → 自动建议: related=[HMI, DOCU, SAFE]   │
└─────────────────────────────────────────┘
```

### 6.3 版本管理规范

#### 6.3.1 版本号格式
遵循语义化版本规范（Semantic Versioning）：`MAJOR.MINOR.PATCH`

- **MAJOR（主版本号）**：不兼容的API修改
- **MINOR（次版本号）**：向下兼容的功能性新增
- **PATCH（修订号）**：向下兼容的问题修正

#### 6.3.2 版本递增规则
- **主版本号递增**：重大架构变更、不兼容的API修改
- **次版本号递增**：新增功能、向下兼容的API修改
- **修订号递增**：Bug修复、性能优化、文档更新

#### 6.3.3 版本发布流程
1. **变更申请**：提交变更单
2. **变更审批**：审批人审批变更
3. **变更执行**：执行变更内容
