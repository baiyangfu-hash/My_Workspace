# 变更管理规范更新建议 — V2.1.0 → V2.2.0（草案）

> **来源**: SW-2026-005 PLC项目管理工具 实施修复 (2026-06-12)
> **适用对象**: 电气工程师 / PLC工程师 / 项目经理(PM)
> **关联规范**: PM-042 通用变更管理流程规范 V2.1.0

---

## 一、本次更新的背景

在 SW-2026-005 项目实际使用中，发现 PM-042 §5.2 状态机定义与工具实现之间存在**三处不一致**，导致以下实际问题：

| # | 问题 | 影响 | 涉及角色 |
|---|------|------|----------|
| P0 | 验证不通过时无法退回返工 | 变更卡在「验收中」状态，无法回到实施 | PM、电气/PLC工程师 |
| P1 | 缺少验收中间态（待验收→验收中） | 实施完成后直接跳到验收，职责不清 | PM |
| P2 | 门禁逻辑对"部分不通过"未拦截 | 可将不通过的变更误关闭为已完成 | QA、PM |

**根本原因**: 工具代码中的状态机缺少 `pending_acceptance` 和 `accepting` 两个中间状态，且 `accepting → implementing` 返工路径的门禁条件施加错误。

---

## 二、状态机变更详解

### 2.1 变更前（有缺陷）

```
implementing ──→ completed    ← 直接跳转，无验收环节
     ↑                      |
     └──── 返工？(被门禁拦截) ┘
```

**问题**: 规范 PM-042 §5.2 第143行明确定义了 `accepting --> implementing: 验证不通过` 的合法路径，但工具实现中：
- 不存在 `accepting` 状态（验收中）
- 返工路径被错误地要求"验证全部通过"才能操作

### 2.2 变更后（已对齐规范）

```
                    ┌── 验证通过 ──→ completed ──→ closed
                    │
implementing ──→ pending_acceptance ──→ accepting
   ▲                                          │
   │              ┌── 验证不通过(返工) ─────────┘
   │              │
   └── 退回已批准 ←┘
```

### 2.3 新增状态说明

| 状态码 | 中文名称 | 说明 | 前置状态 | 后续操作 |
|--------|----------|------|----------|----------|
| `pending_acceptance` | 待验收 | 实施完成，等待PM指派验收人 | implementing | 开始验收 |
| `accepting` | 验收中 | 正在进行验收检查 | pending_acceptance | 完成验收 / 退回返工 |

### 2.4 关键路径：验收不通过时的返工流程

这是本次修复的**核心变更**。当验收结论为「部分不通过」或「需补充验证」时：

1. **不允许直接关闭** (`accepting → completed`) — 门禁会拦截并提示错误
2. **必须走返工路径** (`accepting → implementing`) — 系统自动记录返工原因到§9实施记录
3. 返工后重新走 `implementing → pending_acceptance → accepting` 流程

**门禁规则对比**:

| 操作路径 | 门禁条件 | 说明 |
|----------|----------|------|
| `approved → implementing`（首次进入实施） | 需要 §7 实施计划至少一条任务 | 首次实施必须先做计划 |
| `accepting → implementing`（验证不通过返工） | **无额外门禁** | 允许立即返回重做 |
| `accepting → completed`（完成验收） | 验证结论必须为「全部通过」 | 不通过则强制走返工 |

## 三、对各角色的操作影响

### 3.1 给电气工程师 / PLC工程师

#### 实施阶段

| 操作步骤 | 你看到的按钮 | 操作说明 |
|----------|-------------|----------|
| 1. 收到批准通知 | 「开始实施」 | 点击后进入 `implementing` 状态 |
| 2. 实施完成 | **「提交验收」** *(新增)* | 进入 `pending_acceptance`，等待PM指派验收人 |
| 3. 被退回返工 | （系统自动推送） | 状态回到 `implementing`，§9记录显示"返工重做"及原因 |

**重要变化**:
- ~~之前~~: 实施完成后没有明确的"提交验收"动作，状态模糊
- **现在**: 必须主动点击「提交验收」，明确交接点

#### 返工场景示例

> 场景: 你修改了PLC程序中的输送机联锁逻辑（CHG-PLC-2026-002），验收时发现急停回路未被覆盖。
>
> 旧行为: 验收人员点击「完成验收」→ 报错或卡住，不知道怎么处理
>
> 新行为:
> 1. 验收人员在 `accepting` 状态下选择 **「退回返工」**
> 2. 填写原因: "急停回路联锁未覆盖"
> 3. 你收到通知，变更单回到 `implementing`
> 4. §9新增一行: `2026-06-12 \| verifier \| 返工重做 \| 验证不通过: 急停回路联锁未覆盖 \| 返工中 \|`
> 5. 你补充修改后再次「提交验收」

### 3.2 给项目经理(PM)

#### 验收管理

| 操作步骤 | 你看到的按钮 | 操作说明 |
|----------|-------------|----------|
| 1. 工程师提交验收 | （看板显示 `pending_acceptance`） | 指派验收人 |
| 2. 开始验收 | **「开始验收」** *(新增)* | 进入 `accepting` 状态 |
| 3. 验收结论 | **「完成验收」** 或 **「退回返工」** *(新增)* | 根据实际情况选择 |

#### 看板列变化

| 旧看板列 | 新看板列 | 变化说明 |
|----------|----------|----------|
| 实施中 | 实施中 + **待验收** + **验收中** | 拆分为3个明确的状态 |
| - | **待验收** (`pending_acceptance`) | 新增：工程师已提交，等你指派验收 |
| - | **验收中** (`accepting`) | 新增：正在验收，待你决策 |

#### 决策树

```
你在「验收中」状态看到变更单 CHG-PLC-XXX
        │
        ├── 验证项全部满足预期？
        │       ├── 是 → 点「完成验收」→ 状态变为「已完成」✅
        │       └── 否 ↓
        │
        └── 点「退回返工」→ 填写原因 → 状态回到「实施中」
                （工程师收到通知，可重新实施）
```

## 四、门禁规则完整清单

以下是所有状态流转的门禁条件，供日常操作参考：

| 当前状态 | 目标状态 | 操作名称 | 门禁条件 | 不满足时提示 |
|----------|----------|----------|----------|-------------|
| draft | submitted | 提交变更 | §3全部填写 + §4非空 | "XX未填写" |
| submitted | under_review | 开始审核 | 无 | - |
| under_review | approved | 批准通过 | §8.1有审批记录 + 审批人非空 | "无审批记录/审批人为空" |
| under_review | conditionally_approved | 有条件批准 | 同上 + comment非空 | "需附条件说明" |
| under_review | rejected | 驳回 | 审批人+comment非空 | "审批人/驳回原因为空" |
| approved/conditionally_approved | implementing | 开始实施 | **§7实施计划至少一条任务** | "实施计划未填写" |
| **implementing** | **pending_acceptance** | **提交验收** | **§9实施记录至少一条** | **"实施记录未填写"** |
| **pending_acceptance** | **accepting** | **开始验收** | **无额外门禁** | - |
| **accepting** | **completed** | **完成验收** | **验证结论=「全部通过」** | **"结论为'部分不通过'，请用退回返工"** |
| **accepting** | **implementing** | **退回返工** | **无额外门禁** | - |
| implementing | approved | 退回已批准 | 无 | - |
| completed | closed | 关闭变更 | 无 | - |

> **粗体行 = 本次新增或修改的流转**

## 五、建议的规范文本修订

以下是对 PM-042 规范的具体修订建议，可直接纳入 V2.2.0 版本：

### 5.1 §5.2 看板交互规则 补充第5条

```markdown
**现有第4条**: 验收不通过时，变更单返回实施阶段重新实施

**新增第5条**: 验收不通过时，只能通过「退回返工」按钮返回实施阶段，
禁止在验证结论为「部分不通过」或「需补充验证」时执行「完成验收」操作。
系统将自动在校验阶段拦截此类操作并给出明确指引。
```

### 5.2 §5.7 变更验证 补充验证结论定义

```markdown
**新增内容**:
3. **验证结论分类**（必须在§10.2填写）:
   - 全部通过: 所有验证项均满足预期 → 可执行「完成验收」关闭变更单
   - 部分不通过: 存在不满足项但可修复 → 必须「退回返工」，不可关闭
   - 需补充验证: 数据不足无法判定 → 补充验证数据后重新判定
4. **返工机制**: 验证结论为非「全部通过」时，验收人应点击「退回返工」，
   系统将变更单退回至「实施中」状态并在§9记录返工原因。
```

### 5.3 §10.5 变更验证步骤 补充返工子流程

```markdown
**新增 3.5 返工处理步骤**:
1. 验收人在验收界面选择「退回返工」
2. 填写返工原因（必填，≤30字）
3. 系统自动:
   - 将变更单状态从「验收中」回退至「实施中」
   - 在§9实施记录追加一行返工记录（含原因和时间戳）
   - 通知实施工程师和项目经理
4. 实施工程师根据返工原因修正后重新「提交验收」
5. PM重新指派验收人，重复验收流程
```

### 5.4 版本号升级

```markdown
| 版本号 | 变更内容 | 变更日期 |
|--------|----------|----------|
| V2.2.0 | 新增验收中间态(pending_acceptance/accepting) + 返工路径门禁校验 | 2026-06-12 |
```
